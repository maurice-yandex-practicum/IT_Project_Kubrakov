# Открытые вопросы проекта АС «Каршеринг»

Документ содержит исходные вопросы проекта и дополнительные решения, выявленные при подготовке технического проекта. Вопрос считается закрытым после согласования решения владельцем проекта и, если решение влияет на модель, внесения изменений в ER, DFD, BPMN, архитектуру или технический проект.

## Исходные вопросы проекта

1. Нужно зафиксировать, что состояние ТС и телематическое событие дублируют друг друга. Это денормализация и она сделана для оптимизации запроса.
2. Мы не храним поломки в БД.
3. Мы вырезали зоны покрытия.

## Дополнительные вопросы, выявленные при подготовке технического проекта

4. Для F2 не определён источник точки поиска. **[Ответ: точка поиска передаётся арендатором в запросе (координаты); близость определяется по расстоянию между координатами; сортировка — по возрастанию расстояния; область поиска ограничивается радиусом.]**
5. DFD F2 обращается к хранилищу ТС, а местоположение показано в ER в сущности «Состояние». **[Ответ: F2 читает сведения о ТС и актуальное местоположение из сущности «Состояние».]**
6. Для F3 повторно выполняется проверка документов. **[Ответ: при аренде выполняется повторная проверка документов через имитатор (полная), как показано в BPMN.]**
7. В BPMN аренды второй запрос проверки документов был подписан как запрос проверки паспорта, но направлен системе проверки ВУ. **[Ответ: закрыт — подпись исправлена в BPMN.drawio(3): второй запрос подписан «Отправить запрос на проверку ВУ».]**
8. BPMN завершения аренды не полностью согласована с DFD по ветке неуспешной оплаты. **[Ответ: ТС блокируется и аренда завершается в обоих случаях; при неуспешном списании создаётся задолженность и арендатор уведомляется.]**
9. ER не содержит отдельную сущность «Платёж» и реквизиты внешней платёжной операции. **[Ответ: отдельная сущность не вводится; внешний идентификатор операции, её статус и время сохраняются у связанного обязательства (аренда, штраф или задолженность); идемпотентность F12 обеспечивается уникальностью внешнего идентификатора операции.]**
10. Не определён контракт платёжного шлюза. **[Ответ: обмен по HTTP; АС отправляет запрос на списание и получает ссылку либо результат; результат приходит callback-запросом; корреляция — по идентификатору операции; подлинность подтверждается подписью запроса.]**
11. В ER у парковки показан адрес, но нет координат; F5 должен подтверждать парковочное место по местоположению ТС. **[Ответ: парковка хранит координаты; подтверждение выполняется по расстоянию от ТС до парковки в пределах заданного радиуса.]**
12. Критерии формирования перечня ТС на обслуживание (F8) не заданы. **[Ответ: критерии — статус ТС «требует обслуживания», низкий уровень топлива или заряда, превышение пробега/интервала обслуживания.]**
13. F11 в DFD связан с администратором, а контекстная модель показывает запрос арендатора. **[Ответ: арендатор видит свои штрафы и задолженности, администратор — по всем арендаторам.]**
14. В ER не показан полный набор ключей и ограничений. **[Ответ: первичные ключи — суррогатные идентификаторы; внешние ключи — по связям; обязательные поля — NOT NULL; уникальность — государственный номер, VIN, серия и номер паспорта и ВУ.]**
15. Не определена формула расчёта стоимости аренды. **[Ответ: стоимость = стартовая стоимость + стоимость за единицу времени × количество единиц времени аренды; округление — вверх до целой единицы.]**
16. Не определено поведение при изменении тарифа во время активной аренды. **[Ответ: к аренде применяется тариф, действовавший на момент её начала; тариф фиксируется в записи аренды.]**
17. Не получен точный контракт имитатора проверки паспорта и ВУ. **[Ответ: имитатор реализует HTTP-интерфейс: запрос содержит серию и номер документа, ответ — результат проверки; формат изолируется адаптером.]**
18. Не получен полный контракт телематического модуля. **[Ответ: телематический модуль имитируется; имитатор реализует HTTP-интерфейс (JSON): приём команд открытия/закрытия, передача состояния, подтверждения и статусы.]**
19. Не выбран способ аутентификации и авторизации. **[Ответ: аутентификация — JWT-токены; роли — арендатор, администратор, техническая служба; доступ — по матрице прав.]**
20. Не утверждены JSON-схемы и формат ошибок REST API. **[Ответ: формат сообщений — JSON; ошибки — единый формат (код, сообщение); HTTP-статусы 200, 201, 400, 401, 403, 404, 409, 500.]**
21. Не выбрана СУБД. **[Ответ: PostgreSQL.]**
22. Не выбраны версии Python/FastAPI, ОС, ASGI-сервер и способ развёртывания. **[Ответ: ASGI-сервер — Uvicorn; развёртывание — Docker (Docker Compose); версии Python, FastAPI и ОС не фиксируются.]**
23. Не определён канал, формат и история уведомлений. **[Ответ: канал — электронная почта; сервис уведомлений формирует письмо, отправляет его через SMTP-сервер и хранит историю отправки; при недоступности SMTP-сервера уведомление сохраняется и отправляется повторно.]**
24. Не определены правила защиты и сроки хранения паспортных данных и ВУ. **[Ответ: сканы не хранятся; хранятся серия, номер и статус; доступ — по ролям; срок хранения — в течение действия учётной записи.]**
25. Не определены объём автопарка, количество пользователей и интенсивность телеметрии. **[Ответ — ДОПУЩЕНИЕ: пилотный масштаб — до 100 ТС и до 5000 пользователей, телеметрия по событию; точные значения уточняются при эксплуатации.]**
26. Не определены временные характеристики и показатели качества. **[Ответ: устанавливаются на этапе испытаний.]**
27. В архитектуре сохранён принцип независимого масштабирования шлюза и модулей, противоречащий монолиту. **[Ответ: решение о монолите принято; архитектурный артефакт синхронизируется — независимое масштабирование модулей заменяется масштабированием монолита.]**
28. Не определено поведение при недоступности внешних интеграций. **[Ответ: задаются таймауты и ограниченное число повторов; при недоступности внешней системы операция завершается ошибкой с уведомлением участника; повторные события обрабатываются идемпотентно.]**
29. Не определено, как сохраняется факт принятия оферты. **[Ответ: в записи пользователя сохраняются признак и дата принятия оферты.]**
30. Не решено, должен ли текст оферты предоставляться через REST API. **[Ответ: текст оферты через REST API не предоставляется; оферта отображается в клиентском приложении вне API.]**
31. Не решено, должен ли арендатор инициировать оплату отдельным запросом к API АС. **[Ответ: отдельный пользовательский маршрут инициирования платежа не вводится; АС получает платёжную ссылку от шлюза и передаёт её арендатору; результат оплаты приходит callback-запросом.]**
32. Не утверждены идентификаторы сообщений, форматы и допустимая точность реквизитов. **[Ответ: определяются JSON-схемами REST API и контрактами внешних систем; точность — по типам данных.]**
33. Не присвоено формальное обозначение техническому проекту по ГОСТ 34.201-2020 и не составлена отдельная ведомость комплекта. **[Ответ: для учебного проекта формальное обозначение и ведомость комплекта не присваиваются; при отдельном требовании оформляются дополнительно.]**
34. Уведомления доставляются по электронной почте, поэтому пользователю нужен адрес электронной почты, а в ER-модели такой атрибут у сущности «Пользователь» не показан. **[Ответ: адрес электронной почты относится к деталям реализации и хранится в составе сведений о пользователе; ER-диаграмма не изменяется.]**

## Принцип работы с открытыми вопросами

- Все проектные предложения, которые влияют на ER, DFD, BPMN или архитектуру, должны быть согласованы владельцем проекта.
- После согласования нужно обновить затронутые диаграммы и документы.
- До закрытия вопроса нельзя выдавать соответствующее проектное предложение за утверждённое требование.
