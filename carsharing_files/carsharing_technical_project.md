# Технический проект автоматизированной системы «Каршеринг»

> **Статус документа:** проектное описание технического решения.

## 1. Назначение документа и область применения

Настоящий документ описывает техническое решение автоматизированной системы «Каршеринг» (далее — АС «Каршеринг»). Он переводит принятые архитектурные решения в описание технических компонентов: данных, операций, правил обработки, интерфейсов взаимодействия и порядка подготовки системы к реализации и развёртыванию.

Документ разработан на основе артефактов проекта:

- описания предметной области;
- ER-диаграммы в нотации Чена;
- функциональной модели, включающей контекстную диаграмму и DFD с декомпозицией;
- процессной модели BPMN;
- архитектуры программного обеспечения АС «Каршеринг».

Серверная часть реализуется на Python с использованием FastAPI; ASGI-сервер — Uvicorn; СУБД — PostgreSQL; развёртывание — контейнеризация Docker (Docker Compose) на сервере под управлением Linux; интерфейс взаимодействия с внешними участниками — REST API поверх HTTP.

### 1.1. Границы технического решения

В технический проект входят:

- шлюз доступа к прикладным сервисам;
- модуль регистрации и управления пользователями;
- модуль аренды ТС;
- модуль состояния ТС;
- административный модуль;
- модуль штрафов и задолженностей;
- модуль формирования перечня ТС, требующих обслуживания;
- адаптер взаимодействия с имитатором проверки документов, адаптер имитатора телематического модуля и адаптер платёжного шлюза;
- сервис уведомлений;
- единая база данных, состав данных которой определяется ER-моделью.

Внешние участники взаимодействуют с системой через API. Мобильное приложение арендатора и административная панель в объём проекта не входят.

## 3. Общая концепция технического решения

### 3.1. Принятая архитектурная основа

АС «Каршеринг» проектируется как **монолитное серверное приложение на Python с использованием FastAPI**. Приложение предоставляет внешним участникам единый REST API поверх HTTP. Внутри приложения выделяются логические модули, соответствующие функциям и компонентам архитектуры: регистрация пользователей, аренда ТС, состояние ТС, администрирование, штрафы и задолженности, формирование перечня ТС на обслуживание, интеграционные адаптеры и уведомления.

Монолитность означает, что перечисленные модули являются частями одного приложения и одной единицы развёртывания. Внутреннее взаимодействие модулей выполняется средствами приложения через их программные интерфейсы. Внешние участники обращаются к приложению через REST API, а внешние системы — через соответствующие адаптеры.

Техническая декомпозиция выполняется по следующему принципу:

- информационные объекты предметной области преобразуются в логические структуры хранения;
- операции функциональной модели распределяются между внутренними модулями монолитного приложения;
- проверки и правила обработки закрепляются за теми операциями, в которых они необходимы;
- обмен с внешними системами выполняется через выделенные адаптеры;
- маршруты HTTP API принимают запросы внешних участников, передают их соответствующим внутренним модулям и возвращают результат;
- результаты операций и события передаются участникам через API и внутренний модуль уведомлений.

Единая точка входа REST API является логической частью FastAPI-приложения. Внутренние модули масштабируются вместе с приложением как единое целое.

### 4.1. Границы ответственности модулей

Модуль регистрации отвечает за регистрацию пользователя и проверку документов в рамках F1. Модуль аренды отвечает за пользовательские операции поиска, начала, просмотра и завершения аренды (F2–F5). Обновление телеметрических сведений выделено в F6 и выполняется отдельно от пользовательского запроса на аренду.

Административный модуль объединяет F9, F10 и F11. Начисление штрафов и обработка оплаты штрафов (F7 и F12) относятся к отдельному модулю штрафов и задолженностей.

Модуль формирования перечня ТС на обслуживание (F8) предоставляет результат технической службе. Учёт неисправностей и ремонтных заявок в объём проекта не входит.

### 4.2. Монолитное размещение компонентов

Все перечисленные прикладные модули, REST-маршруты FastAPI, адаптер проверки документов, адаптер телематики, адаптер платёжного шлюза и сервис уведомлений входят в одно серверное приложение. Их выделение отражает разделение ответственности внутри приложения.

Внутренние вызовы между модулями выполняются внутри приложения. HTTP используется на границе системы для REST API внешних участников и для взаимодействия с внешними системами через адаптеры.

### 4.3. Описание программного обеспечения

#### 4.3.1. Структура программного обеспечения

Программное обеспечение АС представляет собой одно серверное приложение на Python с использованием FastAPI. В его состав входят:

- HTTP-слой REST API, принимающий запросы внешних участников;
- прикладные модули регистрации, аренды, состояния ТС, администрирования, штрафов и задолженностей, формирования перечня обслуживания;
- адаптеры проверки документов, телематики и платёжного шлюза;
- сервис уведомлений;
- слой доступа к единой базе данных.

Перечисленные части входят в одно приложение и используют внутренние программные вызовы.

#### 4.3.2. Методы и средства разработки

Принятые средства и подходы:

- Python — язык серверной разработки;
- FastAPI — веб-фреймворк;
- Uvicorn — ASGI-сервер, запускающий приложение FastAPI;
- PostgreSQL — реляционная СУБД для хранения данных;
- SQLAlchemy — ORM для доступа к данным;
- psycopg — драйвер подключения к PostgreSQL;
- Alembic — управление миграциями базы данных;
- Pydantic — валидация и моделирование данных;
- pytest и httpx — тестирование приложения и HTTP-интерфейса;
- pyproject.toml и pip — описание зависимостей и сборка;
- GitHub Actions — конвейер CI/CD;
- монолитный архитектурный стиль — все прикладные модули входят в одно приложение;
- REST API поверх HTTP — внешний интерфейс взаимодействия;
- адаптерный подход — изоляция прикладной логики от интерфейсов имитатора документов, телематики и платёжного шлюза;
- Docker (Docker Compose) — контейнерное развёртывание приложения и СУБД;
- фоновые задачи FastAPI — асинхронная обработка телеметрии, результатов оплаты и уведомлений.

#### 4.3.3. Операционная система и среда выполнения

Серверная часть функционирует под управлением операционной системы семейства Linux. Приложение FastAPI запускается ASGI-сервером Uvicorn. Поставка и запуск выполняются в контейнерах Docker; приложение и СУБД разворачиваются средствами Docker Compose.

#### 4.3.4. Средства, расширяющие возможности операционной системы

Для контейнеризации используется Docker, для оркестрации контейнеров приложения и СУБД — Docker Compose.

### 5.4. Правила целостности

На уровне технического проектирования обеспечиваются следующие проверки и ограничения:

1. **Регистрация пользователя.** Запись пользователя создаётся после принятия оферты и получения положительных результатов проверки паспорта и водительского удостоверения. При непринятой оферте или отрицательном результате проверки регистрация не подтверждается.
2. **Доступность ТС.** Перед созданием аренды проверяется состояние выбранного ТС. Если ТС недоступно, операция аренды отклоняется.
3. **Задолженность пользователя.** Перед началом аренды проверяется наличие задолженности. При наличии задолженности в аренде отказывается.
4. **Проверка документов при аренде.** Перед созданием аренды выполняется обращение к имитатору проверки документов.
5. **Расчёт стоимости аренды.** Стоимость = стартовая стоимость + стоимость за единицу времени × количество единиц времени аренды; округление — вверх до целой единицы. К аренде применяется тариф, действовавший на момент её начала.
6. **Завершение аренды.** Процесс использует идентификатор ТС, местоположение, сведения о парковке, команду на закрытие ТС и результат списания. Завершение фактического использования ТС и результат списания фиксируются раздельно.
7. **Оплата.** Повторное получение одного и того же сообщения о списании не создаёт повторную запись и не изменяет состояние штрафа дважды.
8. **Штраф.** Штраф регистрируется по запросу администратора и связан с процессом аренды. Платёжный шлюз участвует в формировании ссылки или обработке платёжной операции.
9. **Тарифы и парковки.** Изменения параметров тарифа и парковки выполняются через административный модуль; остальные модули используют сохранённые значения.

### 5.9. Организация внутримашинной информационной базы

Единая база данных является общим хранилищем логических сущностей ER-модели. Внутри неё выделяются группы информации:

- автопарк: ТС, модель, паспорт ТС;
- состояние автопарка: состояние ТС;
- пользователи и документы: пользователь, паспорт, водительское удостоверение;
- аренда и тарификация: аренда, тариф;
- парковки: парковка;
- финансовые обязательства: штраф, задолженность.

Логические связи между сущностями определяются ER-диаграммой. Функции, использующие соответствующие группы данных, указаны в подразделах 5.1–5.4 и в разделе 6.

В качестве СУБД утверждена PostgreSQL. Схема базы данных включает таблицы сущностей, первичные и внешние ключи, ограничения целостности и индексы; изменения схемы выполняются миграциями Alembic. Уровень изоляции транзакций и механизм резервного копирования настраиваются в PostgreSQL в составе среды развёртывания.

Ведение базы данных включает создание пользователя после проверок, создание аренды, обновление состояния ТС, изменение тарифов и парковок, регистрацию штрафов и актуализацию задолженностей после результата платежа. Для идемпотентной обработки результатов оплаты сохраняется внешний идентификатор платёжной операции, его статус и время.

### 6.1. Регистрация пользователя (F1)

Операция начинается с запроса арендатора. Система предоставляет оферту и получает подтверждение её принятия. После принятия оферты выполняется имитация проверки паспорта и водительского удостоверения через адаптер, связанный с имитатором внешней системы. При положительных результатах имитации создаётся запись пользователя и возвращается статус регистрации. Если оферта не принята либо документы не прошли проверку, регистрация не подтверждается.

Входные данные включают сведения, необходимые для создания пользователя и проверки документов.

### 6.2. Поиск ближайших ТС (F2)

Функция получает запрос арендатора и формирует перечень ближайших ТС. Точка поиска передаётся арендатором в запросе (координаты). Для поиска по местоположению функция получает актуальное местоположение ТС из информационного объекта «Состояние». Близость ТС определяется по расстоянию до точки поиска; перечень упорядочивается по возрастанию расстояния.

### 6.3. Аренда ТС (F3)

Функция выполняет проверку выбранного ТС, задолженности пользователя и документов через имитатор, получает тарифные параметры и стартовую стоимость, создаёт запись аренды и инициирует разблокировку автомобиля через адаптер телематики. Если ТС недоступно, у пользователя есть задолженность или проверка документов не пройдена, в аренде отказывается.

Создание записи аренды и выдача команды на разблокировку выполняются в рамках одного пользовательского сценария; при неуспешной разблокировке аренда не создаётся.

### 6.4. Получение информации об аренде (F4)

Функция предоставляет арендатору сведения об аренде и ТС. Данные включают сведения о тарифе, модели, автомобиле и состоянии. Результат включает информацию об аренде и предпросмотр стоимости. Предпросмотр рассчитывается по тем же правилам, что и итоговая стоимость при завершении аренды.

### 6.5. Завершение аренды (F5)

Функция получает запрос на завершение аренды, определяет ТС, получает его местоположение, подтверждает парковочное место, рассчитывает итоговую стоимость и взаимодействует с платёжным шлюзом. ТС блокируется и аренда завершается в обоих случаях; при неуспешном списании создаётся задолженность и арендатор уведомляется о завершении аренды с задолженностью.

### 6.6. Обновление состояния ТС (F6)

Функция получает сведения от имитатора телематического модуля и обновляет объект «Состояние». Для состояния сохраняются временная отметка, местоположение, пробег, уровень топлива и уровень заряда. Телеметрические события обрабатываются асинхронно через адаптер телематики.

### 6.7. Начисление штрафа (F7)

Функция получает запрос администратора, фиксирует штраф и взаимодействует с платёжным шлюзом для формирования ссылки на оплату. Арендатор уведомляется о начислении штрафа. В ER-модели для штрафа показаны размер и статья; в модели также присутствует задолженность.

### 6.8. Формирование перечня ТС на обслуживание (F8)

Функция получает запрос технической службы, читает сведения о состоянии ТС и возвращает перечень автомобилей, требующих обслуживания. Критерии отбора: статус ТС «требует обслуживания», низкий уровень топлива или заряда, превышение пробега или интервала обслуживания.

### 6.9. Управление тарифами (F9)

Администратор получает текущие параметры тарифа и выполняет их создание или изменение. Операция использует сущность «Тариф», в которой ER-модель показывает единицу времени, стоимость за единицу и признак активности. Изменение тарифа возвращает администратору результат операции.

### 6.10. Управление парковками (F10)

Администратор получает и изменяет сведения о парковках. ER-модель показывает адрес парковки. Данные используются в процессе завершения аренды для подтверждения парковочного места.

### 6.11. Просмотр штрафов и задолженностей (F11)

Функция получает сведения из хранилищ штрафов и задолженностей и возвращает их инициатору запроса. Доступ к сведениям ограничивается ролью участника: арендатору доступны его собственные обязательства, администратору — сведения по всем арендаторам.

### 6.12. Оплата штрафов и задолженностей (F12)

Функция связана с платёжным шлюзом и хранилищами штрафов и задолженностей. Она обрабатывает результат платёжной операции и отражает его в данных системы. Повторные сообщения об оплате обрабатываются идемпотентно.

## 7. Алгоритмы ключевых процессов

В разделе приведены последовательности операций, полученные из BPMN-диаграмм.

### 7.1. Процесс регистрации

1. АС получает запрос арендатора на регистрацию.
2. Арендатор знакомится с офертой.
3. АС получает решение о принятии оферты.
4. Если оферта не принята, процесс завершается отказом.
5. Если оферта принята, АС направляет запрос на имитацию проверки паспорта через адаптер проверки документов.
6. АС направляет запрос на имитацию проверки водительского удостоверения через тот же адаптер.
7. АС получает результаты обеих проверок от имитатора внешней системы.
8. Если хотя бы одна проверка не пройдена, регистрация отклоняется.
9. Если проверки пройдены, АС создаёт запись пользователя в базе данных.
10. АС возвращает результат регистрации.

### 7.2. Процесс аренды автомобиля

1. АС получает запрос на аренду выбранного ТС.
2. АС получает сведения о состоянии ТС и проверяет его доступность.
3. Если ТС недоступно, АС возвращает отказ.
4. АС проверяет наличие задолженности пользователя.
5. Если задолженность имеется, АС возвращает отказ.
6. АС выполняет проверки документов через адаптер, обращающийся к имитатору проверки паспорта и водительского удостоверения.
7. При отрицательном результате проверки АС возвращает отказ.
8. АС получает тариф и стартовую стоимость модели ТС.
9. АС создаёт запись аренды.
10. АС передаёт через адаптер телематики команду на разблокировку ТС.
11. АС возвращает подтверждение аренды.

### 7.3. Процесс завершения поездки

1. АС получает запрос на завершение поездки.
2. По записи аренды определяется идентификатор ТС.
3. АС получает местоположение ТС.
4. АС проверяет парковочное место: расстояние от ТС до парковки не должно превышать заданный радиус.
5. АС рассчитывает итоговую стоимость по данным аренды, тарифа и стартовой стоимости.
6. АС направляет запрос на списание в платёжный шлюз.
7. АС получает результат списания.
8. АС закрывает ТС и завершает аренду.
9. При успешном списании аренда завершается без задолженности; при неуспешном списании создаётся задолженность и арендатор уведомляется о завершении аренды с задолженностью.

### 7.4. Процесс начисления штрафа

1. Администратор направляет запрос на начисление штрафа.
2. АС фиксирует сведения о штрафе в соответствующем хранилище.
3. АС взаимодействует с платёжным шлюзом для получения платёжной ссылки.
4. АС уведомляет арендатора о начислении штрафа.
5. Дальнейшая оплата обрабатывается в рамках F12.

### 7.5. Алгоритмы функций F2, F4, F6, F8–F12

Для функций F2, F4, F6, F8, F9, F10, F11 и F12 последовательности операций определены по DFD, ER-модели и архитектуре. Для каждой функции приведены назначение, используемая информация, результат, математическое описание и последовательность решения.

#### 7.5.1. Поиск ближайших ТС (F2)

- **Назначение:** сформировать для арендатора перечень ближайших транспортных средств.
- **Используемая информация:** запрос поиска, сведения о ТС, местоположение и состояние ТС.
- **Результат:** перечень ТС, упорядоченный по близости.
- **Математическое описание:** близость ТС определяется по расстоянию между точкой поиска арендатора и координатами ТС.
- **Алгоритм:** получить запрос с координатами точки поиска; прочитать сведения о ТС и состоянии; исключить ТС, не удовлетворяющие условиям доступности; определить близость по расстоянию; упорядочить по возрастанию расстояния; вернуть перечень.

#### 7.5.2. Получение информации об аренде (F4)

- **Назначение:** предоставить арендатору сведения об аренде и связанном ТС, включая предпросмотр стоимости.
- **Используемая информация:** запрос арендатора, запись аренды, сведения о ТС, модели, состоянии и тарифе.
- **Результат:** сведения об аренде и предпросмотр стоимости.
- **Математическое описание:** предпросмотр стоимости рассчитывается по тем же правилам, что и итоговая стоимость при завершении аренды.
- **Алгоритм:** принять запрос; определить аренду; получить связанные сведения о ТС, модели и тарифе; при необходимости получить состояние; сформировать информационный ответ; вычислить предпросмотр; вернуть ответ.

#### 7.5.3. Обновление состояния ТС (F6)

- **Назначение:** актуализировать сведения о состоянии ТС на основании телеметрического сообщения.
- **Используемая информация:** идентификатор ТС, временная отметка, местоположение, пробег, уровень топлива и уровень заряда.
- **Результат:** обновлённое состояние ТС и статус обработки сообщения.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять сообщение; проверить возможность идентификации ТС; проверить наличие обязательных данных; сопоставить сообщение с текущим состоянием; применить правило актуализации; сохранить результат; вернуть статус обработки.

#### 7.5.4. Формирование перечня ТС на обслуживание (F8)

- **Назначение:** сформировать перечень ТС, требующих обслуживания, по запросу технической службы.
- **Используемая информация:** сведения о ТС и состоянии.
- **Результат:** перечень ТС.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять запрос; получить сведения о ТС и состоянии; отобрать ТС по критериям (статус «требует обслуживания», низкий уровень топлива или заряда, превышение пробега или интервала обслуживания); сформировать перечень; вернуть результат.

#### 7.5.5. Управление тарифами (F9)

- **Назначение:** предоставить администратору операции просмотра, создания и изменения тарифов.
- **Используемая информация:** единица времени, стоимость за единицу времени, признак активности тарифа.
- **Результат:** список тарифов или результат создания/изменения.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять запрос администратора; проверить права; при чтении получить и вернуть тарифы; при создании проверить и сохранить параметры; при изменении определить тариф и сохранить изменения; вернуть результат.

#### 7.5.6. Управление парковками (F10)

- **Назначение:** предоставить администратору операции просмотра, создания и изменения сведений о парковках.
- **Используемая информация:** адрес парковки.
- **Результат:** список парковок или результат создания/изменения.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять запрос администратора; проверить права; при чтении получить список; при создании проверить и сохранить адрес; при изменении определить запись и сохранить новое значение; вернуть результат.

#### 7.5.7. Просмотр штрафов и задолженностей (F11)

- **Назначение:** предоставить инициатору сведения о доступных ему штрафах и задолженностях.
- **Используемая информация:** запрос, полномочия инициатора, сведения о штрафах и задолженностях.
- **Результат:** перечень доступных сведений.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять запрос; определить инициатора; проверить полномочия по матрице доступа; прочитать доступные сведения; сформировать ответ; вернуть результат.

#### 7.5.8. Обработка результата оплаты (F12)

- **Назначение:** обработать сообщение платёжного шлюза и актуализировать сведения о соответствующем обязательстве.
- **Используемая информация:** результат платежа, внешний идентификатор операции и сведения для сопоставления со штрафом, задолженностью или арендой.
- **Результат:** статус обработки сообщения и актуализированное состояние обязательства.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять сообщение; проверить источник; найти связанное обязательство; определить, обрабатывалось ли сообщение ранее; при новом подтверждённом результате актуализировать данные; при повторе не выполнять повторное финансовое изменение; при невозможности сопоставления не менять обязательство и зафиксировать ошибку; вернуть статус обработки.

## 8. Интерфейсы и взаимодействие с окружением

### 8.1. Шлюз взаимодействия и организация REST API

Внешнее взаимодействие арендатора, администратора и технической службы с АС «Каршеринг» выполняется через единый REST API поверх HTTP. API реализуется внутри монолитного серверного приложения на Python с использованием FastAPI и представляет собой входной слой приложения.

Маршрут HTTP принимает запрос, проверяет его структуру и обязательные данные, передаёт управление соответствующему внутреннему модулю и возвращает результат в HTTP-ответе. Внешние участники и системы не обращаются к базе данных напрямую. Внутренние модули взаимодействуют друг с другом программными вызовами внутри монолита.

#### 8.1.1. Проектные HTTP-маршруты

Ниже приведён перечень конечных точек, задающих интерфейс верхнего уровня. Названия полей описаны смысловым образом; JSON-схемы запросов и ответов согласуются с ER-моделью и правилами обработки.

| Функция | HTTP-метод и путь | Инициатор | Назначение и основные данные |
|---|---|---|---|
| F1. Регистрация пользователя | `POST /api/registrations` | Арендатор | Передача сведений пользователя, паспортных данных, данных водительского удостоверения и решения о принятии оферты. Приложение обращается к имитатору проверки документов и при положительных результатах создаёт пользователя. |
| F2. Поиск ближайших ТС | `GET /api/vehicles/nearby` | Арендатор | Получение перечня ближайших ТС. Точка поиска передаётся параметрами запроса. |
| F3. Начало аренды ТС | `POST /api/rentals` | Арендатор | Передача идентификатора выбранного ТС и необходимых сведений для начала аренды. Идентификатор арендатора определяется сервером из подтверждённого контекста пользователя. |
| F4. Получение информации об аренде | `GET /api/rentals/{rental_id}` | Арендатор | Получение сведений об аренде, ТС, тарифе и предпросмотре стоимости по идентификатору аренды. |
| F5. Завершение аренды | `POST /api/rentals/{rental_id}/finish` | Арендатор | Инициирование завершения аренды. Приложение получает актуальное состояние ТС, проверяет парковочное место, рассчитывает стоимость и взаимодействует с платёжным шлюзом и телематикой. |
| F6. Обновление состояния ТС | `POST /api/integrations/telematics/state` | Имитатор телематического модуля ТС | Приём сообщения о состоянии ТС. Состав включает идентификатор ТС, временную отметку и сведения о состоянии: местоположение, пробег, уровень топлива и уровень заряда. |
| F7. Начисление штрафа | `POST /api/admin/fines` | Администратор | Создание записи о штрафе с передачей сведений, предусмотренных ER-моделью, и связью штрафа с арендатором и арендой. |
| F8. Перечень ТС на обслуживание | `GET /api/maintenance/vehicles` | Техническая служба | Получение перечня ТС, требующих обслуживания, по данным состояния ТС. |
| F9. Просмотр тарифов | `GET /api/admin/tariffs` | Администратор | Получение сохранённых параметров тарифов. |
| F9. Создание тарифа | `POST /api/admin/tariffs` | Администратор | Создание тарифа с параметрами: единица времени, стоимость за единицу и признак активности. |
| F9. Изменение тарифа | `PATCH /api/admin/tariffs/{tariff_id}` | Администратор | Изменение разрешённых параметров существующего тарифа по его идентификатору. |
| F10. Просмотр парковок | `GET /api/admin/parking` | Администратор | Получение списка парковок и их адресов. |
| F10. Создание парковки | `POST /api/admin/parking` | Администратор | Создание записи парковки с адресом. |
| F10. Изменение парковки | `PATCH /api/admin/parking/{parking_id}` | Администратор | Изменение сведений о парковке по её идентификатору. |
| F11. Просмотр штрафов | `GET /api/fines` | Арендатор или администратор | Получение доступных инициатору сведений о штрафах. |
| F11. Просмотр задолженностей | `GET /api/debts` | Арендатор или администратор | Получение доступных инициатору сведений о задолженностях. |
| F12. Обработка результата оплаты | `POST /api/integrations/payments/result` | Платёжный шлюз | Приём результата платёжной операции и передача его модулю штрафов и задолженностей либо модулю аренды. Повторные сообщения обрабатываются идемпотентно. |

Маршруты F1–F12 отражают функции функциональной модели. Два интеграционных маршрута предназначены для входящих сообщений от телематического модуля и платёжного шлюза. Вызовы из АС во внешние системы (команды открытия/закрытия ТС, запросы списания, запросы имитации проверки документов) выполняются соответствующими адаптерами.

Оферта в состав REST API не входит: текст оферты отображается в клиентском приложении до регистрации. Отдельный пользовательский маршрут инициирования платежа не вводится: АС получает платёжную ссылку от платёжного шлюза и передаёт её арендатору.

#### 8.1.2. Правила HTTP-взаимодействия

В проектном интерфейсе применяются следующие соглашения:

- `GET` используется для чтения сведений и не изменяет состояние предметных объектов;
- `POST` используется для создания записи, запуска бизнес-операции или приёма внешнего события;
- `PATCH` используется для частичного изменения параметров существующего объекта;
- идентификаторы объектов передаются в пути для операций над конкретной записью;
- параметры поиска передаются в строке запроса, а данные создания и изменения — в теле HTTP-запроса;
- формат структурированных сообщений — JSON;
- аутентификация выполняется по JWT-токенам; доступ к маршрутам ограничивается по ролям участников;
- ошибки возвращаются в едином формате (код, сообщение) с HTTP-статусами 200, 201, 400, 401, 403, 404, 409, 500.

### 8.2. Внешние интерфейсы

| Внешний участник или система | Направление взаимодействия | Содержание обмена | Компонент-посредник |
|---|---|---|---|
| Арендатор | Запросы в АС и ответы из АС | Регистрация, поиск ТС, аренда, получение информации, завершение аренды, получение уведомлений и работа со штрафами/задолженностями | Шлюз доступа к API |
| Администратор | Запросы в АС и ответы из АС | Управление тарифами и парковками, начисление штрафов, просмотр штрафов и задолженностей | Шлюз доступа к API |
| Техническая служба | Запрос в АС и результат из АС | Запрос перечня ТС, требующих обслуживания | Шлюз доступа к API |
| Имитатор проверки документов (паспорт и ВУ) | Запрос из АС и результат во входной поток АС | Имитация проверки паспортных данных и водительского удостоверения | Адаптер проверки документов |
| Имитатор телематического модуля ТС | Команды из АС и сведения о состоянии в АС | Открытие и закрытие ТС, передача местоположения и иных сведений о состоянии | Адаптер телематики |
| Платёжный шлюз | Запросы из АС и результаты в АС | Списание стоимости аренды, операции по штрафам и задолженностям, получение результата оплаты | Адаптер платёжного шлюза |

### 8.3. Синхронное и асинхронное взаимодействие

По принципам архитектуры:

- пользовательские операции, для которых участник ожидает непосредственный результат, выполняются в режиме синхронного запроса и ответа;
- телеметрические сведения передаются как асинхронные события;
- результаты платёжных операций обрабатываются как сообщения от внешнего платёжного шлюза;
- уведомления формируются прикладными модулями как события и доставляются отдельным сервисом уведомлений.

Асинхронные события (телеметрия, результаты оплаты, уведомления) обрабатываются фоновыми задачами приложения FastAPI.

## 9. Обработка ошибок и нестандартных ситуаций

В процессных моделях определены следующие альтернативные исходы:

| Ситуация | Ожидаемое поведение |
|---|---|
| Оферта не принята | Регистрация завершается отказом |
| Паспорт или ВУ не прошли проверку | Регистрация или аренда не подтверждается |
| ТС недоступно | В аренде отказывается |
| У пользователя есть задолженность | В аренде отказывается |
| Списание за аренду не выполнено | Создаётся задолженность, арендатор уведомляется о завершении аренды с задолженностью |
| Получен повторный результат списания | Повторное сообщение не создаёт запись и не меняет состояние штрафа |

Для внешних интеграций определено следующее поведение:

- при недоступности имитатора проверки документов операция завершается отказом с уведомлением участника;
- при отсутствии подтверждения открытия или закрытия ТС операция завершается ошибкой с уведомлением участника;
- при недоступности платёжного шлюза или неопределённом результате платёжная операция завершается ошибкой с уведомлением участника;
- при отсутствии местоположения ТС подтверждение парковки не выполняется, операция завершается ошибкой;
- при попытке изменить тариф, используемый в активной аренде, изменение отклоняется;
- повторно поступившее телеметрическое событие не изменяет сохранённое состояние;
- события, поступившие не по порядку, не перезаписывают более актуальное состояние.

Внешние вызовы выполняются с таймаутами и ограниченным числом повторов; повторные события обрабатываются идемпотентно.

## 10. Требования к согласованности и транзакционной обработке

Единая база данных является общим источником состояния сущностей системы. При проектировании операций обеспечивается согласованность взаимосвязанных записей и исключается ситуация, когда участник получает подтверждение операции, не соответствующее сохранённому состоянию данных.

На уровне технического проекта фиксируются следующие требования:

1. Операция создания аренды использует актуальные сведения о ТС, пользователе, задолженности и тарифе.
2. Проверка доступности ТС и регистрация аренды выполняются как единый бизнес-сценарий; конфликтующие одновременные запросы обрабатываются средствами СУБД.
3. Завершение аренды связывает сведения о времени аренды, ТС, парковке, расчёте стоимости и результате оплаты.
4. Результат оплаты сопоставляется с той арендой, штрафом или задолженностью, к которым относится платёж.
5. Повторная обработка одного платёжного сообщения выполняется идемпотентно.
6. Обновление состояния ТС сохраняет согласованность с идентификатором автомобиля и временной отметкой полученных данных.

Транзакции охватывают операции с базой данных. Внешние вызовы (команды телематическому модулю, операции платёжного шлюза) выполняются вне транзакции базы данных.

### 11.3. Разделение окружений

В проекте используется последовательность подготовки `Dev → Test → Prod`:

- **Dev** — среда разработки, предназначенная для создания и первичной проверки программных компонентов;
- **Test** — среда проверки интеграций и поведения системы на контрольных сценариях;
- **Prod** — эксплуатационная среда.

Каждое окружение разворачивается средствами Docker Compose на сервере под управлением Linux; приложение и СУБД размещаются в отдельных контейнерах.
