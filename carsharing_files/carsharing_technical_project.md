# Технический проект автоматизированной системы «Каршеринг»

> **Статус документа:** проектное описание технического решения. Программная реализация, физическая схема базы данных и испытания в рамках данного документа не заявляются как выполненные.

## 1. Назначение документа и область применения

Настоящий документ описывает техническое решение автоматизированной системы «Каршеринг» (далее — АС «Каршеринг»). Его задача — перевести принятые на предыдущих этапах архитектурные решения в более подробное описание технических компонентов: данных, операций, правил обработки, интерфейсов взаимодействия и порядка подготовки системы к реализации и развёртыванию.

Документ разработан на основе уже подготовленных артефактов проекта:

- описания предметной области;
- ER-диаграммы в нотации Чена;
- функциональной модели, включающей контекстную диаграмму и DFD с декомпозицией;
- процессной модели BPMN;
- архитектуры программного обеспечения АС «Каршеринг»;

В рамках настоящего технического проекта приняты Python и FastAPI для серверной части, монолитный способ построения приложения и REST API поверх HTTP в качестве интерфейса взаимодействия с внешними участниками. Конкретная СУБД, версии программных средств, ASGI-сервер, способ развёртывания, сетевые адреса, точные JSON-схемы и физические параметры инфраструктуры пока не утверждены и не назначаются произвольно.

### 1.1. Границы технического решения

В технический проект входят:

- шлюз доступа к прикладным сервисам;
- модуль регистрации и управления пользователями;
- модуль аренды ТС;
- модуль состояния ТС;
- административный модуль;
- модуль штрафов и задолженностей;
- модуль формирования перечня ТС, требующих обслуживания;
- адаптер взаимодействия с имитатором проверки документов, а также адаптеры телематического модуля и платёжного шлюза;
- сервис уведомлений;
- единая база данных, состав данных которой определяется ER-моделью.

В соответствии с принятой архитектурой внешние участники взаимодействуют с системой через API. Разработка мобильного приложения арендатора и административной панели в текущий объём проекта не включена.

В техническое решение не добавляются функции, отсутствующие в функциональной модели и архитектуре. В частности, отдельные процессы бронирования, обработки инцидентов, страхования, работы с поставщиками топлива и формирования управленческой отчётности не проектируются как реализуемые функции данного артефакта. Они упоминаются в описании предметной области, но не имеют соответствующего полного набора функций и данных в текущих ER-, DFD- и BPMN-моделях.

## 3. Общая концепция технического решения

### 3.1. Принятая архитектурная основа

АС «Каршеринг» проектируется как **монолитное серверное приложение на Python с использованием FastAPI**. Приложение предоставляет внешним участникам единый REST API поверх HTTP. Внутри приложения выделяются логические модули, соответствующие функциям и компонентам архитектуры: регистрация пользователей, аренда ТС, состояние ТС, администрирование, штрафы и задолженности, формирование перечня ТС на обслуживание, интеграционные адаптеры и уведомления.

Монолитность означает, что перечисленные модули являются частями одного приложения и одной единицы развёртывания, а не самостоятельными микросервисами. Внутреннее взаимодействие модулей выполняется средствами приложения через их программные интерфейсы; для вызова одного внутреннего модуля другим не создаются отдельные HTTP-сервисы. Внешние участники обращаются к приложению через REST API, а внешние системы — через соответствующие адаптеры.

Техническая декомпозиция выполняется по следующему принципу:

- информационные объекты предметной области преобразуются в логические структуры хранения;
- операции функциональной модели распределяются между внутренними модулями монолитного приложения;
- проверки и правила обработки закрепляются за теми операциями, в которых они необходимы;
- обмен с внешними системами выполняется через выделенные адаптеры;
- маршруты HTTP API принимают запросы внешних участников, передают их соответствующим внутренним модулям и возвращают результат;
- результаты операций и события передаются участникам через API и внутренний модуль уведомлений.

Единая точка входа REST API является логической частью FastAPI-приложения, а не отдельным шлюзовым микросервисом. В рамках принятого монолита внутренние модули не масштабируются и не развёртываются независимо друг от друга.

### 4.1. Границы ответственности модулей

Модуль регистрации отвечает за регистрацию пользователя и проверку документов в рамках F1. Модуль аренды отвечает за пользовательские операции поиска, начала, просмотра и завершения аренды (F2–F5). Обновление телеметрических сведений выделено в F6 и не должно смешиваться с пользовательским запросом на аренду.

Административный модуль объединяет F9, F10 и F11, как это предусмотрено архитектурой. Начисление штрафов и обработка оплаты штрафов (F7 и F12) относятся к отдельному модулю штрафов и задолженностей.

Модуль формирования перечня ТС на обслуживание (F8) предоставляет результат технической службе, но не выполняет ремонт и не ведёт учёт неисправностей: в текущей ER-модели отдельная сущность неисправности отсутствует, а в перечне открытых вопросов проекта прямо указано, что поломки в БД не хранятся.

### 4.2. Монолитное размещение компонентов

Все перечисленные прикладные модули, REST-маршруты FastAPI, адаптер проверки документов, адаптер телематики, адаптер платёжного шлюза и сервис уведомлений входят в одно серверное приложение. Их выделение в таблице отражает разделение ответственности в коде и проектной документации, а не наличие отдельных сетевых служб или независимо развёртываемых микросервисов.

Внутренние вызовы между модулями выполняются внутри приложения. HTTP используется на границе системы для REST API внешних участников и в тех интеграциях, где такой контракт будет согласован с внешней системой. Наличие FastAPI не означает, что внутренние вызовы модулей должны проходить через HTTP.

#### 4.3.1. Структура программного обеспечения

Программное обеспечение АС представляет собой одно серверное приложение на Python с использованием FastAPI. В его состав входят:

- HTTP-слой REST API, принимающий запросы внешних участников;
- прикладные модули регистрации, аренды, состояния ТС, администрирования, штрафов и задолженностей, формирования перечня обслуживания;
- адаптеры проверки документов, телематики и платёжного шлюза;
- сервис уведомлений;
- слой доступа к единой базе данных.

Перечисленные части выделяются логически по назначению и ответственности. Они входят в одно приложение, используют внутренние программные вызовы и не развёртываются как самостоятельные микросервисы.

#### 4.3.2. Методы и средства разработки

Принятые средства и подходы:

- Python — язык серверной разработки;
- FastAPI — обязательный веб-фреймворк;
- монолитный архитектурный стиль — все прикладные модули входят в одно приложение;
- REST API поверх HTTP — внешний интерфейс взаимодействия;
- адаптерный подход — изоляция прикладной логики от конкретных интерфейсов имитатора документов, телематики и платёжного шлюза.

Конкретные дополнительные библиотеки, ORM, драйвер СУБД, средство миграций, тестовый фреймворк, система сборки и CI/CD не выбраны. Они не включаются в утверждённый стек до отдельного решения.

#### 4.3.3. Операционная система и среда выполнения

Операционная система и её версия не определены. Также не выбран ASGI-сервер и не утверждён способ запуска приложения. Поэтому название ОС, версия, параметры процесса, системные зависимости и настройки сетевого окружения не приводятся.

#### 4.3.4. Средства, расширяющие возможности операционной системы

Конкретные средства контейнеризации, обратный прокси, балансировщик, брокер сообщений, планировщик, система мониторинга и централизованного журналирования не выбраны. Они могут быть рассмотрены при проектировании среды развёртывания, но не считаются частью утверждённого технологического стека.

### 5.2. Группировка информационных объектов по назначению

Для проектирования доступа к данным объекты могут быть сгруппированы следующим образом:

- **Данные автопарка:** ТС, модель, паспорт ТС.

- **Данные финансовых обязательств:** штраф, задолженность.

Это логическая группировка для распределения ответственности между модулями. Она не означает физического разделения единой базы данных на несколько баз или серверов.

### 5.4. Правила целостности, вытекающие из моделей

На уровне технического проектирования необходимо обеспечить следующие проверки и ограничения. Их конкретное выражение в ограничениях СУБД, прикладных операциях или иных механизмах определяется после выбора технологической платформы.

1. **Регистрация пользователя.** Запись пользователя создаётся после принятия оферты и получения положительных результатов проверки паспорта и водительского удостоверения. При непринятой оферте или отрицательном результате проверки регистрация не подтверждается.
2. **Доступность ТС.** Перед созданием аренды проверяется состояние выбранного ТС. Если ТС недоступно, операция аренды отклоняется.
3. **Задолженность пользователя.** Перед началом аренды проверяется наличие задолженности. При наличии задолженности BPMN предусматривает отказ в аренде.
4. **Проверка документов при аренде.** DFD и BPMN процесса аренды предусматривают обращение к внешней системе проверки документов. В рамках реализации вместо реальной системы используется имитатор. Конкретный смысл повторной проверки при аренде по сравнению с регистрацией требует согласования.
5. **Расчёт стоимости аренды.** В качестве исходных сведений используются время аренды, тариф и стартовая стоимость ТС, связанная в ER-модели с моделью автомобиля. Формула расчёта, правила округления и дополнительные начисления в исходных документах не определены.
6. **Завершение аренды.** Процесс использует идентификатор ТС, местоположение, сведения о парковке, команду на закрытие ТС и результат списания. Порядок фиксации завершения аренды при неуспешной оплате должен быть согласован между DFD и BPMN.
7. **Оплата.** Повторное получение одного и того же сообщения о списании не должно создавать повторную запись и повторно изменять состояние штрафа. Это требование прямо закреплено в принципах функционирования архитектуры.
8. **Штраф.** Штраф регистрируется по запросу администратора и связан с процессом аренды. Платёжный шлюз участвует в формировании ссылки или обработке платёжной операции согласно BPMN.
9. **Тарифы и парковки.** Изменения параметров тарифа и парковки выполняются через административный модуль; остальные модули используют сохранённые значения для своих операций.

### 5.5. Ограничения текущей ER-модели

В ER-модели отсутствует отдельная сущность «Платёж», а также явно не показан полный набор реквизитов платёжной операции: идентификатор операции внешнего платёжного шлюза, состояние оплаты, время получения результата и связь результата с арендой, штрафом или задолженностью. Отдельные атрибуты состояния оплаты также не прослеживаются в текущей диаграмме.

Поэтому настоящий технический проект не добавляет самостоятельно таблицу «Платёж» и не утверждает несуществующие атрибуты. До реализации необходимо принять решение: расширить ER-модель отдельной сущностью платежа либо определить, какие именно сведения об оплате хранятся в существующих сущностях «Штраф» и «Задолженность» и каким образом связываются с арендой.

Также ER-модель не содержит отдельной сущности неисправности или инцидента. Это согласуется с открытым вопросом проекта о том, что поломки в БД не хранятся. Следовательно, технический проект не вводит таблицу неисправностей.

### 5.9. Системы классификации и кодирования

В текущих ER-, DFD- и BPMN-моделях отдельные внешние классификаторы или утверждённые системы кодирования не определены. В модели присутствуют предметные признаки и статусы, например статус ТС, статус паспорта, статус ВУ и признак активности тарифа, но полный перечень допустимых значений и их кодов не задан.

Поэтому в настоящем техническом проекте:

- не назначаются числовые коды статусов;
- не задаются длины и маски идентификаторов;
- не создаются произвольные классификаторы моделей, типов кузова, энергии, топлива или статей штрафов;
- фиксируется необходимость определить справочники, допустимые значения и правила кодирования при завершении логической модели БД и спецификации API.

Ведение базы данных на логическом уровне включает создание пользователя после проверок, создание аренды, обновление состояния ТС, изменение тарифов и парковок, регистрацию штрафов и актуализацию задолженностей после результата платежа. Регламент обслуживания, защиты, резервирования и восстановления определяется после выбора СУБД и среды размещения.

### 6.1. Регистрация пользователя (F1)

Операция начинается с запроса арендатора. Система предоставляет оферту и получает подтверждение её принятия. После принятия оферты выполняется имитация проверки паспорта и водительского удостоверения через адаптер, связанный с имитатором внешней системы. Реальные государственные системы не вызываются. При положительных результатах имитации создаётся запись пользователя и возвращается статус регистрации. Если оферта не принята либо документы не прошли проверку, регистрация не подтверждается.

Входные данные включают сведения, необходимые для создания пользователя и проверки документов. Состав дополнительных реквизитов регистрации, правила хранения копий документов и срок хранения персональных данных в текущих моделях не определены.

### 6.2. Поиск ближайших ТС (F2)

Функция получает запрос арендатора и формирует перечень ближайших ТС. В DFD уровня 1 для функции указан доступ к хранилищу ТС. При этом в ER-модели местоположение показано в сущности «Состояние». Следовательно, состав читаемых данных необходимо согласовать: для поиска по местоположению функция должна получать актуальное местоположение ТС из соответствующего информационного объекта.

Алгоритм определения близости, система координат, правила фильтрации по статусу и способ сортировки в исходных моделях не заданы. В техническом проекте они не подменяются произвольной формулой или радиусом поиска.

### 6.3. Аренда ТС (F3)

Функция выполняет проверку выбранного ТС, задолженности пользователя и документов через имитатор, получает тарифные параметры и стартовую стоимость, создаёт запись аренды и инициирует разблокировку автомобиля через адаптер телематики. Если ТС недоступно, у пользователя есть задолженность или проверка документов не пройдена, BPMN предусматривает отказ в аренде.

Создание записи аренды и выдача команды на разблокировку являются связанными действиями одного пользовательского сценария, однако точная транзакционная граница между записью в БД и внешней командой телематическому модулю не определена. Механизм обработки ситуации, когда запись создана, но автомобиль не разблокирован, должен быть уточнён до реализации.

### 6.4. Получение информации об аренде (F4)

Функция предоставляет арендатору сведения об аренде и ТС. DFD показывает чтение сведений о тарифе и модели, а также данных об автомобиле и состоянии. Результат включает информацию об аренде и предпросмотр стоимости. Правила расчёта предпросмотра должны совпадать с правилами итогового расчёта при завершении аренды; сами правила округления и возможных дополнительных начислений пока не определены.

### 6.5. Завершение аренды (F5)

Функция получает запрос на завершение аренды, определяет ТС, получает его местоположение, подтверждает парковочное место, рассчитывает итоговую стоимость и взаимодействует с платёжным шлюзом. BPMN содержит ветвление по результату списания: при успешном списании выполняется закрытие ТС и завершение аренды; при неуспешном списании создаётся задолженность и арендатор уведомляется о завершении поездки с задолженностью.

В текущей BPMN последовательность завершения аренды при отрицательном результате оплаты показана не полностью: операция закрытия ТС и фиксации завершения аренды визуально связана с ветвью успешного списания. DFD при этом предусматривает работу с задолженностью в процессе завершения аренды. До программной реализации необходимо согласовать, что завершение фактического использования ТС и успешность списания являются разными результатами и как каждый из них фиксируется в данных.

### 6.6. Обновление состояния ТС (F6)

Функция получает сведения от телематического модуля и обновляет объект «Состояние». ER-модель показывает для состояния временную отметку, местоположение, пробег, уровень топлива и уровень заряда. В архитектуре предусмотрен асинхронный обмен телеметрическими событиями через адаптер телематики.

В перечне открытых вопросов проекта уже зафиксировано, что сведения о состоянии ТС и телематическое событие дублируют друг друга; это обозначено как денормализация, применённая для оптимизации запроса. Технический проект сохраняет этот факт как исходное проектное решение, но требует документально уточнить, какие именно сведения дублируются, какая запись считается источником актуального состояния и как согласуются обновления. Правила обработки устаревших, повторных и поступивших не по порядку сообщений также должны быть определены до реализации.

### 6.7. Начисление штрафа (F7)

Функция получает запрос администратора, фиксирует штраф и взаимодействует с платёжным шлюзом для формирования ссылки или иного предусмотренного платёжного действия. Арендатор уведомляется о начислении штрафа. В ER-модели для штрафа показаны размер и статья; в модели также присутствует задолженность.

Точный жизненный цикл штрафа, связь штрафа с конкретной арендой, состояние оплаты и хранение ответа платёжного шлюза требуют уточнения по ER-модели. До этого нельзя утверждать, что вся история оплаты уже представлена существующими сущностями.

### 6.8. Формирование перечня ТС на обслуживание (F8)

Функция получает запрос технической службы, читает сведения о состоянии ТС и возвращает перечень автомобилей, требующих обслуживания. DFD связывает функцию с хранилищем состояний.

Критерии включения ТС в перечень в текущих моделях не заданы. В частности, в БД не предусмотрено хранение поломок, а отдельная сущность неисправности отсутствует. Поэтому функция не должна описываться как полноценная подсистема учёта дефектов или ремонтных заявок без изменения предметной, функциональной и информационной моделей.

### 6.9. Управление тарифами (F9)

Администратор получает текущие параметры тарифа и выполняет их создание или изменение. Техническая операция использует сущность «Тариф», в которой ER-модель показывает единицу времени, стоимость за единицу и признак активности. Изменение тарифа должно возвращать администратору результат операции.

Правила изменения тарифа во время уже начатой аренды не определены. Необходимо согласовать, использует ли расчёт конкретной аренды тариф, действовавший в момент её начала, или актуальные параметры на момент завершения.

### 6.10. Управление парковками (F10)

Администратор получает и изменяет сведения о парковках. ER-модель показывает адрес парковки. Данные используются в процессе завершения аренды для подтверждения парковочного места.

Правила допустимости парковки, географические границы, исключения и способ подтверждения адреса в текущих моделях не детализированы. Зоны покрытия в проекте удалены и не добавляются в техническое решение.

### 6.11. Просмотр штрафов и задолженностей (F11)

Функция получает сведения из хранилищ штрафов и задолженностей и возвращает их инициатору запроса. В DFD уровня 1 функция связана с администратором. При этом контекстная модель содержит запрос арендатора на получение сведений о неоплаченных штрафах и задолженностях. Роль, имеющая право просматривать эти сведения, должна быть согласована между контекстной моделью, DFD и архитектурой.

### 6.12. Оплата штрафов и задолженностей (F12)

Функция связана с платёжным шлюзом и хранилищами штрафов и задолженностей. На техническом уровне она должна обрабатывать результат платёжной операции и отражать его в данных системы. Архитектура требует идемпотентной обработки повторных сообщений об оплате.

DFD уровня 1 показывает платёжный шлюз как источник взаимодействия с F12. При этом пользовательский сценарий перехода от просмотра задолженности к оплате и возврата результата в контекстной модели детализирован не полностью. До реализации требуется определить инициатора операции, состав платёжного запроса, способ корреляции ответа с задолженностью или штрафом и атрибуты, в которых фиксируется результат.

## 7. Алгоритмы ключевых процессов

В разделе приведены технологически независимые последовательности операций, полученные из имеющихся BPMN-диаграмм. Они не являются программным кодом и не определяют конкретный язык или платформу реализации.

### 7.1. Процесс регистрации

1. АС получает запрос арендатора на регистрацию.
2. Арендатор знакомится с офертой.
3. АС получает решение о принятии оферты.
4. Если оферта не принята, процесс завершается отказом.
5. Если оферта принята, АС направляет запрос на имитацию проверки паспорта через адаптер проверки документов.
6. АС направляет запрос на имитацию проверки водительского удостоверения через тот же адаптер.
7. АС получает результаты обеих проверок от имитатора внешней системы.
8. Если хотя бы одна проверка не пройдена, регистрация отклоняется.
9. Если проверки пройдены, АС создаёт запись пользователя в базе данных.
10. АС возвращает результат регистрации.

### 7.2. Процесс аренды автомобиля

1. АС получает запрос на аренду выбранного ТС.
2. АС получает сведения о состоянии ТС и проверяет его доступность.
3. Если ТС недоступно, АС возвращает отказ.
4. АС проверяет наличие задолженности пользователя.
5. Если задолженность имеется, АС возвращает отказ.
6. АС выполняет проверки документов через адаптер, обращающийся к имитатору проверки паспорта и водительского удостоверения. Реальные государственные системы проверки не вызываются.
7. При отрицательном результате проверки АС возвращает отказ.
8. АС получает тариф и стартовую стоимость модели ТС.
9. АС создаёт запись аренды.
10. АС передаёт через адаптер телематики команду на разблокировку ТС.
11. АС возвращает подтверждение аренды при успешном завершении предусмотренных шагов.

В BPMN процесса аренды два узла имеют подпись «Отправить запрос на проверку паспорта», однако один из них связан с системой проверки ВУ. По DFD и отдельной BPMN-диаграмме регистрации система проверяет и паспорт, и водительское удостоверение. Поэтому подпись узла, связанного с системой проверки ВУ, должна быть исправлена в BPMN. В настоящем техническом проекте не создаётся третья проверка документа: отмеченное расхождение рассматривается как ошибка подписи исходной диаграммы.

### 7.3. Процесс завершения поездки

1. АС получает запрос на завершение поездки.
2. По записи аренды определяется идентификатор ТС.
3. АС получает местоположение ТС.
4. АС проверяет парковочное место по данным о местоположении и парковках.
5. АС рассчитывает итоговую стоимость по данным аренды, тарифа и стартовой стоимости.
6. АС направляет запрос на списание в платёжный шлюз.
7. АС получает результат списания.
8. При успешном списании выполняются предусмотренные BPMN действия по закрытию ТС и завершению аренды.
9. При неуспешном списании BPMN предусматривает создание задолженности и уведомление арендатора о завершении поездки с задолженностью.

Ветвь неуспешной оплаты нуждается в уточнении: необходимо явно определить, выполняются ли блокировка ТС и фиксация времени завершения аренды независимо от результата списания. Это не следует оставлять на усмотрение реализации.

### 7.4. Процесс начисления штрафа

1. Администратор направляет запрос на начисление штрафа.
2. АС фиксирует сведения о штрафе в соответствующем хранилище.
3. АС взаимодействует с платёжным шлюзом для получения платёжной ссылки или выполнения предусмотренного платёжного действия.
4. АС уведомляет арендатора о начислении штрафа.
5. Дальнейшая оплата обрабатывается в рамках F12.

BPMN начисления штрафа не раскрывает полный жизненный цикл оплаты и не задаёт все состояния штрафа. Подробный алгоритм F12 должен быть согласован отдельно.

### 7.5. Алгоритмы функций, не имеющих отдельных BPMN-диаграмм

Для функций F2, F4, F6, F8, F9, F10, F11 и F12 отдельные BPMN-диаграммы в текущем проекте не представлены. Их последовательности ниже сформированы по DFD, ER и архитектуре. Для каждой функции указаны назначение, используемая информация, результат, математическое описание (если оно существует) и последовательность решения. Это проектные алгоритмы, а не описание уже реализованного кода.

#### 7.5.1. Поиск ближайших ТС (F2)

- **Назначение:** сформировать для арендатора перечень ближайших транспортных средств.
- **Используемая информация:** запрос поиска, сведения о ТС, местоположение и состояние ТС.
- **Результат:** перечень ТС, упорядоченный по утверждённому критерию близости.
- **Математическое описание:** в исходных моделях отсутствует. Не определены источник координат арендатора, система координат, метрика расстояния, область поиска и правило сортировки. Формула не вводится до согласования.
- **Алгоритм:** получить запрос; определить точку поиска согласованным способом; прочитать сведения о ТС и состоянии; исключить ТС, не удовлетворяющие утверждённым условиям доступности; определить близость по утверждённому алгоритму; сформировать и вернуть перечень.

#### 7.5.2. Получение информации об аренде (F4)

- **Назначение:** предоставить арендатору сведения об аренде и связанном ТС, включая предпросмотр стоимости.
- **Используемая информация:** запрос арендатора, запись аренды, сведения о ТС, модели, состоянии и тарифе.
- **Результат:** сведения об аренде и предпросмотр стоимости.
- **Математическое описание:** формула предпросмотра стоимости в исходных материалах не приведена. Она должна быть согласована с формулой итогового расчёта F5.
- **Алгоритм:** принять запрос; определить аренду; получить связанные сведения о ТС, модели и тарифе; при необходимости получить состояние; сформировать информационный ответ; вычислить предпросмотр по утверждённой формуле; вернуть ответ.

#### 7.5.3. Обновление состояния ТС (F6)

- **Назначение:** актуализировать сведения о состоянии ТС на основании телеметрического сообщения.
- **Используемая информация:** идентификатор ТС, временная отметка, местоположение, пробег, уровень топлива и уровень заряда — в пределах состава ER-модели и контракта телематики.
- **Результат:** обновлённое состояние ТС и статус обработки сообщения.
- **Математическое описание:** не требуется. Правила сравнения временных отметок, устранения дублей и обработки событий, поступивших не по порядку, не определены.
- **Алгоритм:** принять сообщение; проверить возможность идентификации ТС; проверить наличие обязательных данных; сопоставить сообщение с текущим состоянием; применить утверждённое правило актуализации; сохранить результат; вернуть статус обработки.

#### 7.5.4. Формирование перечня ТС на обслуживание (F8)

- **Назначение:** сформировать перечень ТС, требующих обслуживания, по запросу технической службы.
- **Используемая информация:** сведения о ТС и состоянии.
- **Результат:** перечень ТС.
- **Математическое описание:** не определено. В исходных моделях отсутствуют критерии отбора и отдельная сущность неисправности; поломки в БД не хранятся.
- **Алгоритм:** принять запрос; получить сведения о ТС и состоянии; применить утверждённые критерии; сформировать перечень; вернуть результат. До утверждения критериев алгоритм не может считаться полностью специфицированным.

#### 7.5.5. Управление тарифами (F9)

- **Назначение:** предоставить администратору операции просмотра, создания и изменения тарифов.
- **Используемая информация:** единица времени, стоимость за единицу времени, признак активности тарифа.
- **Результат:** список тарифов или результат создания/изменения.
- **Математическое описание:** не требуется. Допустимые значения параметров и правила применения тарифа к уже начатой аренде не определены.
- **Алгоритм:** принять запрос администратора; проверить права; при чтении получить и вернуть тарифы; при создании проверить и сохранить параметры; при изменении определить тариф и сохранить разрешённые изменения; вернуть результат.

#### 7.5.6. Управление парковками (F10)

- **Назначение:** предоставить администратору операции просмотра, создания и изменения сведений о парковках.
- **Используемая информация:** адрес парковки.
- **Результат:** список парковок или результат создания/изменения.
- **Математическое описание:** не требуется. Географическое сопоставление адреса парковки с местоположением ТС не определено.
- **Алгоритм:** принять запрос администратора; проверить права; при чтении получить список; при создании проверить и сохранить адрес; при изменении определить запись и сохранить новое значение; вернуть результат.

#### 7.5.7. Просмотр штрафов и задолженностей (F11)

- **Назначение:** предоставить инициатору сведения о доступных ему штрафах и задолженностях.
- **Используемая информация:** запрос, полномочия инициатора, сведения о штрафах и задолженностях.
- **Результат:** перечень доступных сведений.
- **Математическое описание:** не требуется.
- **Алгоритм:** принять запрос; определить инициатора; проверить полномочия по утверждённой матрице доступа; прочитать доступные сведения; сформировать ответ; вернуть результат. Матрица доступа не может быть окончательно утверждена до устранения расхождения между контекстной моделью и DFD.

#### 7.5.8. Обработка результата оплаты (F12)

- **Назначение:** обработать сообщение платёжного шлюза и актуализировать сведения о соответствующем обязательстве.
- **Используемая информация:** результат платежа, внешний идентификатор операции и сведения для сопоставления со штрафом, задолженностью или арендой. Точные реквизиты определяются контрактом шлюза.
- **Результат:** статус обработки сообщения и актуализированное состояние обязательства.
- **Математическое описание:** не требуется. Для повторных сообщений должно соблюдаться требование идемпотентности, зафиксированное в архитектуре.
- **Алгоритм:** принять сообщение; проверить источник по согласованному механизму; найти связанное обязательство; определить, обрабатывалось ли сообщение ранее; при новом подтверждённом результате актуализировать данные; при повторе не выполнять повторное финансовое изменение; при невозможности сопоставления не менять обязательство и зафиксировать ошибку; вернуть статус обработки по контракту.

### 7.6. Математические зависимости, требующие отдельного утверждения

В текущем проекте не приведены формулы для:

- определения расстояния до ближайшего ТС (F2);
- предпросмотра стоимости аренды (F4);
- итоговой стоимости аренды (F5);
- определения необходимости обслуживания ТС (F8).

Для F5 известны исходные данные, которые должны учитываться: время аренды, тариф и стартовая стоимость модели ТС. Однако не определены правила округления, тарификация неполного интервала, минимальная стоимость, дополнительные начисления и порядок применения тарифа при его изменении во время аренды. До согласования этих правил математические формулы не добавляются.


## 8. Интерфейсы и взаимодействие с окружением

### 8.1. Шлюз взаимодействия и организация REST API

Внешнее взаимодействие арендатора, администратора и технической службы с АС «Каршеринг» выполняется через единый REST API поверх HTTP. API реализуется внутри монолитного серверного приложения на Python с использованием FastAPI. Шлюз REST API не является отдельным микросервисом: он представляет собой входной слой одного приложения.

Маршрут HTTP принимает запрос, проверяет его структуру и обязательные данные, передаёт управление соответствующему внутреннему модулю и возвращает результат в HTTP-ответе. Внешние участники и системы не обращаются к базе данных напрямую. Внутренние модули взаимодействуют друг с другом программными вызовами внутри монолита, а не через отдельные HTTP-сервисы.

#### 8.1.1. Проектные HTTP-маршруты

Ниже приведён проектный перечень конечных точек. Пути и методы задают согласуемый интерфейс верхнего уровня и предназначены для последующей реализации в FastAPI. Они не означают, что API уже реализован. Названия полей в таблице описаны смысловым образом; окончательные JSON-схемы запросов и ответов должны быть согласованы с ER-моделью и правилами обработки.

| Функция | HTTP-метод и путь | Инициатор | Назначение и основные данные |
|---|---|---|---|
| F1. Регистрация пользователя | `POST /api/registrations` | Арендатор | Передача сведений пользователя, паспортных данных, данных водительского удостоверения и решения о принятии оферты. Приложение обращается к имитатору проверки документов и при положительных результатах создаёт пользователя. |
| F2. Поиск ближайших ТС | `GET /api/vehicles/nearby` | Арендатор | Получение перечня ближайших ТС. Параметры точки поиска и способ их передачи пока не определены; координаты не добавляются в контракт до согласования. |
| F3. Начало аренды ТС | `POST /api/rentals` | Арендатор | Передача идентификатора выбранного ТС и необходимых сведений для начала аренды. Идентификатор арендатора должен определяться сервером из подтверждённого контекста пользователя после выбора механизма аутентификации; принимать произвольный идентификатор арендатора из тела запроса без проверки не следует. Сам механизм аутентификации пока не выбран. |
| F4. Получение информации об аренде | `GET /api/rentals/{rental_id}` | Арендатор | Получение сведений об аренде, ТС, тарифе и предпросмотре стоимости по идентификатору аренды. |
| F5. Завершение аренды | `POST /api/rentals/{rental_id}/finish` | Арендатор | Инициирование завершения аренды. Приложение получает актуальное состояние ТС, проверяет парковочное место, рассчитывает стоимость и взаимодействует с платёжным шлюзом и телематикой. |
| F6. Обновление состояния ТС | `POST /api/integrations/telematics/state` | Телематический модуль ТС | Приём сообщения о состоянии ТС. Смысловой состав включает идентификатор ТС, временную отметку и сведения о состоянии, предусмотренные ER-моделью: местоположение, пробег, уровень топлива и уровень заряда. Точный контракт телематического модуля требует согласования. |
| F7. Начисление штрафа | `POST /api/admin/fines` | Администратор | Создание записи о штрафе с передачей сведений, предусмотренных ER-моделью и согласованными правилами связи штрафа с арендатором и арендой. |
| F8. Перечень ТС на обслуживание | `GET /api/maintenance/vehicles` | Техническая служба | Получение перечня ТС, требующих обслуживания, по данным состояния ТС. Критерии отбора пока не определены. |
| F9. Просмотр тарифов | `GET /api/admin/tariffs` | Администратор | Получение сохранённых параметров тарифов. |
| F9. Создание тарифа | `POST /api/admin/tariffs` | Администратор | Создание тарифа с параметрами, предусмотренными ER-моделью: единица времени, стоимость за единицу и признак активности. |
| F9. Изменение тарифа | `PATCH /api/admin/tariffs/{tariff_id}` | Администратор | Изменение разрешённых параметров существующего тарифа по его идентификатору. Правила изменения тарифа при активной аренде требуют согласования. |
| F10. Просмотр парковок | `GET /api/admin/parking` | Администратор | Получение списка парковок и их адресов. |
| F10. Создание парковки | `POST /api/admin/parking` | Администратор | Создание записи парковки с адресом. |
| F10. Изменение парковки | `PATCH /api/admin/parking/{parking_id}` | Администратор | Изменение сведений о парковке по её идентификатору. |
| F11. Просмотр штрафов | `GET /api/fines` | Арендатор или администратор — после согласования прав | Получение доступных инициатору сведений о штрафах. Текущие модели расходятся в определении роли, поэтому правила доступа должны быть согласованы. |
| F11. Просмотр задолженностей | `GET /api/debts` | Арендатор или администратор — после согласования прав | Получение доступных инициатору сведений о задолженностях. |
| F12. Обработка результата оплаты | `POST /api/integrations/payments/result` | Платёжный шлюз | Приём результата платёжной операции и передача его модулю штрафов и задолженностей либо модулю аренды. Повторные сообщения обрабатываются идемпотентно. Точный контракт callback должен быть согласован с платёжным шлюзом. |

Маршруты F1–F12 отражают функции функциональной модели. Два дополнительных интеграционных маршрута предназначены для входящих сообщений от телематического модуля и платёжного шлюза. Вызовы из АС во внешние системы (команды открытия/закрытия ТС, запросы списания, запросы имитации проверки документов) выполняются соответствующими адаптерами и не являются пользовательскими маршрутами REST API.

**Дополнительные маршруты, требующие решения:**

- `GET /api/offer` может быть добавлен, если текст оферты должен предоставляться через REST API. BPMN требует ознакомления арендатора с офертой, но не устанавливает способ её доставки. Если оферта предоставляется как отдельный документ или иным способом, отдельный HTTP-маршрут не нужен.
- `POST /api/payments` не включён в основной перечень обязательных маршрутов. В DFD источником F12 указан платёжный шлюз, а BPMN начисления штрафа предусматривает получение платёжной ссылки. Если пользователь должен отдельно инициировать платёж через API АС, такой маршрут и его связь с платёжным шлюзом необходимо добавить после уточнения процесса. До этого F12 описывается как обработка результата, поступившего от шлюза.
- `POST /api/integrations/telematics/state` и `POST /api/integrations/payments/result` являются проектными входящими маршрутами для интеграций. Их применение зависит от того, поддерживают ли внешние системы передачу сообщений по HTTP. Если внешний контракт использует иной протокол, адаптер должен реализовать соответствующее сопряжение, а указанные HTTP-маршруты могут не применяться.

#### 8.1.2. Правила HTTP-взаимодействия

В проектном интерфейсе применяются следующие соглашения:

- `GET` используется для чтения сведений и не должен изменять состояние предметных объектов;
- `POST` используется для создания записи, запуска бизнес-операции или приёма внешнего события;
- `PATCH` используется для частичного изменения параметров существующего объекта;
- идентификаторы объектов передаются в пути для операций над конкретной записью;
- параметры поиска передаются в строке запроса, а данные создания и изменения — в теле HTTP-запроса;
- в качестве формата структурированных сообщений предлагается JSON; это проектное предложение, которое необходимо подтвердить до реализации;
- конкретные схемы JSON, обязательность полей, HTTP-коды успешных и ошибочных ответов, формат ошибки и правила аутентификации/авторизации уточняются до реализации.

Доступ к маршрутам должен ограничиваться по ролям участников. Однако контекстная модель и DFD не полностью согласованы в отношении просмотра штрафов и задолженностей (F11), а способ аутентификации пользователя не выбран. Поэтому окончательная матрица доступа не фиксируется до согласования этих вопросов.

| Внешний участник или система | Направление взаимодействия | Содержание обмена | Компонент-посредник |

| Администратор | Запросы в АС и ответы из АС | Управление тарифами и парковками, начисление штрафов, просмотр штрафов и задолженностей | Шлюз доступа к API |

### 8.3. Синхронное и асинхронное взаимодействие

По принципам архитектуры:

- пользовательские операции, для которых участник ожидает непосредственный результат, выполняются в режиме синхронного запроса и ответа;
- телеметрические сведения передаются как асинхронные события;
- результаты платёжных операций обрабатываются как сообщения от внешнего платёжного шлюза;
- уведомления формируются прикладными модулями как события и доставляются отдельным сервисом уведомлений.

Монолитный характер приложения не отменяет необходимости обрабатывать отдельные события асинхронно. При этом наличие брокера сообщений или отдельного сервиса очередей не утверждается: способ фоновой обработки телеметрии, результатов оплаты и уведомлений внутри монолита должен быть выбран отдельно. Конкретные протоколы внешних интеграций, гарантии повторной передачи и сроки хранения сообщений также требуют согласования.

## 9. Обработка ошибок и нестандартных ситуаций

В текущих процессных моделях явно показаны следующие альтернативные исходы:

| Ситуация | Ожидаемое поведение по исходным моделям |
|---|---|
| Оферта не принята | Регистрация завершается отказом |
| Паспорт или ВУ не прошли проверку | Регистрация или аренда не подтверждается |
| ТС недоступно | В аренде отказывается |
| У пользователя есть задолженность | В аренде отказывается |
| Списание за аренду не выполнено | Создаётся задолженность, арендатор уведомляется о завершении поездки с задолженностью; детали закрытия аренды требуют согласования |
| Получен повторный результат списания | Повторное сообщение не должно повторно создавать запись или повторно менять состояние штрафа |

Следующие ситуации не описаны достаточно подробно и не должны получать выдуманное поведение в техническом проекте:

- имитатор проверки документов недоступен или не отвечает;
- телематический модуль не подтверждает открытие или закрытие ТС;
- платёжный шлюз недоступен либо возвращает неопределённый результат;
- местоположение ТС отсутствует или не позволяет подтвердить парковку;
- администратор пытается изменить тариф, который уже используется в активной аренде;
- повторно поступает одно и то же телематическое событие;
- сведения о состоянии ТС поступают в неправильном временном порядке.

Для каждой такой ситуации требуется определить допустимый результат, состояние данных и способ информирования участника до разработки программного кода.

## 10. Требования к согласованности и транзакционной обработке

Единая база данных является общим источником состояния сущностей системы. При проектировании операций необходимо обеспечить согласованность взаимосвязанных записей и исключить ситуацию, когда участник получает подтверждение операции, не соответствующее сохранённому состоянию данных.

На уровне технического проекта фиксируются следующие требования:

1. Операция создания аренды должна использовать актуальные сведения о ТС, пользователе, задолженности и тарифе.
2. Проверка доступности ТС и регистрация аренды должны быть согласованы как единый бизнес-сценарий. Конкретный механизм защиты от конфликтующих одновременных запросов должен быть определён при физическом проектировании.
3. Завершение аренды должно связывать сведения о времени аренды, ТС, парковке, расчёте стоимости и результате оплаты.
4. Результат оплаты должен быть сопоставлен с той арендой, штрафом или задолженностью, к которым относится платёж.
5. Повторная обработка одного платёжного сообщения должна быть идемпотентной в соответствии с принципами архитектуры.
6. Обновление состояния ТС должно сохранять согласованность с идентификатором автомобиля и временной отметкой полученных данных.

Границы транзакций, блокировки, уровень изоляции, механизмы повторов и компенсационные действия при неуспешных внешних вызовах не фиксируются без выбора СУБД и согласования сценариев. В частности, транзакция базы данных не должна автоматически считаться охватывающей внешнюю команду телематическому модулю или операцию платёжного шлюза.

## 11. Подготовка к реализации и порядок развёртывания

Настоящий раздел описывает логический порядок подготовки системы. Серверная платформа Python/FastAPI, монолитный способ построения приложения и REST API уже выбраны. Раздел не содержит команд установки, параметров серверов или длительности развёртывания, поскольку СУБД, ASGI-сервер, инфраструктура и конкретный способ поставки приложения ещё не утверждены.

### 11.1. Подготовительные решения

До начала реализации необходимо:

- согласовать расхождения между ER, DFD и BPMN;
- утвердить состав данных об оплатах и способ их связи с арендой, штрафом и задолженностью;
- определить критерии формирования перечня ТС на обслуживание;
- определить правила расчёта стоимости аренды и порядок фиксации завершения при неуспешной оплате;
- выбрать СУБД, версии Python и FastAPI, ASGI-сервер и средства развёртывания;
- реализовать REST API по маршрутам раздела 8 и согласовать окончательные JSON-схемы запросов и ответов;
- получить контракт имитатора проверки паспорта и водительского удостоверения;
- определить контракты обмена с телематическим модулем и платёжным шлюзом;

### 11.3. Разделение окружений

В проекте используется последовательность подготовки `Dev → Test → Prod`:

- **Dev** — среда разработки, предназначенная для создания и первичной проверки программных компонентов;
- **Test** — среда проверки интеграций и поведения системы на контрольных сценариях;
- **Prod** — эксплуатационная среда.

Конкретные серверы, контейнеры, сетевые сегменты, параметры конфигурации и порядок поставки версий должны быть определены после выбора технологической платформы. В настоящем документе не утверждается, что какие-либо из этих окружений уже развёрнуты.
