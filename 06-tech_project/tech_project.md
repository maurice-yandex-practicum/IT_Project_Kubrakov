# Технический проект АС «Каршеринг»

## 6.1. Назначение решения

Технический проект раскрывает реализацию назначения, функций F1–F12 и операций четырёх процессных представлений. Объект — серверное ПО с API, PostgreSQL, адаптерами и уведомлениями. Документ описывает проектируемую реализацию; исходного программного кода и результатов испытаний здесь не предъявляется. Требования requirements.md включаются в этот раздел при сборке записки.

## 6.2. Состав программных средств

Приложение — модульный монолит Python/FastAPI под Uvicorn. PostgreSQL хранит данные; SQLAlchemy/psycopg обеспечивают доступ, Alembic — миграции, Pydantic — проверку схем. Docker Compose запускает приложение и PostgreSQL на Linux. Контрольная среда: 4 vCPU, 8 ГиБ RAM, локальная сеть, один процесс Uvicorn. Блокирующие обращения к PostgreSQL выполняются в выделенных рабочих потоках, а не в цикле ASGI. pytest/httpx рассматриваются как средства исполнения подготовленных проверок после реализации.

gateway принимает и формирует сообщения; auth выполняет вход, JWT и роли; registration создаёт пользователя; rental реализует F2–F5; state — F6; finance — F7/F11/F12; maintenance — F8; admin — F9/F10. docs_adapter, telemetry_adapter и payment_adapter выполняют соответствующие внешние обмены. notifier исполняет задания отправки писем. Каждый компонент имеет входной обработчик, прикладную обработку и доступ к своим данным/адаптерам; технические части выбранных цепочек раскрыты далее.

Нормативная опора: ГОСТ Р 57100-2025 для архитектурных связей и обоснования решений; ГОСТ 19.301-79 и ГОСТ Р 56920-2024 для проверки требований, средств и методов. Их положения используются в пределах содержания учебных артефактов.

## 6.3. Данные и ограничения

- Пользователь: идентификатор, телефон (уникальный), почта, ФИО, роль, хеш пароля с солью, принятие оферты и дата; документы имеют серию, номер и статус проверки. Регистрация создаёт только роль арендатора; служебные роли подготавливаются отдельно.
- ТС: идентификатор, номер и VIN (уникальные), модель, год/цвет, операционный статус, lease_version, дата/пробег последнего ТО. Модель содержит технические признаки, стартовую стоимость и интервалы ТО.
- Состояние: vehicle_id (уникальный), measured_at, координаты, пробег, применимые уровни топлива/заряда и technical_status. Операционный статус этой записью не изменяется.
- Аренда: пользователь, ТС, тариф, starting/active/start_failed/finished, created_at, started_at, ended_at, снимок стартовой стоимости/единицы/цены, итог, финансовый результат и результат закрытия. started_at отсутствует до подтверждения; ended_at — до успешного завершения.
- Справочники: тариф с минутной единицей, точной ценой и активностью; парковка с координатами и положительным радиусом.
- Штраф и задолженность: аренда, владелец через аренду, сумма, unpaid/paid, текущая платёжная попытка. На исходную аренду допускается не более одной созданной задолженности.
- Технические записи: история платёжных попыток с внутренним UUID, типом/идентификатором обязательства, внешним id, суммой/RUB, статусом и ссылкой; журнал нормализованных результатов; квитанции message_id/хеш тела/исход; исходящие задания и история уведомлений.

Первичные идентификаторы суррогатные; обязательные значения NOT NULL, связи защищены внешними ключами. Для starting/active действует ограничение уникальности ТС; проверки и создание выполняются под блокировкой строки ТС. Ключ пользовательской идемпотентности уникален по пользователю и операции, хранит отпечаток параметров. Внешний id платежа уникален в техническом реестре, результат — по паре внешний id/нормализованный статус. У обязательства не более одной незавершённой попытки. Денежные значения хранятся точным десятичным типом с двумя знаками; двоичная арифметика float для суммы не используется.

Для парка допускается не более одного активного тарифа; это защищается уникальным частичным индексом по признаку активности для active=true. Активация тарифа и снятие активности с прежнего выполняются одной транзакцией. F3 читает и блокирует действующий тариф при сохранении снимка; при отсутствии тарифа возвращает 409 TARIFF_UNAVAILABLE без создания попытки. Снимок содержит цену этого тарифа и стартовую стоимость модели ТС.

Проверка ключа, отпечатка параметров и привязка к новой попытке атомарны с её созданием. При конкуренции одинаковых запросов после фиксации первого возвращается существующая попытка; конфликт уникальности не превращается в ошибку доступности ТС. Другие параметры под тем же ключом дают 409.

Техническая загрузка справочных данных принимает регламент и факты ТО от технической службы с проверкой дат, пробега и ссылок модели; это подготовка информационного обеспечения. F8 эти сведения не редактирует. Нормы проекта: 15000 км/180 суток; топливо ≤10%, заряд ≤20%. При отсутствии базы ТО выдаётся DATA_INCOMPLETE.

## 6.4. Входы и формат

Доступ пользователя — HTTPS/JSON и Bearer JWT. Идентификаторы UUID передаются строками. Даты RFC3339 обязательно содержат часовой пояс и нормализуются к UTC. Цена — строка точного десятичного значения в RUB; координаты — числа с широтой [-90,90], долготой [-180,180]; радиусы/расстояния — метры. Ошибка: `{code, message, request_id}`. Применяются 200/201/202, 400, 401, 403, 404, 409, 422, 429, 500, 503.

| Функция | Метод и маршрут | Существенные данные |
|---|---|---|
| вход | POST /api/auth/login | phone, password → access_token, role |
| F1 | POST /api/registrations | phone, email, full_name, password, passport, driving_license, offer_accepted |
| F2 | GET /api/vehicles/nearby | latitude, longitude, radius_m → vehicles |
| F3 | POST /api/rentals | vehicle_id, заголовок Idempotency-Key → rental_id, status, status_url |
| F4 | GET /api/rentals/{rental_id} | status, started_at, ended_at, price_snapshot, amount, payment_status, close_status, confirmation_url, attention_required |
| F5 | POST /api/rentals/{rental_id}/finish | ключ идемпотентности; сохранённый операционный/финансовый результат |
| F6 | POST /api/integrations/telematics/state | сообщение состояния и квитанция |
| команды | POST /api/integrations/telematics/commands/result | command_id, attempt_id, lease_version, command_seq, result |
| F7 | POST /api/admin/fines | rental_id, amount, article; 201 и штраф/текущая попытка |
| F8 | GET /api/maintenance/vehicles | перечень с reason_codes, measured_at и state_age_seconds |
| F9 | GET/POST /api/admin/tariffs; PATCH /api/admin/tariffs/{id} | price_per_minute, active; unit=minute |
| F10 | GET/POST /api/admin/parking; PATCH /api/admin/parking/{id} | latitude, longitude, radius_m |
| F11 | GET /api/fines; GET /api/debts | владельца/роль определяет сервер; сумма, статус, попытка и ссылка |
| F12 | POST /api/integrations/payments/result | уведомление шлюза; результат проверяется через его API |

Регистрация и вход не требуют уже выданного JWT. Документы — обязательные объекты с серией и номером; offer_accepted должен быть true для создания пользователя. Пароль сохраняется только в виде хеша. Все обращения арендатора к аренде/обязательствам фильтруются его идентификатором. Неверный токен — 401, чужая роль/владелец — 403; неизвестный объект — 404.

В F2 rental соединяет карточку, актуальное состояние и незавершённую аренду, применяет условия доступности и вычисляет сферическое расстояние по координатам с радиусом 6371000 м. Включение по radius_m выполняется по неокруглённому расстоянию, сортировка — расстояние, затем идентификатор. F8 сравнивает текущий пробег минус пробег последнего ТО с интервалом модели; календарную разность дат оценки/последнего ТО в часовом поясе Москвы — с числом суток. Загрузка проверяет непротиворечивость даты/пробега ТО; отсутствующие сведения не заменяются нулями.

### 6.4.1. Представительные сообщения API

F3 получает `{"vehicle_id":"00000000-0000-4000-8000-000000000001"}` и отдельный заголовок Idempotency-Key. Пример ответа 202:

```json
{"rental_id":"00000000-0000-4000-8000-000000000101","status":"starting","started_at":null,"amount":"0.00","status_url":"/api/rentals/00000000-0000-4000-8000-000000000101"}
```

После подтверждённого открытия тот же ресурс F4 содержит active и серверный started_at. Пример результата F5 для контрольных 601 секунды:

```json
{"rental_id":"00000000-0000-4000-8000-000000000101","status":"finished","started_at":"2026-06-30T09:00:02Z","ended_at":"2026-06-30T09:10:03Z","amount":"127.00","payment_status":"pending","close_status":"pending","confirmation_url":null,"attention_required":false}
```

В ответе F4 также присутствуют vehicle_id и price_snapshot: start_fee="50.00", unit="minute", unit_seconds=60, price_per_unit="7.00". confirmation_url выдаётся только для текущей pending-попытки; для paid/attention возвращается null. attention_required и reason_code показывают необходимость сверки. Состояния closed/pending/failed результата команды не заменяют status аренды.

Пример обязательного сообщения F6:

```json
{"schema_version":"1.0","message_id":"00000000-0000-4000-8000-000000000201","vehicle_id":"00000000-0000-4000-8000-000000000001","measured_at":"2026-06-30T09:00:02Z","latitude":55.75,"longitude":37.61,"mileage_km":44999,"fuel_percent":60,"charge_percent":null,"technical_status":"normal"}
```

После фиксации ответ 200 содержит тот же message_id, outcome="applied", applied=true, current_measured_at="2026-06-30T09:00:02Z". Для ignored/duplicate applied=false; current_measured_at указывает сохранённую актуальную отметку. Ошибка содержит code/message/request_id и не выдаёт ложной квитанции обработки.

## 6.5. Техническая цепочка начала аренды

**Обработчик входа** (RA1–RA3) проверяет JWT, схему и ключ идемпотентности. Повтор с тем же телом возвращает прежнюю попытку. Другие параметры под тем же ключом дают 409. **Адаптер документов** (RA4/RA5) параллельно отправляет имитаторам `{request_id, series, number}` и получает `{request_id, valid, reason}`; каждый запрос ограничен 3 с. Отрицательный результат/таймаут исключает создание попытки.

**Прикладная обработка rental** (RA6/RA7) получает состояние и выполняет транзакцию: блокировка ТС, проверка available/normal/возраста ≤30 с и отсутствия starting/active, проверка задолженности, сохранение снимка условий, starting, reserved, нового lease_version и задания открытия. Результат клиенту — 202 starting с адресом F4. Оплачиваемая стоимость до active — 0.

**Адаптер телематики** (RA10) получает сохранённое задание и вне транзакции передаёт имитатору `POST /commands`: обязательные command_id UUID, attempt_id UUID, vehicle_id UUID, lease_version целое >0, command_seq (1 для открытия, 2 для закрытия), action open/close. 202 имитатора означает принятие команды, а не физическое открытие. Физический результат приходит через маршрут commands/result; возможен запрос `GET /commands/{command_id}` при восстановлении.

**Применение результата** (RA13/RA14) проверяет служебный токен, идентификаторы, поколение и срок. Перед первой отправкой сохраняется deadline=first_sent_at+5 с; повтор его не продлевает. Ответ имитатора содержит result из opened/closed/rejected/stale и идентификаторы команды. Под блокировкой rental своевременный opened даёт active, rented и started_at по серверному времени приёма. Отказ/5 с без результата даёт start_failed, blocked и задание согласующего закрытия. Поздний ответ не активирует start_failed. При восстановлении просроченное открытие не отправляется заново, выполняется согласование закрытия. Перед каждой компенсацией проверяется, что задание относится к прежней попытке и не вмешивается в новую.

Имитатор хранит поколение и результаты команд: повтор command_id возвращает прежний результат; закрытие поколения делает последующее старое открытие неисполняемым; команда старого lease_version не меняет автомобиль. Только подтверждённое закрытие, отсутствие другой незавершённой аренды и допустимый технический признак позволяют rental вернуть available. Иначе blocked; после исчерпания повторов — attention. Цепочка RC… раскрывает согласование и восстановление.

## 6.6. Техническая цепочка завершения

Вход FN1–FN3 проверяет JWT, владельца и состояние. Повтор finished возвращает сохранённое окончание и не создаёт задания. Для active проверяются состояние не старше 30 секунд и расстояние до парковки ≤radius_m. Отказ даёт 409, без ended_at и изменения активной аренды.

В транзакции FN6 rental блокирует ТС, затем аренду; такой порядок блокировок применяется ко всем изменяющим их операциям. После получения блокировок повторно проверяются статус, возраст состояния и парковочный радиус. Если другой запрос уже завершил аренду, возвращается сохранённый итог без новых заданий. Для active фиксируется ended_at по серверному времени успешной проверки парковки, вычисляется `start_fee + price_per_minute × ceil((ended_at − started_at)/60 секунд)`, записываются итог, finished, blocked, pending, внутренний operation_id и задания оплаты/закрытия. FN7 возвращает 200 с законченной арендой, суммой и текущими payment_status/close_status.

Снимок согласуется при оформлении попытки; новая цена справочника его не меняет. При условиях 50,00 и 7,00 за минуту: 600 с → 120,00; 601 с → 127,00. Для active F4 использует момент своего запроса; для finished — сохранённый итог, для starting/start_failed — 0 и пустой started_at.

Внешние действия CL…/CP… выполняются после фиксации независимо от ответа FN7. Сбой оплаты или закрытия не отменяет ended_at. Подтверждение закрытия сохраняется отдельно, до него ТС blocked. Оплата pending не равна отказу; подтверждённый отказ исходной попытки аренды создаёт задолженность в F12.

## 6.7. Платёжный протокол и применение результата

Выбрана ЮKassa. Запрос создания использует HTTPS, аутентификацию магазина, Idempotence-Key с внутренним operation_id и JSON с amount/value/currency, capture=true, confirmation/redirect и metadata.operation_id. Шлюз возвращает внешний id и confirmation_url. Пользователь подтверждает оплату на стороне шлюза; данные карты АС не принимает. Эти особенности описаны в официальной документации процесса платежа [ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).

Внешний id не создаётся до запроса: до отправки сохраняются внутренний operation_id, сумма и задание. Внешний id связывается из проверенного ответа/объекта. При уведомлении адаптер получает текущий объект по id через аутентифицированное API. finance проверяет магазин, metadata, сумму, RUB и тип обязательства. Сигнал не считается доказательством списания сам по себе; используется проверка статуса, предусмотренная [документацией уведомлений](https://yookassa.ru/developers/using-api/webhooks).

| Локальное состояние попытки | Проверенный результат | Действие |
|---|---|---|
| pending | pending / ожидание / неизвестное получение | сохранить pending; повторить получение сведений |
| pending | succeeded | paid; погасить целевое обязательство один раз |
| pending | canceled | failed; для аренды создать задолженность один раз |
| paid | тот же успех или запоздалый неокончательный сигнал | без нового финансового эффекта |
| failed | тот же отказ | без нового финансового эффекта |
| paid/failed | несовместимый проверенный окончательный итог | журнал аномалий и сверка, без автоматического пересмотра |

Применение и запись нормализованного результата выполняются под блокировкой обязательства. Ошибка магазина/суммы/metadata отклоняет сообщение; невозможность получить объект — 503 без применения. Подтверждение 200 выдаётся после фиксации результата либо журнала повтора/аномалии.

Для штрафа/задолженности состояние обязательства unpaid/paid отделено от статуса попытки. Отказ текущей попытки сохраняется; система создаёт следующую ссылку с новым operation_id и тем же неоплаченным обязательством. После трёх окончательных отказов — attention, уведомление и эксплуатационная сверка. Исторические id и результаты не перезаписываются. F4/F11 возвращают confirmation_url только для текущей pending-попытки; при paid/attention ссылка отсутствует, а при требуемой сверке задаются attention_required и reason_code. Администратор при сверке проверяет журнал, текущий объект шлюза и отсутствие pending другой попытки; возобновление допускается только по согласованному фактическому состоянию, без автоматического второго списания.

Повтор транспортного запроса использует тот же ключ в пределах одного часа с первой отправки; за пределом окна автоматическое повторное создание запрещено, требуется сверка. Выбранное окно короче 24-часового срока идемпотентности провайдера, указанного в [формате взаимодействия](https://yookassa.ru/developers/using-api/interaction-format). Повтор одной доставки, новое состояние той же попытки и следующая попытка имеют разные основания: пара внешний id/статус; переход pending; новый внутренний operation_id соответственно. Таймаут HTTP шлюза — 5 с.

## 6.8. Приём F6 и ресурсы

Обязательный JSON: schema_version (1.0/1.1), message_id UUID, vehicle_id UUID, measured_at RFC3339, latitude/longitude, mileage_km ≥0, fuel_percent и charge_percent (0–100 либо null по типу энергии), technical_status из normal/service_required/unavailable. Токен интеграции проверяет auth; telemetry_adapter нормализует схему; state проверяет ТС и значения.

measured_at не должен превышать серверное время начала приёма: будущее измерение даёт 400 INVALID_MESSAGE без изменения состояния. При подготовке стенда согласуются часы имитатора и сервера. F2/F3/F5 принимают возраст от 0 до 30 секунд включительно. Квитанции сохраняют идентификатор, хеш и исход обработки; полная история телематических значений не хранится. Актуальная запись каждого ТС содержит значения с максимальной принятой отметкой времени.

Восемь мест обработки выделены только F6. При отсутствии места возвращается 429 до подтверждения. Отдельной прикладной очереди нет; отправитель сохраняет неподтверждённое сообщение и повторяет его с тем же message_id. Пулы PostgreSQL: телеметрия 8, пользовательские запросы 8, фоновые действия 2; соответствующие блокирующие обработчики используют раздельные исполнители на 8/8/2 потока. Восемь мест F6 включают всю обработку сообщения и исключают скрытую очередь перед исполнителем. HTTP-ожидание выполняется асинхронно без удержания соединения PostgreSQL. Это устройство проверяется П-20, а не объявляется достаточным только по числу пулов.

В транзакции state условно обновляет актуальную запись, только если новая отметка больше сохранённой; сравнение и запись атомарны. Затем сохраняется квитанция message_id/хеш тела/исход. Раннее/равное сообщение даёт ignored. Повтор идентичного message_id даёт duplicate; повтор id с другим телом — 409 MESSAGE_ID_REUSED. 200 содержит `{message_id, outcome, applied, current_measured_at}` и выдаётся после фиксации. Некорректное — 400, неизвестное ТС — 404, неверный токен — 401, отказ PostgreSQL — 503. Поддерживаемое необязательное расширение 1.1 не меняет смысл 1.0; другая основная версия — 400 UNSUPPORTED_SCHEMA.

Текущая запись ищется по vehicle_id без обхода истории. Метрики: received/applied/ignored/duplicate/rejected, сообщения не по порядку, занятые места, задержка приём→фиксация и возраст состояния. Журналы содержат ТС, message_id, время и результат; пароль, JWT и документы не записываются. Функции F2/F3/F5/F8 используют дату измерения; F6 не меняет available/reserved/rented/blocked.

## 6.9. Долговечные задания и восстановление

Предметная запись и исходящее задание сохраняются одной транзакцией. Задание содержит id, тип и владельца, object_id, operation_id/command_id, полезные данные, created_at, attempts, next_run_at, lease_until и состояние ready/running/done/attention. Обработчик компонента-владельца выбирает запись каждые 5 с с блокировкой и арендой на 15 с, фиксирует её, выполняет внешний вызов вне транзакции, затем сохраняет ответ и результат. После сбоя просроченная аренда может быть взята повторно.

Для открытия/закрытия сохраняются command_id, поколение и последовательность; для платежа — operation_id и окно повтора; для письма — id уведомления и стабильный Message-ID. После трёх транспортных неудач — attention. Автомобиль остаётся blocked при неопределённом закрытии, финансовая попытка — pending при неизвестном результате. Восстановление продолжает прежнее действие; оно не создаёт новый идентификатор для обхода неизвестного исхода. SMTP не гарантирует устранения повторной доставки после сбоя между приёмом письма и записью результата, поэтому повтор письма допустим с тем же Message-ID и не меняет предметный результат.

Контрольные границы: фиксация до отправки; внешний эффект до записи ответа; запись ответа до подтверждения клиенту. Проверяются повтор, неизменность идентификатора и отсутствие повторного открытия/списания; уведомление допускает повторную доставку. Ожидаемое возобновление после восстановления стенда — ≤60 с. notifier применяет тот же механизм заданий; результат SMTP означает передачу серверу и доступен для наблюдения.

## 6.10. Подготовка, измерение и развитие

Подготовить карточки парка, регламент/базу ТО, тарифы/парковки, роли и имитаторы. Развернуть изолированный стенд, миграции, конфигурацию SMTP и тестовый магазин шлюза. Затем реализовать обработчики и выполнить проверки П-01–П-28. Нормативы нагрузки заданы до прогона: 100 сообщений/с 10 минут, параллельно 20 чтений/с; P95 фиксации ≤1 с, P95 чтения ≤2 с. При 200 сообщениях/с 30 с разрешены явные отказы приёма; подтверждённые записи сохраняются, восстановление ≤60 с.

Новая схема, изменение внешнего протокола или профиля нагрузки требуют проверки совместимости, миграций и повторения затронутых проверок. Наличие описанного механизма оценивается анализом проекта; его фактические показатели устанавливаются только исполнением реализации на указанном стенде.
