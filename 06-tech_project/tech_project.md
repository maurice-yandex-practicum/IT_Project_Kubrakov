# Технический проект автоматизированной системы «Каршеринг»

## 6.1. Назначение и границы системы

АС «Каршеринг» автоматизирует регистрацию арендаторов, поиск и аренду транспортных средств, сопровождение поездки, завершение аренды, расчёты, штрафы, задолженности и контроль состояния автопарка. Технический проект переводит решения предметной, ER-, функциональной, BPMN- и архитектурной моделей в состав программных компонентов, данных, операций и интерфейсов.

В состав решения входят единое серверное приложение, REST API, модули регистрации, аренды, состояния ТС, администрирования, финансовых обязательств, обслуживания, адаптеры внешних систем, сервис уведомлений и единая база данных. Система взаимодействует с имитаторами проверки документов и телематики, платёжным шлюзом и SMTP-сервером.

## 6.2. Архитектура и программная платформа

Система строится как модульный монолит на Python с использованием FastAPI. Uvicorn запускает приложение как ASGI-сервис. Внешние участники обращаются к единой точке входа по REST API поверх HTTP; внутренние компоненты взаимодействуют программными вызовами внутри одного приложения и одной единицы развёртывания.

Компоненты и их техническая ответственность:

| Компонент | Техническая ответственность |
|---|---|
| `gateway` | приём запроса, маршрутизация, единый формат ошибок |
| `auth` | выдача и проверка JWT, проверка роли |
| `registration` | оферта, проверки документов, создание пользователя |
| `rental` | поиск, начало, сведения и завершение аренды |
| `state` | приём и хранение состояния ТС |
| `finance` | штрафы, задолженности, состояние обязательств |
| `maintenance` | критерии и перечень обслуживания |
| `admin` | тарифы и парковки |
| `docs_adapter` | обмен с системами проверки документов |
| `telemetry_adapter` | команды ТС и приём телеметрии |
| `payment_adapter` | списание, ссылка и результат оплаты |
| `notifier` | формирование, отправка и повтор уведомлений |

Данные хранятся в PostgreSQL. Для доступа используются SQLAlchemy и psycopg, миграции выполняются Alembic, проверка входных данных и схем сообщений — Pydantic. Аутентификация выполняется JWT-токенами; предусмотрены роли арендатора, администратора и технической службы. Тестирование выполняется средствами pytest и httpx, сборка и CI/CD — через `pyproject.toml`, pip и GitHub Actions. Приложение и СУБД разворачиваются в контейнерах Docker Compose на сервере Linux.

### 6.2.1. Переход от концептуального компонента к техническому устройству

Каждый прикладной компонент реализуется по единой ролевой схеме:

1. входной обработчик принимает запрос;
2. проверяется структура сообщения;
3. проверяются права и предметные условия;
4. выполняется прикладная обработка;
5. выполняется доступ к данным в транзакции;
6. при необходимости вызывается интеграционный адаптер;
7. формируется результат или контролируемая ошибка.

Роли технических частей не требуют раскрытия исходного кода. Для подробно раскрываемых цепочек указывается, кто вызывает часть, какие данные передаются, что изменяется, где возможен отказ и как он отражается в результате.

## 6.3. Информационное обеспечение

База данных содержит предметные массивы:

- **пользователи и документы:** ФИО, телефон, электронная почта, признак и дата принятия оферты, паспорт и ВУ со статусами проверки;
- **автопарк:** ТС (государственный номер, VIN, год выпуска, цвет, операционный статус), модель, паспорт ТС;
- **состояние:** дата и время измерения, координаты, пробег, уровень топлива и заряда, технический статус;
- **аренда и тариф:** время начала и окончания, применённые стартовая стоимость, единица времени и стоимость единицы, состояние аренды, внешний идентификатор платежа;
- **парковка:** координаты и радиус подтверждения;
- **финансы:** штраф, задолженность, сумма, состояние оплаты, ссылка на оплату, внешний идентификатор операции;
- **уведомления:** адресат, содержание, результат и число попыток отправки.

Применимые финансовые условия копируются в запись аренды при её начале. Справочник тарифов используется только при создании новой аренды.

## 6.5. Ключевые процессы

### 6.5.1. Регистрация

АС получает данные арендатора и решение по оферте. При отказе процесс прекращается. При согласии система параллельно направляет через `docs_adapter` запросы проверки паспорта и ВУ, объединяет результаты и создаёт пользователя только при положительных результатах обеих проверок. Отрицательный результат любой проверки даёт отказ; недоступность внешней системы — контролируемую ошибку без создания пользователя.

### 6.5.2. Начало аренды

1. `POST /api/rentals` принимает идентификатор ТС и ключ идемпотентности.
2. В транзакции базы данных выполняется блокировка строки ТС, проверяются операционный статус, отсутствие аренды в состоянии `starting` или `active`, отсутствие непогашенной задолженности и результаты повторной проверки документов.
3. В аренду копируются применимые стартовая стоимость, единица времени и стоимость единицы; создаётся запись в состоянии `starting`; ТС резервируется; транзакция фиксируется.
4. Вне транзакции `telemetry_adapter` передаёт команду разблокировки с таймаутом.
5. При подтверждении аренда переходит в `active`. При отказе, недоступности модуля или истечении времени ожидания — в `start_failed`, ТС освобождается, арендатор получает объяснимый результат.
6. Повторный запрос с тем же ключом возвращает существующую попытку; конкурирующий запрос по тому же ТС получает конфликт.

Защищаемый инвариант — у одного ТС не может быть более одной аренды в состоянии `starting` или `active`. Конфликт возвращается как `409`. Внешний HTTP-вызов находится вне транзакции, поэтому согласование внешнего эффекта с сохранённым состоянием выполняется отдельным переходом состояния и компенсирующей командой закрытия при позднем подтверждении.

### 6.5.3. Завершение аренды и стоимость

1. `POST /api/rentals/{rental_id}/finish` принимает запрос.
2. В транзакции блокируется аренда, проверяется состояние `active`, определяется ТС.
3. Из состояния читается местоположение; проверяется расстояние до парковки. При отрицательном результате возвращается `409`, аренда остаётся действующей.
4. Фиксируется `ended_at` — серверное время приёма корректного запроса, до внешних вызовов.
5. Рассчитывается стоимость:
   `стоимость = стартовая стоимость + стоимость единицы времени × ceil((ended_at − started_at) / длительность единицы времени)`.
   Единицы измерения — рубли и минуты. Дополнительные денежные округления не применяются.
6. Создаётся обязательство по оплате аренды с внешним идентификатором операции и состоянием `pending`; аренда переходит в `finished`; изменения фиксируются.
7. Вне транзакции выполняется списание через `payment_adapter` и команда закрытия ТС через `telemetry_adapter`; результаты сохраняются отдельно.
8. Финансовый результат: окончательный успех — обязательство `paid`; окончательный отказ — создаётся задолженность и ссылка на оплату; ожидание или неизвестный исход — обязательство остаётся `pending` до получения результата или согласованного решения по таймауту.

Предварительная стоимость F4 использует то же правило на момент запроса. Изменение справочника тарифов не изменяет применённые условия аренды.

### 6.5.4. Финансовые результаты и оплата

`POST /api/integrations/payments/result` принимает callback платёжного шлюза. Проверяется подпись, сообщение сопоставляется с обязательством по внешнему идентификатору операции. Допустимые переходы: `pending → paid`, `pending → failed`. Состояние `paid` является поглощающим. Повторное сообщение с тем же идентификатором не создаёт эффекта; противоречивое сообщение журналируется как аномалия и не изменяет окончательный результат.

Ответственность разделена: F5 инициирует списание стоимости аренды и создаёт обязательство; F12 принимает и обрабатывает результаты оплаты аренды, штрафа и задолженности. Дублирование одного сообщения, повторная платёжная попытка и новый самостоятельный платёж различаются по внешнему идентификатору.

При окончательном отказе списания стоимости аренды создаётся задолженность и ссылка на оплату; событие получения ссылки — создание задолженности. Отдельный пользовательский маршрут инициирования платежа не вводится. Поздний успешный результат после отказа переводит обязательство в `paid` и снимает задолженность.

### 6.5.5. Приём состояния ТС

1. `POST /api/integrations/telematics/state` принимает JSON-сообщение от имитатора телематики.
2. Проверяются служебные учётные данные, структура и допустимость значений.
3. Проверяется, что ТС известно.
4. В транзакции выполняется условное обновление актуального состояния: применяется только сообщение с более поздней временной отметкой.
5. Подтверждение `200` выдаётся после фиксации. Устаревшее или равное сообщение получает `200` с признаком «не применено» и отдельным кодом; неизвестное ТС — `404`; некорректное сообщение — `400`; недоступность базы данных — `503` без подтверждения обработки.

Одной фразы о транзакции недостаточно: атомарность охватывает решение об актуальности и запись, поэтому сравнение отметки и обновление выполняются одним условным запросом. Это исключает перезапись более новых сведений конкурирующим устаревшим сообщением.

### 6.5.6. Состояние и обслуживание

Актуальное состояние хранится отдельно от журнала сообщений; получение текущего состояния не зависит от объёма накопленных сообщений. `maintenance` формирует перечень по техническому признаку, уровню топлива или заряда, пробегу и интервалу обслуживания. Технический признак, уровень топлива и заряда, а также пробег читаются из актуального состояния ТС. Нормы интервала и пороговые значения задаются параметрами проекта и фиксируются до применения; произвольные значения не подставляются. ТС включается в перечень, если истинно хотя бы одно условие, а в ответе указывается основание включения.

### 6.5.7. Штраф и просмотр обязательств

Администратор создаёт штраф, связанный с арендой. `finance` сохраняет штраф, получает через `payment_adapter` ссылку на оплату и формирует уведомление. `GET /api/fines` и `GET /api/debts` возвращают арендатору только его обязательства, администратору — обязательства всех арендаторов. Ограничение по роли и владельцу выполняется на сервере, а не клиентом.

## 6.6. Интерфейсы

Формат прикладных сообщений — JSON. Идентификаторы ресурсов передаются в URL. Доступ проверяется JWT и ролью. Ошибки возвращаются в едином формате с кодом и сообщением; применяются HTTP-статусы 200, 201, 400, 401, 403, 404, 409, 422, 429 и 500.

| Функции | Метод и путь | Существенные поля |
|---|---|---|
| вход | `POST /api/auth/login` | телефон, пароль; ответ — JWT и роль |
| F1 | `POST /api/registrations` | сведения пользователя, паспорт, ВУ, признак оферты |
| F2 | `GET /api/vehicles/nearby` | широта, долгота, радиус |
| F3 | `POST /api/rentals` | `vehicle_id`, ключ идемпотентности |
| F4 | `GET /api/rentals/{rental_id}`; `GET /api/vehicles/{vehicle_id}` | идентификатор аренды или ТС |
| F5 | `POST /api/rentals/{rental_id}/finish` | идентификатор аренды |
| F6 | `POST /api/integrations/telematics/state` | `vehicle_id`, `measured_at`, координаты, пробег, топливо, заряд, статус |
| F7 | `POST /api/admin/fines` | `rental_id`, размер, статья |
| F8 | `GET /api/maintenance/vehicles` | критерии выборки |
| F9 | `GET/POST /api/admin/tariffs`; `PATCH /api/admin/tariffs/{tariff_id}` | единица времени, стоимость, активность |

Интеграционные запросы телематики и платежей аутентифицируются служебными учётными данными; подлинность callback проверяется подписью. Имитатор документов получает запросы проверок; телематический модуль принимает команды открытия и закрытия и отправляет состояние; платёжный шлюз обрабатывает списания и возвращает результаты; SMTP-сервер доставляет письма.

## 6.7. Надёжность и нагрузка

Приём телеметрии выполняется синхронной записью в базу данных с ограничением параллелизма на уровне пула соединений и числа рабочих процессов. Отдельная очередь в текущем решении не вводится: подтверждение выдаётся только после фиксации, а при исчерпании допустимой ёмкости модуль возвращает контролируемую ошибку и ограничивает приём. Если заявленные гарантии потребуют очереди, изменение решения обосновывается отдельно и синхронизируется с архитектурой и испытаниями.

Метрики очереди не означают наличия технического механизма; выбранное решение согласует требования F6/2.1–F6/2.7 за счёт ограничения приёма, изоляции пула соединений и измерения задержки. Телеметрия не блокирует пользовательский API: запросы обрабатываются отдельными соединениями, а деградация телеметрии не делает пользовательский API недоступным.

Ведётся журнал приёма и обработки с идентификатором ТС, временной отметкой, результатом и причиной отказа; предоставляются показатели числа принятых, обработанных, отклонённых и повторных сообщений, числа сообщений не по порядку, времени обработки и возраста последнего состояния.

## 6.8. Ошибки и согласованность

Техническая ошибка сохранения отличается от предусмотренного предметного исхода. Неуспешное списание является основанием правила о задолженности, а не основанием откатить весь процесс завершения аренды. Сбои внешней системы, таймаут и отрицательный деловой ответ описываются раздельно там, где различаются последствия.

Операции с базой данных выполняются транзакционно. Создание аренды использует согласованные данные пользователя, ТС, тарифа и задолженности; завершение связывает финансовый результат с конкретной арендой; платёжные сообщения проверяются на повтор; телеметрия связывается с ТС и временной отметкой. Внешние вызовы выполняются с таймаутами и ограниченным числом повторов вне транзакции базы данных.

6. Провести интеграционные и функциональные проверки средствами pytest и httpx по методике испытаний.

Результатом технического проекта является единое серверное приложение, связанное с PostgreSQL, внешними адаптерами и сервисом уведомлений, с определёнными функциями F1–F12, интерфейсами, правилами данных и поведением при штатных и ошибочных ситуациях.
