# **6 Требования технические. Требования к наиболее сложному программному модулю**

## **6.1 Технический стек**

Программная система реализуется на едином языке Python как на стороне пользовательского интерфейса, так и на стороне прикладного слоя. Состав применённых технологий и их назначение приведены в таблице 4.

Таблица 4 — Технический стек системы

| **Область**                          | **Технология**             | **Назначение**                                                                                                                       |
| ------------------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Серверный пользовательский интерфейс | Python, Streamlit          | Формы ввода и отображение данных; обращается к Backend по HTTP/JSON; доступ к БД напрямую запрещён                                   |
| Прикладной слой (Backend)            | Python, FastAPI            | Предметные операции, проверка пользователя и прав, HTTP/JSON API                                                                     |
| Доступ к данным                      | SQLAlchemy                 | Объектно-реляционное отображение; доступ к основной базе данных                                                                      |
| Основная база данных                 | PostgreSQL 18              | Единый источник данных системы; ограничения целостности на уровне БД                                                                 |
| Аутентификация                       | JWT                        | Короткоживущий подписанный токен входа; проверка подписи, срока, активности и полномочий                                             |
| Транспорт                            | HTTPS, WSS                 | Защита пользовательского канала; клиент Streamlit — WSS; локальная HTTP-связь UI и Backend внутри контейнера                         |
| Развёртывание                        | Инфраструктурный контейнер | UI и Backend — отдельные процессы одного контейнера; PostgreSQL — на отдельном сервере; данные БД переживают пересоздание контейнера |

Среда эксплуатации включает по одному экземпляру UI, Backend и Database: два приложения работают отдельными процессами в одном инфраструктурном контейнере, база данных размещена на отдельном сервере. Численные требования к нагрузке, времени ответа, доступности, допустимой потере данных и сроку восстановления в базовой модели не установлены; конкретные операционная система, продукт контейнеризации и параметры защиты и восстановления определяются при реализации и развёртывании.

## **6.2 Требования к наиболее сложному программному модулю**

Наиболее сложным программным модулем системы является компонент Backend «Управление заявками». Сложность модуля определяется его ролью единственной точки регистрации заявок и управления жизненным циклом (пять статусов), необходимостью координации участников трёх ролей (REPORTER, DISPATCHER, TECHNICIAN), взаимодействием с компонентами «Авторизация» (проверка права и внутреннее чтение участников) и «Учёт ремонта» (общая транзакция), а также требованиями целостности и защищённости данных.

Функциональные требования к модулю:

– принимать и проверять данные заявки по справочным накопителям (сотрудник, оборудование, категория неисправности) до регистрации;

– регистрировать заявку со статусом NEW и создавать запись о заявителе с ролью REPORTER; записи формируются только данным модулем;

– по запросу сотрудника предоставлять текущий статус заявки и результат выполненного ремонта;

– выполнять отмену заявки только при условии, что сотрудник является её автором и заявка находится в статусе NEW; при несоблюдении условий запись заявки остаётся без изменений;

– обеспечивать переходы статусов NEW → ASSIGNED → IN_PROGRESS → CLOSED в согласованных сценариях назначения и ремонта.

Требования к данным и целостности:

– данными модуля являются таблицы repair_requests (D7) и request_participants (D8) с составным ключом (request_id, role_in_request);

– ограничения CHECK контролируют допустимые значения статусов, приоритетов и ролей участников;

– связанные изменения заявки и ремонта выполняются в общей транзакции: ошибка вызывает откат, вложенные операции не фиксируют изменения независимо;

– конкурирующие изменения одной заявки должны обнаруживаться, повторное действие не должно незаметно создавать дубликаты.

Требования к безопасности и интерфейсу:

– при каждом защищённом запросе проверяются подпись, назначение и срок JWT, актуальная активность сотрудника, полномочия и участие в заявке;

– взаимные вызовы с компонентом «Авторизация» разделяются на проверку права и внутреннее чтение участников без повторного запуска того же защищённого сценария;

– пароль и его хэш не включаются в JWT; ключ подписи не передаётся UI; секреты не журналируются;

– модуль предоставляет HTTP/JSON API; прямой доступ пользовательского интерфейса к базе данных запрещён.
