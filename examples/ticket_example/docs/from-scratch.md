# Как строить модели с нуля: сквозной пример

Этот файл показывает на маленьком примере, как из словесного описания шаг за шагом получаются все модели курса: ER, контекстная диаграмма, дерево функций, ДПД, BPMN, архитектура, Solution и ПМИ. Заодно видно, как модели проверяют друг друга.

Пример нарочно простой — **районная библиотека**, чтобы не мешали детали. В конце есть таблица: где тот же шаг в нашем проекте.

## Главная мысль

Все модели вырастают из одного описания и **проверяют друг друга**:

- ER отвечает на вопрос «что система помнит»;
- DFD — «что система делает и какими документами обменивается»;
- BPMN — «в каком порядке».

ER и DFD строятся параллельно. Встречаются они в двух местах:

- хранилище DFD — это группа сущностей ER;
- поле документа DFD — это атрибут ER.

Если что-то есть в одной модели и нет в другой, значит, одна из них ошибочна. Поиск таких расхождений — основная работа на стадии 2.

## Шаг 1. Описание

Пишем обычным текстом, как идёт деятельность:

> Районная библиотека выдаёт книги. Читатель записывается в библиотеку: библиотекарь вносит его ФИО, паспорт и телефон, а читатель получает читательский билет с номером. Новые книги библиотекарь принимает в фонд: у книги есть ISBN, название и автор, у каждого экземпляра — инвентарный номер. Чтобы взять книгу, читатель заполняет требование. Книгу выдают на 14 дней. Когда читатель приносит книгу, библиотекарь отмечает возврат. Каждое утро система рассылает должникам напоминания.

Из описания выписываем три списка.

**Участники** — те, кто вне системы и что-то ей даёт или от неё получает: Читатель, Библиотекарь.

**Сценарии** — законченные истории «кто что делает»:

- С1 — запись читателя;
- С2 — приём книг в фонд;
- С3 — выдача книги;
- С4 — возврат книги;
- С5 — напоминание должникам.

**Правила** — то, что нельзя нарушать:

- П1 — на руках у читателя не больше 5 книг;
- П2 — книга выдаётся на 14 дней;
- П3 — читателю с просроченной книгой новых не выдают;
- П4 — экземпляр одновременно выдан не больше чем одному читателю.

## Шаг 2. ER: газетный анализ текста

Метод преподавателя — **газетный анализ**: читаем описание как газетную статью и подчёркиваем слова трёх видов.

| Что подчёркиваем                                                       | Во что превращается | Пример                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| существительные, о которых надо что-то помнить | сущности                     | Читатель, Книга, Экземпляр, Выдача                                                                                                                                                                                                                                    |
| свойства этих существительных                              | атрибуты                     | у Читателя: номер билета, ФИО, паспорт, телефон; у Книги: ISBN, название, автор; у Экземпляра: инвентарный номер; у Выдачи: дата выдачи, срок возврата, дата возврата |
| глаголы между существительными                            | связи                           | Книга *имеет* Экземпляры (1 : N); Читатель *получает* Выдачи (1 : N); Экземпляр *выдаётся по* Выдачам (1 : N)                                                                                                           |

Почему «Выдача» — отдельная сущность, а не связь «Читатель — Экземпляр»: у выдачи есть свои атрибуты (даты), и один экземпляр за свою жизнь выдают много раз.

**Сверка с правилами.** Каждое правило должно опираться на данные ER:

- П1 «не больше 5» — считаем выдачи читателя без даты возврата;
- П2 «14 дней» — атрибут Выдача.срок возврата;
- П3 «просрочка» — срок возврата раньше сегодняшнего дня, а даты возврата нет;
- П4 «экземпляр свободен» — у экземпляра нет выдачи без даты возврата.

Атрибут «статус экземпляра: на полке / выдан» не нужен: он выводится из выдач. Если хранить его отдельно, получится дублирование, и два места могут разойтись.

## Шаг 3. Контекстная диаграмма

Вся система — одна функция **F0 «Учёт выдачи книг»**. Вокруг неё — участники (внешние сущности). Проходим каждый сценарий и спрашиваем: **что участник отдаёт системе и что получает от неё?** Каждый ответ — стрелка с **названием документа**.

| Сценарий | Документ                                               | Откуда → куда       |
| ---------------- | -------------------------------------------------------------- | ------------------------------ |
| С1              | P1 «Анкета читателя»                           | Библиотекарь → F0 |
| С1              | P2 «Читательский билет»                     | F0 → Читатель         |
| С2              | P3 «Сведения о поступивших книгах» | Библиотекарь → F0 |
| С2              | P4 «Акт приёма в фонд»                         | F0 → Библиотекарь |
| С3              | P5 «Требование на книгу»                    | Читатель → F0         |
| С3              | P6 «Квитанция о выдаче или отказ»    | F0 → Читатель         |
| С4              | P7 «Отметка о возврате»                      | Библиотекарь → F0 |
| С4              | P8 «Подтверждение возврата»             | F0 → Библиотекарь |
| С5              | P9 «Напоминание о возврате»              | F0 → Читатель         |

```
E1 Читатель      ── P5 Требование на книгу ──────────────▶  F0
E1 Читатель      ◀─ P2 Читательский билет ───────────────   F0  Учёт
E1 Читатель      ◀─ P6 Квитанция о выдаче или отказ ─────   F0  выдачи
E1 Читатель      ◀─ P9 Напоминание о возврате ───────────   F0  книг
E2 Библиотекарь  ── P1 Анкета читателя ──────────────────▶  F0
E2 Библиотекарь  ── P3 Сведения о поступивших книгах ────▶  F0
E2 Библиотекарь  ◀─ P4 Акт приёма в фонд ────────────────   F0
E2 Библиотекарь  ── P7 Отметка о возврате ───────────────▶  F0
E2 Библиотекарь  ◀─ P8 Подтверждение возврата ───────────   F0
```

Хранилищ на контекстной диаграмме нет: они внутри системы, а КД показывает систему как чёрный ящик.

Запоминаем числа для баланса: Читатель отдаёт 1 документ и получает 3, Библиотекарь отдаёт 3 и получает 2. Всего 9.

## Шаг 4. Функции и дерево функций

Группируем сценарии по виду работы. Имя функции — отглагольное существительное:

- F1 «Учёт читателей и фонда» — С1 и С2: принять сведения и записать их. «Учёт» — слово преподавателя для функции, которая принимает сведения и ведёт хранилище;
- F2 «Выдача книг» — С3;
- F3 «Приём возвращённых книг» — С4;
- F4 «Напоминание должникам» — С5.

Дерево: F0 делится на F1, F2, F3, F4. У каждого листа дерева будет спецификация — процесс BPMN (шаг 9).

Самопроверка: каждый документ КД относится ровно к одной функции.

## Шаг 5. ДПД уровня 1

1. **Разносим документы КД по функциям.** Те же 9 стрелок, ни одной новой и ни одной потерянной — это и есть баланс:

   - F1: P1, P2, P3, P4;
   - F2: P5, P6;
   - F3: P7, P8;
   - F4: P9.
2. **Для каждой функции решаем, что ей нужно прочитать и что записать.** Каждый ответ — пара «запрос / ответ» к хранилищу.
3. **Хранилища** — сущности ER, сгруппированные по тому, кто с ними работает:

   - D1 «Читатели и фонд»: Читатель, Книга, Экземпляр. Пишет F1, читают F2 и F4;
   - D2 «Выдачи»: Выдача. Пишут F2 и F3, читает F4.

   Оба хранилища нужны двум и более функциям, поэтому стоят на уровне 1 (правило преподавателя). Физически это может быть одна база.

| Пара | Функция → хранилище | Запрос                                                     | Ответ                                                                                         |
| -------- | ------------------------------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Q1 / A1  | F1 → D1                             | Сведения о читателе                             | Квитанция записи с номером билета                                     |
| Q2 / A2  | F1 → D1                             | Сведения о книгах и экземплярах       | Квитанция приёма                                                                    |
| Q3 / A3  | F2 → D1                             | Запрос читателя и экземпляра            | Читатель и экземпляр найдены или нет                                |
| Q4 / A4  | F2 → D2                             | Запрос выдач читателя и экземпляра | Книги на руках, просрочки, открытая выдача экземпляра |
| Q5 / A5  | F2 → D2                             | Запись выдачи                                        | Квитанция выдачи                                                                    |
| Q6 / A6  | F3 → D2                             | Закрытие выдачи по экземпляру          | Выдача закрыта или не найдена                                             |
| Q7 / A7  | F4 → D2                             | Запрос просроченных выдач                 | Список просрочек                                                                    |
| Q8 / A8  | F4 → D1                             | Запрос телефонов читателей               | Телефоны                                                                                   |

Запрос и ответ рисуются отдельными стрелками: это разные документы.

## Шаг 6. Газетный анализ документов

Теперь «газетой» служит документ — бланк. Газетный анализ одинаков для любого документа: берём бланк, выписываем его поля и для каждого поля ищем атрибут ER. От направления документа зависит другое — **какой вопрос мы задаём полю**. Есть ещё третья проверка: она идёт не по документу, а по ER целиком.

| | Что проверяем | Вопрос | Если ответа нет |
|---|---|---|---|
| 1 | **входящий** документ (его приносит внешний участник) | куда записать это поле или по какому атрибуту искать? | в ER не хватает атрибута (или поле лишнее) |
| 2 | **исходящий** документ (его отдаёт система) | откуда взять это поле: из какого атрибута и через какое обращение функции к БД? Или как вычислить? | в ER не хватает атрибута **или** в DFD не хватает пары «запрос / ответ» |
| 3 | **ER целиком** | кто кладёт этот атрибут в БД: какой входящий документ или сама система? | не хватает входящего документа (и функции, которая его примет) |

Исходящие документы источником атрибута не бывают: они только читают то, что уже лежит в БД.

### Вопрос 1. Входящий документ: «Требование на книгу»

В библиотеке такой бланк настоящий — «читательское требование»:

```
┌─ ТРЕБОВАНИЕ НА КНИГУ ───────────────────────────┐
│ Читательский билет № ________                   │
│ Фамилия _____________                           │
│ Автор ______________   Название ______________  │
│ ISBN _______________                            │
│ Инв. № экземпляра ________ (пишет библиотекарь) │
└─────────────────────────────────────────────────┘
```

Для каждого поля спрашиваем: **куда это записать или по чему искать?**

| Поле | Атрибут ER | Пояснение |
|---|---|---|
| Читательский билет № | Читатель.номер билета | по нему находим читателя |
| Фамилия | не хранится | только для сверки: фамилия уже есть у Читателя |
| Автор, Название | по ним ищем: Книга.автор, Книга.название | из требования ничего не записывается, но искать можно только по атрибуту, который есть в ER |
| ISBN | Книга.ISBN | — |
| Инв. № экземпляра | Экземпляр.инвентарный номер | выдача ссылается на конкретный экземпляр |

В первом варианте бланка поля «Инв. № экземпляра» не было. Газетный анализ это сразу показал: Выдача в ER ссылается на Экземпляр, а документ не говорит, какой именно. Так находится дыра — **данные нужны ER, а документ их не приносит**.

### Вопрос 2. Исходящий документ: «Квитанция о выдаче или отказ»

Сначала решаем, какие поля логично должны быть в квитанции. Потом для каждого спрашиваем: **откуда функция F2 его возьмёт?**

| Поле квитанции | Откуда взять | Через что |
|---|---|---|
| ФИО читателя | Читатель.ФИО | ответ A3: F2 читает читателя из D1 |
| Название и автор книги | Книга.название, Книга.автор | ответ A3 |
| Инвентарный номер | пришёл в самом требовании | — |
| Дата выдачи | Выдача.дата выдачи, её ставит система | записывается Q5, подтверждается A5 |
| Срок возврата | Выдача.срок возврата = дата выдачи + 14 дней (П2) | Q5 / A5 |
| Причина отказа | не хранится: вычисляется на шлюзе по П1, П3, П4 | по данным ответа A4 |

Эта проверка ловит два вида дыр:
- **атрибута нет в ER.** Хотим, чтобы квитанция говорила, где стоит книга: «стеллаж 4, полка 2». В ER такого атрибута нет — добавляем Экземпляр.место хранения. Сразу включается вопрос 3: кто кладёт место хранения в БД? Значит, в P3 «Сведения о поступивших книгах» нужно поле «стеллаж, полка». Одно поле в исходящем документе потянуло за собой ER и входящий документ;
- **атрибут в ER есть, но функция его не читает.** Если бы у F2 не было пары Q3 к D1, ей неоткуда было бы взять название книги для квитанции. Нужна пара — это дыра в DFD.

Взять такие данные у другой функции через внутренний поток не получится, если между событиями проходит время: функция не помнит данные между событиями, всё, что должно дождаться, лежит в хранилище. В нашем проекте эта проверка нашла билеты (P12): в них есть место и название мероприятия, а функция оплаты не читала D1. Добавили пару Q24.

### Вопрос 3. ER целиком: у каждого атрибута есть источник

Проходим все атрибуты ER и для каждого ищем, кто его кладёт в БД:

| Атрибут | Откуда |
|---|---|
| Читатель.номер билета | формирует система (F1) |
| Читатель.ФИО, паспорт, телефон | P1 «Анкета читателя» |
| Книга.ISBN, название, автор; Экземпляр.инвентарный номер | P3 «Сведения о поступивших книгах» |
| Выдача.дата выдачи | формирует система: сегодняшняя дата |
| Выдача.срок возврата | формирует система: дата выдачи + 14 дней (П2) |
| Выдача.дата возврата | формирует система, когда приходит P7 «Отметка о возврате» |

Допустим, мы забыли сценарий С2 «Приём книг в фонд». Тогда у Книги и Экземпляра не нашлось бы источника: ни один входящий документ их не приносит. Это дыра — **не хватает документа**, а с ним и функции, которая его принимает.

Поля «не хранится» — нормальное явление: это параметры запроса (например, «за какой период» в запросе отчёта) и то, что вычисляется на лету (итоги, причина отказа).

У нас все три вопроса проверяет `tools/check.py`, а ответы по каждому полю видны в карточках документов (`generated/doc-cards.md`).

## Шаг 7. Правила ↔ данные

Для каждого правила отвечаем: при каком документе оно проверяется и какая пара приносит функции нужные данные.

| Правило                             | Когда проверяется  | Что нужно знать                                                             | Какая пара приносит |
| ------------------------------------------ | ---------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------ |
| П1 — не больше 5 книг        | при P5 «Требование» | выдачи читателя без даты возврата                           | Q4                                   |
| П3 — нет просрочек           | при P5                          | выдачи читателя со сроком раньше сегодня              | Q4                                   |
| П4 — экземпляр свободен | при P5                          | выдача экземпляра без даты возврата                       | Q4                                   |
| П2 — 14 дней                         | при P5                          | ничего читать не надо, срок считает сама функция | Q5 записывает срок     |

Если бы пары Q4 не было, F2 не смогла бы проверить П1: правило написано, а данных у функции нет. В нашем проекте такая же дыра была у возврата: F4 не знала дату начала мероприятия, и появилась пара Q19.

## Шаг 8. Требования

Каждое требование «система должна…» пишется из сценария и привязывается к функции:

| Требование | Текст                                                                                                                                                                                                                                                 | Откуда  | Функция |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | -------------- |
| FR-1                 | При получении анкеты система должна записать читателя и выдать номер билета                                                                                                               | С1           | F1             |
| FR-2                 | При получении требования система должна выдать экземпляр на 14 дней или отказать с причиной: лимит 5 книг, есть просрочка, экземпляр занят | С3, П1–П4 | F2             |
| FR-3                 | При отметке о возврате система должна закрыть выдачу экземпляра                                                                                                                                     | С4           | F3             |
| FR-4                 | Каждое утро система должна отправить напоминание каждому должнику                                                                                                                                | С5           | F4             |

Нефункциональное требование («выдача оформляется не дольше 1 секунды») на DFD не видно. Оно уходит в архитектуру и ПМИ.

## Шаг 9. BPMN

Для каждого листа дерева рисуем процесс: порядок действий, ветвления, ожидание. Пример — F2 «Выдача книг». Дорожки: «Читатель» и «Части комплекса программ» (действия системы).

1. Начало «Читатель пришёл за книгой».
2. Читатель заполняет требование. Сообщение P5 уходит в дорожку системы.
3. Система: «Поиск читателя и экземпляра» — обращение Q3 / A3 к D1.
4. Система: «Проверка выдач читателя и экземпляра» — обращение Q4 / A4 к D2.
5. Шлюз «Можно выдать?» — здесь проверяются П1, П3, П4:
   - да → «Запись выдачи на 14 дней» (Q5 / A5 к D2) → сообщение P6 «квитанция» → конец «Книга у читателя»;
   - нет → сообщение P6 «отказ с причиной» → конец «Книга не выдана».

Сверка с DFD: в процессе три обращения к БД (Q3, Q4, Q5) — у F2 в DFD тоже три пары. Документы на сообщениях — те же P5 и P6.

F4 «Напоминание должникам» начинается не с человека, а с **таймера** «каждый день в 9:00». Дальше: «Поиск просроченных выдач» (Q7) → «Поиск телефонов» (Q8) → сообщение P9 каждому должнику → конец.

## Шаг 10. Архитектура

Из дорожки системы в BPMN видно, какие программные части нужны: за каждой группой действий стоит компонент.

- **Компоненты:** К1 «Модуль учёта» (F1), К2 «Модуль выдачи» (F2, F3), К3 «Планировщик напоминаний» (F4).
- **Элементы окружения** — из внешних сущностей DFD: рабочее место библиотекаря, сайт или терминал читателя. Плюс SMS-шлюз для напоминаний — техническое средство доставки P9.
- **Группы данных** — из хранилищ: БД1 «Читатели и фонд», БД2 «Выдачи».
- **Связи** — из документов DFD: «терминал → К2: P5 „Требование“; К2 → терминал: P6 „Квитанция или отказ“».
- **Принцип функционирования** — путь каждой функции по компонентам, шаг за шагом. Для выдачи: терминал → К2 → БД1 (Q3) → БД2 (Q4, Q5) → К2 → терминал.

## Шаг 11. Solution

На каждой связи указываем технологию. Документ P5 «Требование на книгу» становится конкретным запросом:

```
POST /loans
{"card_no": "A-1024", "inventory_no": "INV-55731"}

201 {"loan_id": 901, "due_date": "2026-11-27"}
409 {"reason": "LIMIT_5"} | {"reason": "OVERDUE"} | {"reason": "COPY_TAKEN"}
```

На DFD P5 — просто «какие сведения и от кого кому». Формат (JSON, HTTP) появляется только здесь.

## Шаг 12. ПМИ

Проверки выводятся из требований и правил **до** кода:

| Проверка | Из чего | Что делаем                                                    | Что ожидаем                               |
| ---------------- | ------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| Т-1             | FR-2, П1     | у читателя 5 книг, выдаём шестую              | 409 `LIMIT_5`, выдача не записана |
| Т-2             | FR-2, П4     | выдаём экземпляр, который уже выдан      | 409 `COPY_TAKEN`                                  |
| Т-3             | FR-2, П3     | выдаём читателю с просроченной книгой | 409 `OVERDUE`                                     |

**Сквозная цепочка** для П1: правило → ER (Выдача без даты возврата) → пара Q4 → шлюз «Можно выдать?» → ответ 409 `LIMIT_5` → проверка Т-1. Если цепочка где-то рвётся, это дыра.
