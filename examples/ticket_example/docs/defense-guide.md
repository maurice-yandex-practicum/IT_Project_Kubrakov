Преподаватель 13.11: «за 3 минуты мне рассказать всё содержание вашего программного проекта с указанием всех необходимых вещей», максимум 4. Записку показываем на компьютере (docx), в скобках — что открыть.

1. **Назначение** (§1.1). «Тема — система продажи билетов и контроля входа на мероприятия. Назначение из четырёх частей: одно место одновременно занимает не более одной действующей брони или билета; покупатель получает билет или понятный отказ; на мероприятие проходят только по действительному билету; организатор сам выставляет мероприятие на продажу и видит продажи, возвраты и посещаемость на момент запроса. Пользователи — покупатель, организатор, контролёр и администратор; внешняя система — платёжный сервис».
2. **Декларативная модель** (рисунок ER, §2.2). «Одна ER-диаграмма Чена из двух частей. В контуре базы данных — предметная область, шестнадцать сущностей, в центре — билет. Сверху — система оценивания качества: пользователь пользуется программой, у каждой функции свой частный критерий удовлетворённости, он вычисляется из показателей, а качество программы складывается из этих критериев».
3. **Модель функционирования** (КД, дерево, ДПД-1, ДПД-2). «На контекстной диаграмме — система и пять участников, двадцать девять документов. Дерево делит систему на шесть функций и дальше до листьев: у каждого листа один вход и один ответ. На первом уровне видно, как функции работают с четырьмя хранилищами. Оплату раскрыли на втором уровне».
4. **Процессная модель** (BP1, затем F3.2). «Путь покупателя: афиша, бронь, оплата, билеты. На каждый его запрос — маленький процесс программы: получен документ, его обрабатывает один компонент, работая с базой, и отправляет ответ. Билеты выдаются только после того, как платёжный сервис подтвердил списание».
5. **Архитектура** (схема §3.1, компоненты §3.2, ПФ §3.4). «Из компонентов процессов собрана архитектура: одиннадцать компонентов и связи с технологиями. Каждый принцип функционирования начинается с того, какой части назначения он служит. Например, место занимается одной транзакцией, и вторую заявку на него база отклоняет».
6. **Solution** (§4). «Стек — FastAPI и PostgreSQL, классификатор запросов до аргументов и типов, физическая схема базы».
7. **Испытания** (§5.2.1, §5.7). «Предмет испытаний — качество для пользователя. Для каждой части назначения указано, какие показатели её подтверждают: двойной продажи нет ни в одном из ста конкурентных прогонов, частные критерии бронирования, оплаты и прохода не ниже 0,9. Бронирование, оплата и проход проверяются полностью, остальное — частично. Показатели снимаются по описанной процедуре и сводятся в интегральный критерий Q. Приёмка — Q не меньше 0,9 и выполнены условия назначения. Пользователь сам может проверить результат: в брони видна цена каждого билета, в возврате — расчёт по сроку».
8. **Целостность.** «Все модели заданы в одном реестре, их согласованность проверяет скрипт — около тысячи восьмисот проверок, ошибок нет».

## Шаг 0. Общая картина

> **Как строить модели с нуля** — сквозной учебный пример (библиотека) через все стадии, с газетным анализом и сверками: [from-scratch.md](from-scratch.md). Прочитать первым, если непонятно, откуда что берётся.

### Какой жизненный цикл изучает курс

Жизненных циклов два, и смотрят они с разных сторон:

| | Жизненный цикл **проекта** (управление) | Жизненный цикл **системы** (инженерия) — этот курс |
|---|---|---|
| Вопрос | как вести работу: люди, сроки, деньги | как создать продукт, чтобы он делал то, что нужно |
| Этапы | инициация → планирование → исполнение → контроль → закрытие | требования → концепция → эскизный проект → технический проект → рабочая документация → испытания → эксплуатация (ГОСТ 34.601-90) |
| Результат этапа | устав, план, отчёты о ходе | артефакты: описание, модели, архитектура, Solution, ПМИ, код |

Они вложены друг в друга. Все наши шаги 1–6 — это «исполнение» с точки зрения управления. Курс разбирает именно его, изнутри: какой артефакт получается на каждой инженерной стадии и почему следующий строится из предыдущего.

| Стадия курса | Стадия ГОСТ 34.601 |
|---|---|
| 1–2. Описание, ER, DFD, BPMN | формирование требований и концепция («исследование и обоснование») |
| 3. Архитектура | эскизный проект |
| 4. Solution | технический проект |
| 5. ПМИ | подготовка к испытаниям |
| 6. Программирование | рабочая документация |

### Цепочка артефактов

1. **Описание** — что за деятельность, кто участвует, по каким правилам → правила R01–R23.
2. **ER** — какие данные хранить, чтобы правила выполнялись (*что есть*).
3. **DFD** — какие функции выполняет система и какие документы куда идут (*что делается*).
4. **BPMN** — порядок действий, развилки, исходы, обращения к БД → видно, какие нужны программные компоненты.
5. **Архитектура** — из каких компонентов собрать систему, как она работает и как будет расти.
6. **Solution** — на каких технологиях сделать.
7. **ПМИ** — как проверим, что требования выполнены (до кода).
8. **Код** — курсовая по БД.

**Сквозная история:** бронирование → оплата → билет → проход (или возврат). **Изюминка:** одно место — один билет даже при одновременной покупке.

### Слова, в которых легко запутаться

- **Декларативная модель** (ER). От «декларировать» — объявлять, констатировать. Описывает, *что существует* и как связано, без действий и порядка: «билет входит в заказ», «место принадлежит зоне». Противоположность — модели действий (DFD, BPMN): «покупатель отправляет заявку, система проверяет места…». Аналогия: SQL декларативен (говоришь, *что* получить), цикл на Python — нет (говоришь, *как*). Преподаватель 04.11: «БД и программные компоненты вместе отражают декларативные и процедурные знания» о предметной области.
- **Сущность в ER и внешняя сущность в DFD — разные вещи.**
  - В ER сущность — объект данных: Билет, Заказ, Место.
  - В DFD внешняя сущность — участник вне системы: Покупатель, Контролёр, Платёжный сервис.
  - Функции на DFD — это функции **системы**, а не сущностей.
- **Документ** — порция информации, которая идёт по стрелке DFD: «Заявка на бронирование», «Билеты», «Счёт на оплату», «Отчёт». Не обязательно бумага, это может быть запрос в API. На каждой стрелке должно стоять имя документа (существительное), иначе «схема не полная».
- **Связь ER и DFD через документы.** Документ состоит из полей, а поля — это атрибуты ER. «Заявка на бронирование» = мероприятие + места + ФИО держателей + промокод + контакты (таблица «Состав документов», раздел 2.3.5). Хранилища DFD содержат сущности ER.

### Откуда что берётся в архитектуре

Если спросят «откуда взялись компоненты?»:
- **Компоненты** — из BPMN, из дорожки «Части комплекса программ» (в ВКР — «части КПП»). Преподаватель: «за каждой группой операций стоит программный компонент, который работает с конкретной БД в отношении конкретного документа».
- **Базы данных** — из хранилищ DFD (а в них — сущности ER).
- **Элементы окружения** — из внешних сущностей DFD.
- **Связи** — из документов DFD.

### Правило доклада

Это правило **про то, как рассказывать** на показе и защите, а не про этапы проекта. Порядок: **назначение → функции → устройство**.
1. Сначала зачем система и для кого.
2. Потом что она делает: контекстная диаграмма, DFD.
3. Потом как устроена: ER, BPMN, архитектура, Solution.

Перед каждой схемой — одна фраза о том, как её читать. Команду «гостиниц» он ругал за то, что те начали с устройства и не объяснили значки.

### Вопросы для самопроверки

1. Чем ER отличается от DFD? **Ответ:** ER — какие данные есть и как связаны (статично), DFD — что делает система и какие документы между кем идут.
2. Почему ПМИ до кода? **Ответ:** проверки выводятся из требований, а не из готового кода. Иначе тесты подгоняются под реализацию. У каждого требования уже есть метод проверки.
3. Откуда компоненты архитектуры? **Ответ:** из дорожки «Части комплекса программ» в BPMN. Базы — из хранилищ DFD, окружение — из внешних сущностей DFD.

> **Уточнение к ЖЦ.** Проект — временная работа по созданию (или изменению) системы, заканчивается приёмкой. Система живёт дольше: эксплуатация, **сопровождение** (стадия 8 ГОСТ 34.601-90), вывод из эксплуатации — это уже после закрытия проекта; крупная доработка в сопровождении — новый проект. ## Шаг 1. Описание предметной области и процесса

Файл: `docs/01-description.md`.

### Зачем

Это фундамент. Цепочка преподавателя: **определение процесса → правила → сущности и ограничения**. Каждая схема дальше показывает эти правила: ER хранит данные для них, DFD и BPMN их выполняют, БД их проверяет, ПМИ их испытывает. Без описания непонятно, *что* моделировать: схемы рисовались бы «из головы».

### Что внутри (по порядку)

1. **Назначение** — одна фраза: продать места так, чтобы каждое место было продано не более одного раза, покупатель получал билет или понятный отказ, а проходили только по действительному билету.
2. **Проблема без системы** — по каждому участнику (двойная продажа, ручные возвраты, поддельные билеты, ручной ввод схем залов).
3. **Участники** (таблица «кто — что нужно — что делает — что получает»):
   - Покупатель, Организатор (менеджер), Контролёр, Администратор сервиса — **роли одного Пользователя**: один человек может иметь несколько ролей;
   - **Платёжный сервис** — внешняя система, не наша, поэтому вне границы.
4. **Определение процесса** по ГОСТ Р 57098-2023 (название, цель, основные результаты). Цель: каждое место — не более одного действующего билета, деньги и билеты соответствуют, проход — только по действительному билету.
5. **Сценарии S1–S9** — с несколькими исходами: успех и отказы.
6. **Правила R01–R23** — из них выводятся сущности и ограничения.
7. **Словарь сущностей** — будущая ER (и у каждой сущности — правила, которые её требуют).
8. **Границы** — что внутри, что снаружи (платёжный сервис), что вне объёма (перепродажа, лист ожидания…).

### Главные правила (помнить)

| Правило | Суть | Где потом |
|---|---|---|
| R01 | одно место на мероприятии — не более одной действующей брони или билета | ограничение уникальности в БД, конкурентный тест К-01 |
| R02 | бронь держит места 15 минут | таймер в BPMN, планировщик K10 |
| R07 | заказ: бронь → оплачивается → оплачен; «не списано» — снова бронь; бронь → истёк по сроку; «оплачивается» по сроку не снимается — место держится до ответа банка | автомат состояний (триггер) |
| R08 | цена и скидка фиксируются в каждом билете при оформлении, сумма к оплате вычисляется | исправление ЛР 2 |
| R13 | по билету не более одного прохода | связь 1:1 «Билет — Проход» |
| R16 | возврат от оплаченной стоимости: ≥ 10 суток — 100 %, 5–10 — 50 %, 3–5 — 30 %, < 3 — нет; отмена мероприятия — 100 % (ст. 52.1 Основ законодательства о культуре, постановление № 1491) | функция возврата, граничные тесты |
| R17 | отмена мероприятия возвращает все билеты одной операцией | транзакция + распоряжения «ожидает» |

### Что может спросить преподаватель

- *Зачем определение процесса?* — Из него выводятся правила, из правил — сущности и ограничения. Это первое звено цепочки.
- *Почему пользователь один, а ролей четыре?* — Роли одного физического лица объединяются в одну сущность (его же правило); роль — атрибут связи «работает в организаторе».
- *Почему платёжный сервис — внешняя сущность?* — Это чужая система, мы только обмениваемся с ней документами (счёт, результат оплаты, распоряжение на возврат).
- *Что будет, если двое одновременно купят одно место?* — По R01 бронь получит только первый, второму — «место занято». Это обеспечивает сама БД (уникальность места среди действующих билетов).
- *Чем правило отличается от требования?* — Правило — про предметную область (как должно быть). Требование — что для этого должна делать система (FR-…), со ссылкой на правило и методом проверки.
- *Почему 15 минут?* — Компромисс: покупатель успевает оплатить, места не заблокированы надолго. Это допущение, его легко поменять.

Назначение — продать места так, чтобы каждое место было продано один раз, покупатель всегда получал билет или понятный отказ, а на вход пускали только по действительному билету. Участники — покупатель, организатор, контролёр, администратор сервиса и внешний платёжный сервис. Процесс описан по ГОСТ Р 57098: название, цель и основные результаты. Из процесса и сценариев выведено 22 правила — например, одно место — один билет, бронь держится 15 минут, возврат зависит от срока до начала. Из этих правил дальше получаются сущности ER, функции и ограничения базы данных».

### Вопросы для самопроверки

1. Назови участников. Почему Платёжный сервис — участник, а не часть системы?
2. Откуда берутся правила и куда они потом идут?
3. Что будет по правилам, если покупатель оплатил через 20 минут после брони?

### Разбор вопросов по шагу 1

- **Организатор** — юрлицо, которое проводит мероприятия (концертное агентство и т. п.). В системе работают его сотрудники с ролями:
  - **менеджер** — заводит, публикует и отменяет мероприятия, выпускает промокоды, смотрит отчёты, назначает роли другим сотрудникам;
  - **контролёр** — только сканирует билеты на мероприятиях своего организатора.

  Роли нужны для правила R19: контролёр не меняет мероприятия, чужой организатор не видит чужих данных. Порядок: администратор регистрирует организатора и первого менеджера, менеджер добавляет сотрудников (по email уже зарегистрированного пользователя).
- **Площадки — справочник сервиса.** Администратор заводит площадку, её зал, зоны, места и входы. Организатор при создании мероприятия выбирает площадку из каталога, система проверяет, что она свободна в это время. Владельца площадки и договоры аренды мы **не моделируем** — это допущение: для продажи мест нужна схема зала, а отношения «владелец — организатор» к продаже билетов не относятся. Если спросят: «владелец площадки — вне границы системы, договорённости с ним организатор ведёт сам; в развитии можно добавить роль представителя площадки».
- **Окно продаж** — период, когда билеты можно покупать: «начало продаж» (например, 1 декабря 10:00) и «конец продаж» (например, за час до начала). Вне окна бронь отклоняется: «продажи закрыты» (R03).
- **Администратор поддерживает площадки и схемы залов** — ведёт справочники для всех организаторов: заводит площадки, загружает схемы залов, исправляет их, если зал перестроили, регистрирует организаторов.
- **Бронирование — «заморозка» мест.** Покупатель выбирает места и отправляет заявку: места, ФИО держателей, промокод, контакты. Система одной операцией:
  1. проверяет, что продажи открыты, места свободны, а промокод действителен;
  2. создаёт заказ «бронь» до «сейчас + 15 минут» и билеты «зарезервированы».

  Для остальных покупателей эти места сразу показываются занятыми. Зачем: покупателю нужно время на оплату, а без брони двое оплачивали бы одно место. Не оплатил за 15 минут — планировщик снимает бронь, места освобождаются.
- **Платёжный сервис** (ЮKassa, CloudPayments и т. п.) принимает карты вместо нас: самим принимать карты нельзя без банковских договоров и сертификации (PCI DSS). Как это работает:
  1. Мы создаём **счёт**: сумма, номер заказа, срок — до конца брони. Счёт **двухстадийный**: сервис сначала только **блокирует** сумму на карте (так делают отели и каршеринг).
  2. Сервис даёт ссылку на свою платёжную страницу, покупатель вводит карту **у сервиса** (рыжая стрелка «вне системы» на контекстной диаграмме).
  3. Сервис присылает нам **уведомление** (webhook) «сумма заблокирована / отклонено» с подписью.
  4. Мы проверяем подпись и записываем платёж. Если бронь ещё действует — заказ «оплачивается», и мы **подтверждаем списание**.
  5. Сервис отвечает «списано» — только теперь заказ «оплачен» и выдаём билеты с кодами. Ответил «не списано» — билетов нет, заказ снова в брони, платёж отменён, блокировка снята, покупателю отказ; пока бронь действует, можно оплатить снова (FR-27).
  6. Если бронь уже истекла — **отменяем списание**: блокировка снимается, деньги покупателя не списываются (R22). Повторное уведомление не создаёт второй платёж (R10): сервисы присылают его повторно при сбоях.

  В проекте вместо реального сервиса — эмулятор.
- **Загрузка схемы зала одним файлом.** В зале сотни и тысячи мест: только в ЛР у нас 3810 мест на трёх площадках. Вводить их по одному долго и ошибочно. Администратор загружает CSV (зона, ряд, номер), система проверяет каждую строку: нет повторов, номер не пустой. Корректные строки принимает, ошибочные возвращает в протоколе. Заодно это закрывает требование курсовой по БД о «пакетной загрузке с валидацией и обработкой ошибок» (п. 2.2).
- **Правило, функциональное и нефункциональное требование:**

  | | Отвечает на вопрос | Пример |
  |---|---|---|
  | Правило | как устроена предметная область (верно и для кассы с бумажными билетами) | R01 «одно место — один билет»; R16 «за 3–10 суток — 50 %» |
  | Функциональное требование (FR) | **что** должна делать система, чтобы правила выполнялись | FR-05 «при заявке на бронь удержать места на 15 минут или отказать с причиной» |
  | Нефункциональное требование (NFR) | **насколько хорошо**: скорость, надёжность, безопасность, удобство (характеристики качества ГОСТ Р ИСО/МЭК 25010) | NFR-01 «ответ на бронь ≤ 300 мс при 50 одновременных клиентах»; NFR-05 «пароли не в коде» |

  У каждого требования есть номер, источник (правило или сценарий) и способ проверки — отсюда потом ПМИ.
- **Откуда правила и куда идут.** Цепочка: процесс и сценарии → правила → и **сущности и ограничения ER** (какие данные нужны правилу), и **требования FR** (что делать системе) → проверки ПМИ.
- **Оплата через 20 минут.** Бронь уже истекла (R02, 15 минут), места освобождены и, возможно, куплены другими. Обычно оплатить и не получится: счёт действует только до конца брони. Если оплата всё же пришла (покупатель нажал «оплатить» в последнюю секунду, уведомление опоздало) — R22: сумма только заблокирована, поэтому система отменяет списание, билеты не создаются, деньги не списываются, покупатель получает «Итог покупки (отказ: бронь истекла)».

## Шаг 2. ER-диаграмма (декларативная модель, нотация Чена)

> **18.11 переделано по отзыву преподавателя 13.11.** Он сказал: предметная область одна, значит, и диаграмма должна быть одна (не «общий лист + подробные»), а показатели качества — часть той же ER («в двух кусочках… обозначить, что всё это хранится вот там»). Теперь ER — одно полотно: внизу в синем контуре то, что хранится в БД, сверху в коричневом — система оценивания качества (программа, функции, частные критерии, показатели, качество). Мостик между частями — «Пользователь *пользуется* Программой». Разбор ниже про сущности и связи предметной области по-прежнему верен.

Файлы: `docs/img/er.png` — одна диаграмма (с 18.11, по замечанию преподавателя 13.11: «документ должен быть единый»): предметная область в синем контуре «хранится в БД» и система оценивания качества в коричневом; пояснение — `docs/02-models.md` §2.2.

### Зачем

ER отвечает на вопрос **«какие данные нужно хранить, чтобы правила выполнялись»**. Без неё неизвестно, что лежит в базе и как связано, и DFD нечем проверить: документы состоят из атрибутов ER. Преподаватель: «ER нельзя считать полной без модели функционирования, и наоборот».

### Как читать

- **Прямоугольник** — сущность (16 шт.): Площадка, Зона зала, Место, Вход, Мероприятие, Организатор, Пользователь, Артист, Продаваемая зона, Промокод, Заказ, Билет, Платёж, Возврат, Проход, Попытка сканирования.
- **Ромб** — связь с кодом и глаголом (24 шт., r01–r24), читается предложением: «Площадка *делится на* Зоны зала», «Заказ *включает* Билеты».
- **Числа у линий** — максимальная кратность. «Заказ 1 — включает — N Билет»: в заказе много билетов, билет — в одном заказе.
- **Овал** — атрибут (листы 2–4); ключ подчёркнут. Внешние ключи атрибутами не рисуются — их задают связи.
- На подробных листах сущности с других листов показаны пунктиром.

### Что помнить

- **1:1** — r16 «Билет возвращается» (Возврат) и r17 «Билет погашается» (Проход): у билета не больше одного возврата и одного прохода (R13, R15).
- **M:N** — r05 организаторы мероприятия, r06 сотрудники организатора с атрибутом связи **«Роль»** (менеджер / контролёр), r07 артисты мероприятия.
- **Продаваемая зона** — ассоциативная сущность «Мероприятие × Зона зала» с ценой: цена зависит от пары (партер на концерте и на фестивале стоит по-разному).
- **r23** «Организатор выпускает Промокод» — промокод действует только на его мероприятия (R21).
- **Пользователь** — одна сущность для всех ролей одного человека.
- Самосвязей нет.

**ER и физические таблицы** (курсовая по БД): 16 сущностей + 3 таблицы для M:N (`event_organizers`, `organizer_members`, `event_artists`) = 19 содержательных таблиц + служебные (аудит, загрузка). Продаваемая зона = `event_zones` из ЛР.

### Что может спросить преподаватель

- *Почему Продаваемая зона — отдельная сущность?* — Цена зависит не от мероприятия и не от зоны по отдельности, а от пары; по ней же билет проверяет, что зона продаётся на это мероприятие.
- *Почему Возврат и Проход — отдельные сущности, а не поля билета?* — У них свои данные (сумма, причина, время, вход, контролёр), и это естественные 1:1: у билета их может не быть.
- *Где статус заказа?* — Атрибут «Статус» у Заказа; переходы (бронь → оплачен / истёк / отменён) — правило R07, в БД это проверит триггер.
- *Почему роль — атрибут связи, а не пользователя?* — Один человек может быть менеджером в одном агентстве и контролёром в другом.
- *Как ER связана с DFD?* — Хранилища DFD содержат сущности ER, а каждый документ DFD состоит из атрибутов ER (таблица «Состав документов»); скрипт проверяет, что каждый атрибут приходит в каком-то документе или формируется системой.

### Речь на минуту

«Декларативная модель — одна диаграмма Чена из двух частей. Внизу, в контуре базы данных, — предметная область: шестнадцать сущностей и двадцать четыре связи, каждая связь читается предложением, например „Заказ включает Билеты“. Основа — Билет: он входит в Заказ, занимает Место и даёт право на Продаваемую зону. У билета не более одного Возврата и одного Прохода — связи один к одному. Сверху — система оценивания качества: пользователь пользуется программой, программа выполняет функции, у каждой функции свой частный критерий удовлетворённости, он вычисляется из показателей, а качество программы складывается из этих критериев. Эти же показатели потом измеряются в испытаниях».

### Разбор вопросов по шагу 2

- **Артист.** Исполнитель — человек или коллектив, поэтому один атрибут «Название (имя, псевдоним или коллектив)». Жанр убран: в сервисах афиши категорию задают **мероприятию** (концерт, спектакль, фестиваль, стендап), а не исполнителю — у мероприятия появился атрибут «Категория», по нему фильтруется афиша.
- **Вход** — физический вход площадки («Вход 1», «VIP-вход»), принадлежит площадке (r03). С мероприятием напрямую не связан: на площадке в одно время идёт одно мероприятие (FR-03 — площадка не занята), значит, все её входы в это время работают на него. Контролёр при сканировании указывает мероприятие и вход, система проверяет, что вход — с площадки этого мероприятия (R14). Привязка «VIP-вход только для VIP-зоны» — вне объёма (развитие).
- **Тип зоны (сидячая / стоячая)** — то же, что в ЛР 2: у мест стоячей зоны ряда нет, номер — входной слот. Тип делает это явным: загрузка проверяет, что у сидячей зоны ряд указан, а у стоячей — нет; для стоячей зоны покупатель выбирает не место, а количество, система берёт первые свободные слоты.
- **Сумма в заказе была лишней** — замечание верное. В ЛР 2 `total_price` убрали как вычисляемое значение; ошибкой было только то, что скидка бралась из текущего промокода. Исправлено: цена и скидка — в каждом **билете** (факты на момент оформления), сумма к оплате = Σ (цена − скидка) вычисляется.
- **Платёж и заказ.** Заказ создаётся при брони со статусом «бронь», платежа ещё нет. Платёж появляется, когда приходит результат от платёжного сервиса, и ссылается на заказ (r15: у заказа может быть несколько попыток — первая отклонена, вторая прошла). Сумма в платеже — **не дублирование**: это факт от внешнего сервиса, сколько реально списано. Её сверяют с суммой к оплате, при расхождении — отказ `AMOUNT_MISMATCH`.
- **Новые сущности после ЛР 2:**

  | Сущность | Что это | Зачем |
  |---|---|---|
  | Вход | вход площадки | на каком входе прошли (R14) |
  | Проход | успешное погашение билета, 1:1 с билетом | гарантия «один проход на билет» (R13) |
  | Попытка сканирования | каждое сканирование: удачное, повторное, чужой или неизвестный код | журнал для разбора споров и аналитики, ≥ 100 000 строк для курсовой |
  | Платёж | попытка оплаты заказа от платёжного сервиса | факт оплаты, идемпотентность (R10) |
  | Возврат | распоряжение на возврат денег за билет, 1:1 с билетом | сумма по правилу R16, статус «ожидает → проведено» |
  | Роль в связи «работает в» | менеджер / контролёр | права (R19) |
  | Связь «Организатор выпускает Промокод» | промокод принадлежит организатору | R21 |

- **Почему и Проход, и Попытка.** Попытка — любая, в том числе неудачная или с неизвестным кодом (тогда билета нет). Проход — только успешная, и ровно одна на билет (уникальность в БД). Глаголы связей поправлены, чтобы читались предложением: «Пользователь (контролёр) **выполняет** попытку сканирования», «Пользователь **разрешает** проход».

> **Дыры, найденные при разборе шага 2 (исправлено):**
> - у артиста был жанр → «Название (имя, псевдоним или коллектив)», категория — у мероприятия;
> - «Сумма к оплате» хранилась в заказе (вычисляемое значение) → убрана, хранится только скидка;
> - глаголы r19 и r22 не читались предложением → «разрешает», «выполняет».

- **Без Прохода можно обойтись?** Можно — частичным уникальным индексом по успешным попыткам. Отдельная сущность оставлена сознательно: попытки — большой журнал (в развитии делится по месяцам и чистится по сроку хранения); в разбитой по месяцам таблице PostgreSQL не обеспечит «один проход на билет» обычным уникальным индексом, а ссылка прохода на попытку не дала бы удалять старый журнал. Проход — бизнес-факт в маленькой таблице с простой уникальностью по билету. Цена — осознанное дублирование входа, контролёра и времени.
- **Возврат и платёж.** Возврат — распоряжение вернуть деньги за один билет. Теперь он ссылается и на билет (r16, 1:1), и на **платёж** (r24, 1:N): у заказа может быть несколько попыток оплаты, деньги возвращаются по той, что прошла. Проведён ли возврат — статус «ожидает → проведено», меняется по подтверждению платёжного сервиса. Сумма возвратов по платежу не больше суммы платежа (R23, триггер).
- **Координаты** разбиты на широту и долготу: одно поле с двумя значениями нарушало 1НФ (в ЛР 1 тоже два столбца).

> **Дыры (исправлено):** возврат не был связан с платежом → r24 и правило R23 (FR-25, проверка Б-06); координаты одним атрибутом → широта и долгота.

- **Нет ли аномалий из-за повторов?** Аномалии бывают, когда *один и тот же изменяемый факт* лежит в нескольких местах. У нас каждый повтор либо другой факт, либо неизменяем, либо защищён ограничением — это «обоснованная денормализация», её описываем в ПЗ по БД:

  | Повтор | Почему не аномалия |
  |---|---|
  | вход, контролёр, время в Попытке и Проходе | создаются одной функцией в одной транзакции и никогда не меняются; удаление старого журнала проходы не трогает — так задумано |
  | сумма Платежа и сумма к оплате | разные факты: сколько списал банк и сколько должны были; расхождение → `AMOUNT_MISMATCH` |
  | цена Билета и цена Продаваемой зоны | цена билета — исторический факт на момент покупки |
  | зона в Билете при известном месте | денормализация из ЛР 2, согласованность гарантирует составной FK (место, зона) |

- **Возврат одного билета из заказа.** Так работают реальные сервисы (один из четверых не может пойти), а банки поддерживают **частичные возвраты** по платежу — несколько, пока их сумма не превысит платёж (наше R23). Вернуть весь заказ = вернуть каждый билет; при отмене мероприятия система делает это сама.
- **Сумма возврата — от оплаченной стоимости билета:** цена минус скидка билета. Иначе при промокоде вернули бы больше, чем заплатили.

> **Дыры (исправлено):** возврат считался от полной цены билета, без учёта скидки → R16, FR-12, Ф-13, `refund_ticket`; у афиши не было фильтра по категории → API02; в ПМИ не проверялось, что администратор не назначается через API и пароли хранятся хэшем → З-01, З-02.

- **Где «сумма к оплате».** Она **не хранится**, а вычисляется: Σ (цена − скидка) билетов заказа. Видна в P09 «Бронь» (покупателю) и P10 «Счёт на оплату» (платёжному сервису). Сумма из результата оплаты (P11) записывается в Платёж и сравнивается с вычисленной; расхождение → `AMOUNT_MISMATCH`.
- **Цена и скидка — в билете.** Цена — полная цена зоны на момент покупки. Скидка — доля скидки по промокоду, распределённая по билетам заказа пропорционально цене **один раз при оформлении** (копейки округления — на последний билет). В заказе скидка не хранится: она = Σ скидок билетов. Хранить её и в заказе, и в билетах было бы дублированием (суммы обязаны совпадать, а БД это не гарантирует). Почему именно в билете: так в кассовом чеке (54-ФЗ) каждая позиция идёт с ценой с учётом скидки; распределение и округление делаются один раз; возврат одного билета = цена − скидка этого билета; отчёту не нужно распределять скидку заново.
- **Правило возврата по закону** (R16): не позднее чем за 10 суток — 100 %; за 5–10 — 50 %; за 3–5 — 30 %; менее 3 — не возвращается; отмена мероприятия — 100 %. Основание — ст. 52.1 Основ законодательства РФ о культуре и Правила возврата (постановление Правительства РФ от 18.09.2020 № 1491). Номер постановления сверен поиском, текст закона перед финалом — сверить в КонсультантПлюс.

### Ответы на вопросы шага 2

1. **r14 «Место занимается Билетом», 1 : N.** На одно место за всё время много билетов: прежде всего на **разные мероприятия** в этом зале, а ещё после возврата место продаётся снова. Но в один момент на одно мероприятие — не больше одного действующего (R01, проверяет БД).
2. **Проход 1:1.** Верно: проход фиксирует, что билет использован, и по R13 он может быть только один. Со стороны билета связь необязательна: билет может быть не использован.
3. **Таблиц больше, чем сущностей.** Верно: каждая связь M:N (организаторы мероприятия, сотрудники организатора, артисты) становится отдельной таблицей — 16 + 3 = 19.

## Шаг 3. Модель функционирования (DFD)

> **18.11 дополнено по отзыву преподавателя 13.11.** Дерево функций раскрыто до листьев: лист — «спросили — ответили», один вход и один ответ, у каждого листа указана спецификация (процесс BPMN или таблица листьев). Добавлена **ДПД уровня 2 для одной функции — F3 «Оплата»** («для одной какой-то функции… только для одной»): четыре подфункции, на границе те же документы, что в строке F3 на ДПД-1, — баланс уровней. Контекстная диаграмма принята («допускается, я готов с этим мириться»).

### Зачем

DFD отвечает на вопрос **«что делает система и какие документы между кем идут»**. ER говорит, какие данные *есть*, а DFD — как они *появляются и используются*. Формула преподавателя: **модель функционирования = контекстная диаграмма + дерево функций + диаграммы потоков данных**. Нотация — Гейна–Сарсона.

### Как читать

- **Контекстная диаграмма (уровень 0):**
  - в центре одна функция F0 «Продажа билетов и контроль входа на мероприятия» — почти дословно тема;
  - вокруг пять внешних сущностей E1–E5;
  - 29 стрелок, на каждой документ с кодом P01–P29;
  - внутреннего устройства и БД не видно: система показана целиком;
  - рыжая пунктирная линия — оплата картой между покупателем и платёжным сервисом **вне** системы, на уровень 1 не переносится.
- **Дерево функций:** F0 → F1…F6. С 18.11 дерево раскрыто до листьев: лист — «спросили — ответили», под ним «вход → ответ». Листья покупки (F2, F3) описаны процессами BPMN, остальные — таблицей листьев (§2.3.2). Имена функций — отглагольные существительные («Учёт…», «Бронирование…»).
- **ДПД уровня 1:**
  - у каждой функции своя строка: слева её внешние сущности, в центре функция, справа её хранилища; все стрелки горизонтальные;
  - если сущность или хранилище нужны нескольким функциям, они повторены в строке каждой из них. Знак повтора по Гейну–Сарсону: косая черта в углу внешней сущности, вторая черта у номера хранилища;
  - синяя стрелка — **запрос** к хранилищу (Q), зелёная — **ответ** (A): преподаватель требует рисовать их отдельно;
  - фиолетовые — внутренние потоки: I01 «Сведения об отмене мероприятия» (F1 → F4), I02 «Бронь к оплате» (F2 → F3).

### Что может спросить преподаватель

- *Почему на контекстной диаграмме нет БД?* — Это нулевой уровень: система — одна функция, её устройство (в том числе хранилища) скрыто. БД появляется на уровне 1.
- *Что такое баланс и как вы его проверили?* — При раскрытии функции граничные потоки сохраняются по числу, направлению и названию. У нас 15 / 14 на обоих уровнях; проверяет скрипт `check.py`.
- *Почему запрос и ответ — отдельные стрелки?* — Это разные документы: запрос «Бронь мест» и ответ «Квитанция брони или отказ „место занято“». Так видно, что функция получает от хранилища.
- *Почему хранилища именно такие?* — Хранилище ставится на том уровне, где оно нужно двум и более функциям; D1–D4 нужны нескольким функциям, поэтому они на уровне 1.
- *Что за I01?* — При отмене мероприятия F1 передаёт сведения в F4, а F4 возвращает все билеты.
- *Почему бронирование и оплата — разные функции?* — Разные документы и участники: бронь — с покупателем, оплата — с платёжным сервисом. Есть таймер: бронь может истечь без оплаты.
- *Почему у вас четыре БД, а не одна?* — D1–D4 — логические хранилища, группы данных по смыслу; физически это одна база PostgreSQL. Так видно, какая функция с какими данными работает и кто владелец каждого хранилища.
- *Что это за документ, из каких полей, откуда они?* (про любую стрелку DFD) — Открыть карточку документа по коду в `docs/generated/doc-cards.md`: зачем он, на что отвечает, что запускает, какие правила проверяются, и по каждому полю — куда пишется или откуда берётся. Ответ строится по газетному анализу: «документ в систему — куда записываем; из системы — откуда берём; у каждого атрибута ER есть источник».
- *Где вход в систему?* — Это техническая функция API-шлюза, не меняет данных предметной области, поэтому на DFD не показан (записано в границах системы).
- *Откуда F4 знает, сколько дней до мероприятия?* — Читает начало мероприятия из D1 (Q19), процент считает по R16.
- *Как F5 проверяет, что контролёр «свой» и вход с той площадки?* — Читает D1 (Q20): вход площадки, окно входа, сотрудники организатора. Потом погашает билет в D2 (Q10) и пишет проход в D4 (Q11) — одна транзакция.
- *Если оплата пришла после истечения брони, кто вернёт деньги?* — Возвращать нечего: оплата двухстадийная, сумма только заблокирована. Система отменяет списание (P27), блокировка снимается.
- *Организатор отменил мероприятие — что он получает?* — P04 «Уведомление о статусе мероприятия» со статусом «отменено» (тот же документ, что при публикации).

### Разбор вопросов по шагу 3

- **FR и NFR — на этом этапе?** Да. Стадия 2 курса так и называется: «функциональные требования и концепция применения». В неё входят требования, ER, DFD и BPMN. Требования (`docs/02-requirements.md`) включены в главу 2 записки. Связь с DFD — столбец «Функция» у каждого FR: например, FR-05 выполняет F2. Получается, что функция DFD — это группа требований, которые она выполняет. NFR (скорость, защита) на DFD не видны: они уходят в архитектуру, Solution и ПМИ.
- **Какие файлы относятся к DFD:**
  - текст — `docs/02-models.md` §2.3;
  - схемы — `docs/img/dfd-0-context.png`, `dfd-tree.png`, `dfd-1-level1.png`;
  - таблицы, которые генерирует скрипт, — `docs/generated/flows-ext.md` (P), `flows-int.md` (I), `db-pairs.md` (Q/A), `balance.md`, `doc-fields.md` (состав документов);
  - источник — раздел DFD в `tools/model.py`.

  Вся стадия 2 — это ещё `er-*`, `bpmn-*`, требования и матрица согласования `matrix.md`.
- **Документ** — именованная порция сведений, которую один участник передаёт другому, как бумажный бланк. Например, «Заявка на бронирование» состоит из полей: мероприятие, места, ФИО держателей, промокод, контакты (§2.3.5). На стрелке пишут название бланка, а не «данные».
- **Баланс.** Когда F0 раскрывают на F1–F6, внешний мир не меняется. На границе системы остаются те же стрелки, с теми же названиями и направлениями; меняется только то, к какой функции они подходят. Пример — платёжный сервис E5:
  - на контексте он получает P10, P27, P15 и отправляет P11, P16;
  - на уровне 1 у него те же пять стрелок: P10, P27, P11 подходят к F3, а P15, P16 — к F4.

  Добавить на уровне 1 новую стрелку к E5 нельзя, потерять тоже. Это как «чёрный ящик» с 27 проводами: открыл крышку — видишь те же провода, только они подключены к разным внутренним блокам. Внутренние стрелки (I, Q/A) появляются только внутри и в баланс не входят.
- **Для чего эта стадия.** Это не сценарии. Сравнение трёх моделей:

  | Модель | Отвечает на вопрос | Слова |
  |---|---|---|
  | ER | что система помнит | существительные: Заказ, Билет |
  | DFD | что система делает, какими документами обменивается и где их держит; времени, порядка и «если» нет | глаголы: бронирование, оплата |
  | BPMN | в каком порядке и с какими ветвлениями | сценарий во времени |

  Аналогия — касса до компьютеров. Кассир (функция) получает от покупателя бланк заявки, смотрит в папку со схемой зала (хранилище), записывает бронь в журнал и отдаёт квитанцию. DFD рисует ровно это: людей, бланки, «столы» и «шкафы».
- **Откуда берётся DFD.** ER вырастает из правил («что запомнить»), а DFD — из участников и сценариев («кто что с кем делает»):
  - участники (§1.4) → внешние сущности E1–E5;
  - сценарии → функции: S1, S8, S9 → F1; S2 → F2; S3 → F3; S4, S5 → F4; S6 → F5; S7 → F6;
  - каждый шаг сценария, где участник что-то отдаёт или получает, → документ P;
  - сущности ER, сгруппированные по тому, кто ими пользуется, → хранилища D1–D4;
  - правила → какие данные функция должна прочитать (пары Q/A). Именно здесь были дыры шага 3.

  ER и DFD встречаются в хранилищах: каждое хранилище — группа сущностей ER, а у каждой пары Q/A записано, какие сущности и связи она затрагивает.
- **Коды:**
  - E1–E5 — внешние сущности: Покупатель, Организатор, Контролёр, Администратор сервиса, Платёжный сервис;
  - F0 — вся система, F1–F6 — функции;
  - D1–D4 — хранилища: участники, площадки и мероприятия; заказы и билеты; платежи и возвраты; журнал проходов;
  - P01–P29 — внешние документы, они пересекают границу системы. Например, P08 «Заявка на бронирование» идёт E1 → F2;
  - I01, I02 — внутренние документы между функциями;
  - Q/A — пара с одним номером: Q04 «Бронь мест» (F2 → D2) и A04 «Квитанция брони или отказ „место занято“» (D2 → F2).

  Коды не переиспользуются. Зачем они нужны: по одному коду документ находится во всех стадиях. P11 «Результат оплаты» — стрелка DFD, сообщение BPMN, связь X19 в архитектуре, API10 в Solution, проверка Ф-06 в ПМИ.
- **Стрелки на дереве функций:**
  - сплошные линии — «состоит из»: F0 делится на шесть функций;
  - пунктир к листку — «описана в»: у каждого листа (функции, которую дальше не делят) должна быть спецификация, то есть описание того, как функция работает внутри.

  Спецификация бывает одной из двух форм, обе для одного листа не нужны:
  - **BPMN** — если в работе есть порядок, ветвления, ожидание, таймер, повторы, обмен с несколькими участниками (F2 + F3, F4, F5);
  - **текст** — если функция — набор простых независимых операций «получил → проверил → записал → ответил» (F1 — пять таких операций; F6 — прочитать четыре хранилища и собрать отчёт).

  Признак: описывается тремя-четырьмя строками без «если», «ждать», «повторять» — текст; иначе BPMN. Если функция слишком сложная, её не описывают, а раскрывают дальше в ДПД уровня 2, и она перестаёт быть листом.

  **Решение 13.11 (отменено 18.11 по отзыву преподавателя: процессы нужны для 2–3 функций):** F1 и F6 тоже описаны BPMN (BP4, BP5, BP6). По правилу текста хватило бы, но преподаватель говорил «функция — процесс» и сверяет число обращений к БД в BPMN и DFD: теперь в BPMN видны все пары (сейчас 24), без оговорок.
- **Читаемость.** КД и ДПД-1 перерисованы по образцу одногруппников (`tools/dfd_svg.py`), BPMN — так же вручную (`tools/bpmn_svg.py`):
  - стрелки только горизонтальные, F0 — большой прямоугольник в центре;
  - на уровне 1 у каждой функции своя строка, повторы помечены знаками Гейна–Сарсона;
  - I02 — короткая вертикаль между F2 и F3, I01 идёт каналом слева от функций;
  - в BPMN стрелки прямые, БД стоит прямо под своим действием; путь покупателя показывает, кто кого вызывает.

### Разбор вопросов по шагу 3 (второй круг)

- **Одна БД или четыре хранилища?** Хранилище на DFD — логическая группа данных («папка в шкафу»), а не отдельная СУБД. Физически база одна (PostgreSQL), а D1–D4 — четыре группы её таблиц. Так записано и в архитектуре (решение A2): одна физическая база нужна, чтобы бронь, оплата и билеты шли одной транзакцией.
  - Преподаватель сам рисовал на доске несколько смысловых хранилищ («БД раб.», «БД Заяв.», 16.10). 04.11 он сказал: «по сути база одна… это больше семантически… физически потом ляжет на одну».
  - Одногруппники взяли одну D0: так проще рисовать. Но тогда ко всем функциям идёт одна и та же D0, и по схеме не видно, кто с какими данными работает. У нас видно: F5 не трогает платежи, F6 только читает.
  - Правило «хранилище там, где оно нужно двум и более функциям, и у него есть владелец» с одной D0 выполняется только формально. У нас у каждого хранилища есть владелец, то есть функция, которая его ведёт: D1 — F1, D2 — F2, D3 — F3 и F4, D4 — F5.
  - Хранилища дальше становятся группами данных архитектуры, а `check.py` сверяет, что сущности каждой пары Q/A лежат в её хранилище.

  Минус разделения — больше стрелок и повторов. Вывод: оставляем D1–D4.
- **КПП — это просто «наша программа».** Сокращение взято из ВКР, которую консультировал преподаватель (слайд 18): «Петелька» — сайт вязаных изделий на заказ.
  - Её BPMN-схема называется «Работа с комплексом программ „Петелька“». Комплекс программ — это программа, собранная из нескольких частей (термин ЕСПД, ГОСТ 19.101).
  - Средняя дорожка называется «Дорожка частей КПП», то есть «дорожка частей комплекса программ», — дорожка, где стоят **части программы**: «клиентская часть для заказчика», «модуль расчёта», «почтовый клиент», БД. Расшифровки «КПП» на слайде нет; скорее всего, это «комплекс программ „Петелька“».
  - Зачем такая дорожка: в ней видно, **какая часть программы** выполняет каждое действие и с какой БД работает. Из этих частей потом получаются компоненты архитектуры.
  - У нас эта дорожка называется **«Части комплекса программ»** — без непонятного сокращения. В ней действия системы, у каждого — компонент: «Проверка условий продажи и мест, создание брони [K4 бронирование]». Аналогия — ресторан: дорожка «Гость» (заказывает), дорожка «Кухня» (готовит), а в «кухне» у каждого действия подписано, кто его делает: повар горячего цеха, кондитер, мойщик. Части КПП — это и есть «повара» нашей программы.
- **Три разные схемы, которые легко спутать** («процессорная» модель правильно называется **процессная**):

  | Схема | Что показывает | У нас | У одногруппников |
  |---|---|---|---|
  | ДДФ — дерево функций | из каких функций состоит F0 | `dfd-tree.png` | — |
  | ДПД уровня 2 | одна функция раскрыта на подфункции (F2.1…F2.5) со стрелками | нет: листья описаны BPMN или текстом | «F1…F5 декомпозиция». Они похожи на обычные DFD, потому что это и есть DFD, только на уровень ниже |
  | Процессная модель (BPMN) | порядок действий, ветвления, ожидание | путь покупателя и процессы его запросов (F2.1–F3.4) | один лист на весь сервис |
- **Один лист BPMN или несколько.**
  - Лист одногруппников помещается на слайд только потому, что он узкий и длинный: 2117 × 4200 точек, 63 элемента, шесть сценариев расходятся от одного шлюза «Сценарий работы?». Текст на слайде при этом не читается.
  - Преподаватель 04.11 говорил: «4 основных функции — 4 процесса», то есть свой процесс на каждую функцию. Отдельные процессы ближе к его словам.
  - У нас плохо читается не число листов, а раскладка Graphviz: кривые пунктиры к БД, цилиндры далеко от действий.
- **Состав документов (§2.3.5) простыми словами.** Берём документ как бланк и читаем его поле за полем: куда в ER ложится каждое поле. Преподаватель называет это «газетным анализом».
  - Пример — P08 «Заявка на бронирование»:
    - мероприятие → Мероприятие.ID;
    - места → Место.ID;
    - ФИО держателей → Билет.ФИО держателя;
    - промокод → Промокод.Код;
    - телефон и email → Заказ.Контактный телефон, Заказ.Контактный email.
  - Обратная проверка: у каждого атрибута ER должен быть источник. Он либо приходит во входящем документе (ФИО держателя — из P08), либо его создаёт сама система (срок брони = сейчас + 15 минут, код доступа, статусы).
  - Если поле документа никуда не ложится — в ER не хватает атрибута. Если атрибуту неоткуда взяться — не хватает документа. Так 12.11 нашлись недостающие P21–P26: для пользователей, организаторов и ролей не было ни одного входящего документа.
  - «Не хранится» — поля, которые есть в документе, но в БД не записываются. Это параметры запроса (период в P19 «Запрос отчёта») и то, что вычисляется на лету («сумма к оплате» в P09, «причина отказа»).
- **Как строить модель функционирования с нуля.** ER и DFD строятся **параллельно** и проверяют друг друга, а не одна после другой:
  1. Описание: участники, сценарии S1–S9, правила R01–R23, словарь.
  2. ER — из словаря и правил («что запомнить»).
  3. КД — из участников и сценариев: каждый участник → E; каждый шаг, где он что-то отдаёт или получает, → стрелка с названием документа P.
  4. Функции: шаги сценариев группируются по виду работы → F1–F6 и дерево. Имя функции — отглагольное существительное.
  5. ДПД-1: документы P разносятся по функциям (баланс). Для каждой функции решаем, что ей прочитать и что записать. Так появляются пары Q/A. Хранилища — это сущности ER, сгруппированные по тому, кто ими пользуется. Если одна функция передаёт что-то другой — стрелка I.
  6. Сверка: состав документов ↔ ER (газетный анализ) и правила ↔ данные (у правила есть пара Q/A, которая приносит то, что ему нужно). Нашли дыру — правим ER или DFD и повторяем.
  7. Требования FR пишутся из тех же сценариев, и каждое привязывается к функции (столбец «Функция»).
  8. Для листьев — BPMN или текст.

  Пример по сценарию S6 «Проход»: контролёр сканирует код, система проверяет билет и отвечает.
  - Участник — Контролёр (E3). Он отдаёт P17 «Код билета» и получает P18 «Результат проверки билета».
  - Работа — «Контроль входа» (F5).
  - Что F5 нужно:
    - условия входа (вход площадки, окно, полномочия) — читает D1 (Q20);
    - билет — погашает в D2 (Q10);
    - попытку и проход — записывает в D4 (Q11).
  - Газетный анализ P17: код → Попытка.Предъявленный код, вход → Вход.ID, мероприятие → Мероприятие.ID.
  - Правила R13, R14, R19 закрыты парами Q20 и Q10. Требование — FR-14. Порядок проверок — в таблице листьев (лист F5) и ПФ-5.
- **Что такое P «на самом деле».** P — логический документ: какие сведения и от кого кому. Формат в нём не задан: тот же документ может быть бумагой, экранной формой, JSON или письмом. Формат выбирается позже — в архитектуре (способ передачи на связи) и в Solution (конкретный запрос).

  | Документ (DFD) | В жизни | В Solution |
  |---|---|---|
  | P08 «Заявка на бронирование» | форма на сайте: места, ФИО, промокод | `POST /orders` с JSON `{"event_id": 17, "seats": [{"seat_id": 305, "holder_name": "Иванов Иван"}], "promo_code": "AUTUMN10", "contact_email": "buyer@example.com"}` |
  | P11 «Результат оплаты» | сообщение банка «сумма заблокирована» | вызов платёжного сервиса к нам `POST /payments/callback` с JSON `{"provider_txn_id": "tx-8841", "order_id": 512, "amount": 4500.00, "status": "authorized", "signature": "…"}` |
  | P12 «Итог покупки» | экран заказа с QR-кодом билета или причиной отказа | ответ `GET /orders/{id}`: билеты с `access_code` или `reject_reason` |
  | P17 «Код билета» | QR, отсканированный на входе | `POST /checkins` с JSON `{"access_code": "…", "gate_id": 3, "event_id": 17}` |
  | P01 «Сведения о площадке и схема зала» | файл или форма: зоны, ряды, места | `POST /admin/venues` и загрузка схемы |

  Цепочка: название документа (DFD) → его поля (§2.3.5) → связь и способ передачи (архитектура) → запрос с типами полей (Solution).

### Разбор вопросов по шагу 3 (третий круг)

- **Что такое P12 и почему он в F3.** P12 «Итог покупки» — то, что покупатель получает после оплаты: билеты с кодами или отказ с причиной. Он в F3, потому что билеты становятся действительными именно в момент оплаты: F3 переводит их из «зарезервирован» в «действителен» и выдаёт коды.
- **Почему F3 не берёт данные через I02.** Стрелка DFD — документ, который идёт в одну сторону, а не канал для вопросов. I02 «Бронь к оплате» — F2 сообщает F3 «вот заказ и сумма, выставляй счёт». Положить в I02 место и мероприятие можно, но оплата приходит до 15 минут спустя, а **функция не помнит данные между событиями: всё, что должно дождаться, лежит в хранилище**. Поэтому при оплате F3 читает D2 (билеты) и D1 (мероприятие, места) — это Q06 и Q24.
- **F2 и F3 — одна функция или две.** Функция DFD и процесс BPMN — разные вещи: процесс — путь во времени, он может проходить через несколько функций. Поэтому одна BP1 на две функции — нормально. Оставили две функции:
  - разные участники и документы: бронь — только с покупателем, оплата — с платёжным сервисом;
  - разные запуски: бронь запускает покупатель, оплату — сообщение банка и таймер;
  - разные компоненты (K4 и K5, K7, K10): платёжный сервис можно заменить, не трогая бронирование;
  - деньги — отдельная зона ответственности (защита от повтора, аудит, возвраты).

  Доводы за объединение тоже есть: для покупателя это одно действие «купить», бронь без оплаты пользы не несёт. На показе: «процесс — это путь покупателя, он проходит через две функции».
- **Зачем контролёру место.** Не нужно: задача контролёра — пропустить или нет. F5 находит билет по коду в D2 (Q10) и проверяет условия входа по D1 (Q20) — этого достаточно. Место убрали из P18.
- **Не зашить ли мероприятие в код билета.** Лишнее: даже подписанный код с номером мероприятия не скажет, возвращён ли билет и не прошёл ли по нему уже кто-то. Статус есть только в БД. Код у нас — случайная уникальная строка, по ней F5 находит билет.

### Вопросы для самопроверки

1. Почему на контекстной диаграмме нет хранилищ?
2. Что значит «баланс» и какие у нас числа?
3. Какой документ получит покупатель от F3 и что в нём может быть?

### Ответы на вопросы шага 3

1. **Хранилищ нет на КД**, потому что они — внутренности системы. Контекстная диаграмма показывает систему как чёрный ящик: только границу и документы, которыми она обменивается с внешним миром. Хранилища лежат внутри F0 и появляются при её раскрытии на уровне 1, там, где они нужны двум и более функциям.
2. **Баланс считается по каждой внешней сущности.** У покупателя (E1) 9 стрелок: отдаёт 4 (P06, P08, P13, P21), получает 5 (P07, P09, P12, P14, P22). На уровне 1 те же 9 с теми же названиями и направлениями. Всего 15 входящих + 14 исходящих = 29 документов на обоих уровнях. Входящих больше: платёжный сервис отвечает на подтверждение списания (P29), а сам ничего не получает в ответ. I01, I02 и 25 пар Q/A — внутренние и в баланс не входят.
3. **От F3 покупатель получает P12 «Итог покупки».**
   - В билетах: номер, держатель, место, мероприятие, код доступа.
   - В отказе — причина: «банк отклонил блокировку», «не списано» или «бронь истекла». В последнем случае деньги не списаны: система отменила счёт и блокировку (P27, R22). «Бронь истекла» приходит и тому, кто просто не успел оплатить за 15 минут (F3.4).
   - Билеты приходят только после ответа сервиса «списано» (P29).

## Шаг 4. Процессная модель (BPMN)

> **18.11 переделано по отзыву преподавателя 13.11** (разбор — `analysis/reports/R7_feedback_1311.md`). Он назвал прежний BP1 «громадным суперпроцессом» («жадность»): участник и программа на одном листе, внутренняя кухня программы «разорвана в клочья». Теперь: **путь покупателя** (BP1) без внутренностей программы и на каждый его запрос — **маленький процесс программы** (F2.1, F2.2, F3.1–F3.4): «спросил — ответили», один компонент, вход и выход — документы. Процессы — только для покупки (F2, F3), остальные листья описаны таблицей листьев. Таблицы дыр ниже — история прежней версии.

### Зачем

DFD — карта без времени: кто какие документы передаёт и где они хранятся. На ней не видно:
- порядка действий (сначала бронь, потом оплата);
- решений («если места заняты — отказ»);
- ожидания («ждём оплату 15 минут»);
- того, чем всё заканчивается.

BPMN добавляет время и логику. Аналогия: DFD — схема метро (станции и линии), BPMN — маршрут одной поездки: откуда едем, где пересадка, что делать, если станция закрыта, и где выходим.

Второе назначение — мост к архитектуре. Преподаватель 04.11: «за каждой группой операций стоит программный компонент, который работает с конкретной БД в отношении конкретного документа». Поэтому у каждого действия системы подписан компонент [Kn]. Из этих компонентов собирается архитектура (шаг 5).

1. Найти начало слева.
2. Идти по сплошным стрелкам.

4. Пунктиры вверх и вниз — какие документы уходят участникам и приходят от них.
5. Под действием — с какой БД оно работает и что пишет или читает.
6. Справа — все возможные концы.

| В BPMN | Из чего | Пример |

| процесс программы | лист дерева функций: один вход — один ответ | F2.2 «Оформление брони»: P08 → P09, I02 |
| путь участника | его обращения к программе по порядку | BP1: афиша → заявка → оплата → билеты |
| дорожка участника | внешняя сущность DFD | E1 → «Покупатель» |

| обращение к БД | пара Q/A DFD, каждая ровно один раз | Q04 в F2.2 = Q04 у F2 на ДПД-1 |
| состояние в документе | статус из ER (жизненный цикл в реестре) | «Билет [использован]» |

| цилиндр БД | хранилище DFD → группа данных | D2 → БД2 |

Сквозной пример. В процессе F2.2 действие «Проверка условий продажи и мест, создание брони [K4 бронирование]»:
- это работа функции F2;
- оно читает Q21 из D1 и пишет Q04 в D2 — те же пары, что у F2 на ДПД-1;
- компонент K4 в архитектуре — модуль бронирования, его путь расписан в ПФ-2;
- в Solution это функция `reserve_seats` и запрос `POST /orders`.

### Что помнить (числа)

- Путь покупателя BP1 и шесть процессов программы — по одному на лист F2.1, F2.2, F3.1–F3.4. Обращений к БД в них 9 = 9 парам F2 и F3 в DFD, каждая ровно один раз.
- По процессам: F2.1 — Q02, Q03; F2.2 — Q21, Q04; F3.1 — нет; F3.2 — Q05, Q25; F3.3 — Q06, Q24; F3.4 — Q07.
- Выходы покупателя в BP1: «Билеты у покупателя», «Отказ в брони», «Оплата не прошла». Перед двумя последними — выбор покупателя: «Выбрать места заново?» (тогда снова к афише) или «Повторить оплату?».
- Один документ — одно имя, вариант — в скобках: «P12 Итог покупки (билеты)», «P12 Итог покупки (отказ: не списано)», «P27 Решение о списании (списать)» / «(отменить)». Так же на ДПД-2.
- Главные решения:
  - бронь на 15 минут: её снимает отдельный процесс F3.4, он запускается по времени (R02);
  - явная проверка свободного ресурса «Места свободны, продажи открыты?». Одновременные заявки не дадут двух броней: это гарантирует уникальность в БД (R01);
  - двухстадийная оплата (R22): сервис блокирует сумму, система подтверждает списание или отменяет его, если бронь уже истекла; билеты — только после ответа «списано»;
  - возврат и проход в BPMN не рисуются: преподаватель требует процессы для 2–3 функций; они описаны таблицей листьев.

### Что может спросить преподаватель

- *Почему у вас путь покупателя отдельно от процессов программы?* — Так требовал преподаватель: показать путь пользователя без «внутренней кухни», а там, где пользователь обращается к программе, нарисовать маленький процесс «спросил — ответили». Каждый такой процесс — лист дерева функций, его выполняет один компонент над конкретными данными.
- *Почему процессы только для покупки?* — Он сказал: «выдернули две-три функции и сделали процессы… показали один процесс, как он вызывает другой». У нас это F2 и F3: бронирование передаёт оплате I02. Остальные листья описаны таблицей листьев: вход, обращения к БД, ответ, компонент.
- *Где проверка свободного ресурса?* — Шлюз «Места свободны, продажи открыты?» в процессе F2.2 после Q21 и Q04.
- *Что будет, если оплата придёт через 20 минут?* — Не придёт: через 15 минут сработал таймер, система сняла бронь, отменила счёт у платёжного сервиса («Решение о списании (отменить)») и сообщила покупателю «бронь истекла»; оплатить счёт уже нельзя, покупатель может выбрать места заново. Если сумма успела заблокироваться в последний момент, а бронь уже истекла, транзакция «Запись результата оплаты» это видит (бронь не жива — заказ не станет «оплачивается»): покупателю отказ, блокировка снимается, деньги не списываются.
- *Что если сервис не спишет деньги, а билеты уже выданы?* — Так не бывает: билеты выписываются только после ответа «списано» (P29). Пока ответа нет, заказ «оплачивается»: места удержаны, билетов нет. Ответ «не списано» — заказ снова в брони, платёж отменён, блокировка снята (P27 «отменить»), покупателю отказ; бронь действует до конца срока, можно оплатить снова (FR-27).
- *Если сумма заблокирована, откуда «не списано»?* — Редко, но бывает: между блокировкой и списанием карту заблокировали (украдена, сработал антифрод банка), банк сам снял блокировку, сбой у эквайера. Блокировка — обещание банка, а не деньги на нашем счёте; поэтому билеты выдаём только после ответа «списано». Если сервис просто не ответил, это не «не списано»: адаптер повторяет запрос с тем же ключом идемпотентности.
- *Что блокируется при брони?* — Место заранее не блокируем: билет создаётся при брони, и уникальность «одно место — один живой билет» (R01) сама не пустит второй билет. Второй покупатель ждёт, пока первый зафиксирует транзакцию, и получает «место занято». Места вставляются по возрастанию номера — нет взаимной блокировки (К-02). Строку промокода блокируем (`FOR UPDATE`), иначе два заказа увидят «осталось одно применение» и оба пройдут (К-04).
- *Что если банк ответит «списано» после 15 минут?* — Пока заказ «оплачивается», таймер его не снимает: место держится до ответа банка. При задержке адаптер переспрашивает исход по ID платежа; «списано» — один комплект билетов, повтор ответа ничего не меняет (Ф-21). Снимаются по сроку только брони, по которым оплата не началась.
- *Почему не выписать билеты и списать деньги одной транзакцией?* — Транзакция бывает только внутри нашей БД, банк в неё не входит: откатить списание вместе с БД нельзя. Держать транзакцию открытой, пока идёт сетевой вызов к банку, тоже плохо — всё это время заблокированы строки заказа. Поэтому шаги идут короткими транзакциями по порядку: записать «оплачивается» → списать → записать билеты; при сбое шаг повторяется (ключ идемпотентности) или отменяется (снятие блокировки).
- *Почему БД нарисована несколько раз?* — Как в ВКР («БД заказов (1), (2)»): у каждого обращения свой цилиндр, чтобы стрелки были короткими. Это одна и та же группа данных.
- *Сколько обращений к БД и почему столько же, сколько в DFD?* — 9, как у F2 и F3. Каждая пара Q/A DFD — это обращение, которое где-то происходит во времени. Если в BPMN его нет, непонятно, когда оно выполняется; если оно лишнее — в DFD забыли поток. Совпадение проверяет `check.py`.
- *Что значит [K5]?* — Компонент архитектуры, который выполняет действие. Из этих подписей выведены компоненты (шаг 5).
- *Почему распоряжение на возврат отправляется после транзакции?* — Перевод в банке нельзя откатить вместе с БД. Сначала надёжно записываем «ожидает», потом отправляем с повтором; повтор безопасен благодаря ключу идемпотентности.

### Речь на минуту

«Процессная модель — путь покупателя и маленькие процессы программы. На пути покупателя нет внутренностей программы: он запрашивает афишу, отправляет заявку на бронь, платит и получает билеты, а каждое его обращение обрабатывает свой процесс. Каждый процесс — лист дерева функций: получен документ, его обрабатывает один компонент, работая с БД, и отправляет ответ. Обращений к БД 9, столько же, сколько у бронирования и оплаты в DFD. Процессы связаны сообщениями: бронирование передаёт бронь оплате, ответы платёжного сервиса запускают приём оплаты и выписку билетов. Билеты выдаются только после того, как сервис подтвердил списание».

### Разбор вопросов по шагу 4

- **Что такое компонент.** Программа состоит из частей, у каждой своя работа: модуль бронирования (K4) держит места, модуль оплаты (K5) ведёт платежи, адаптер платёжного сервиса (K7) переводит наши запросы на язык банка, планировщик (K10) по таймеру снимает брони. Каждая часть — **компонент** (в ВКР — «часть КПП»). В коде это отдельный модуль Python со своими функциями. Подпись [K4] у действия значит «это действие выполняет модуль бронирования». На шаге 5 из этих подписей собирается архитектура: какие компоненты есть, с какими БД и кем они связаны. Аналогия — кухня ресторана: повар горячего цеха, кондитер, мойщик. Каждый делает своё, и по подписи видно, кто делает это действие.
- **Откуда обозначения (тонкий, толстый круг…).** Не из ГОСТа: российского ГОСТа на BPMN нет. Это международный стандарт **BPMN 2.0** (организация OMG, он же ISO/IEC 19510:2013). Преподаватель на занятии 16.10 назвал нотацию для процессов — BPMN, отдельно значки не объяснял. Вид листа (дорожка частей программы, БД у каждого обращения, примечания с принципами развития) — из ВКР, которую он принял. Сами значки — стандартные:
  - круг — событие: тонкий — начало, двойной — что-то случилось в середине (получено сообщение, сработал таймер), толстый — конец;
  - скруглённый прямоугольник — действие;
  - ромб — шлюз (решение или ожидание).
- **Что такое сообщение.** Пунктир с кружком — документ, который один участник передаёт другому: покупатель отправляет системе «Заявку на бронирование», система отвечает «Бронью». Это те же документы, что стрелки P на DFD, но здесь видно, **когда** документ уходит и **кто** его ждёт.
- **Действие и событие — в чём разница.** Действие (белый скруглённый прямоугольник) — работа, которая занимает время и которую кто-то выполняет: «Проверка условий продажи и мест, создание брони». Событие (круг) — то, что **случается** в момент времени и само ничего не делает: «решил купить билет» (начало), «получена бронь» (пришёл документ), «15 минут прошло» (таймер), «билеты у покупателя» (конец). Шлюз (ромб) — развилка: по какому пути идти дальше.
- **Как идти по стрелкам.** Не «сначала пунктирные, потом сплошные». Сплошные стрелки — порядок действий **внутри одного участника**: по ним идём, как по маршруту. Пунктирная — документ уходит **к другому участнику**. Дойдя до пунктира, смотрим, кто документ получает, и продолжаем там по его сплошным стрелкам. Пример BP1: покупатель «Выбор мест, заявка на бронь» → пунктир «Заявка на бронирование» вниз → система «Проверка условий продажи и мест» → сплошная к ромбу «Места свободны?» → «да» → «Бронь покупателю» → пунктир «Бронь» вверх → покупатель «Получена бронь» → сплошная к «Оплата заказа картой».

### Как работает платёжный сервис

Как залог в отеле: сначала сумму **блокируют** на карте, списывают позже. На примере заказа № 512 на 4500 ₽:
1. Система выставляет счёт (P10): «заказ 512, 4500 ₽». Сервис заводит платёж под этот счёт и даёт страницу оплаты.
2. Покупатель на странице сервиса вводит карту (вне нашей системы). Сопоставлять ничего не нужно: он платит именно по этому счёту.
3. Банк покупателя: деньги есть — **блокирует** 4500 ₽ (они на карте, но потратить нельзя); денег нет — отказ.
4. Сервис присылает нам результат (P11): номер операции, сумма, «заблокировано» или «отклонено».
5. Система решает (P27): «списать» — бронь жива, заказ «оплачивается»; «снять блокировку» — бронь истекла, деньги остаются у покупателя.
6. На «списать» сервис отвечает (P29): «списано» — только теперь система выписывает билеты; «не списано» — билетов нет, заказ снова в брони, платёж отменён, блокировка снята, покупателю отказ; пока бронь действует, можно оплатить снова.

Зачем две стадии: деньги берём, только когда точно можем выдать билеты. А билеты выдаём, только когда деньги точно взяты.

### Как читать покупку по шагам (BP1 и процессы программы)

Основной путь (билеты получены):
1. Покупатель «Решил купить билет» → «Просмотр афиши»: отправляет P06, процесс **F2.1** читает БД1 и БД2 (Q02, Q03) и возвращает P07.
2. «Выбор мест, заявка на бронь» → P08 → процесс **F2.2**: заново читает условия продажи (Q21) и занимает места (Q04) одной транзакцией. Ромб «Места свободны, продажи открыты?» — «да».
3. F2.2 отправляет покупателю «P09 Ответ на заявку (бронь)» и передаёт процессу **F3.1** «I02 Бронь к оплате». Покупатель на событийном шлюзе «Ответ на заявку?» получает бронь.
4. **F3.1** считает сумму и отправляет платёжному сервису «P10 Счёт на оплату». Покупатель платит картой на странице сервиса — это вне системы.
5. Сервис блокирует сумму и присылает «P11 Результат оплаты» → процесс **F3.2**: одной транзакцией записывает платёж (Q05) и ставит заказу «оплачивается» (Q25). «Сумма заблокирована и бронь жива?» — «да» (заблокирована — по P11, жива — по ответу БД A25), сервису уходит «P27 Решение о списании (списать)».
6. Сервис списывает деньги и отвечает «P29 Результат списания» → процесс **F3.3**: «Списано?» — «да», выписка билетов (Q06), сведения для билетов (Q24), покупателю «P12 Итог покупки (билеты)».
7. Покупатель на шлюзе «Итог покупки?» получает билеты → «Билеты у покупателя».

Другие пути:
- мест нет → F2.2 отправляет «P09 Ответ на заявку (отказ)» → покупатель «Получен отказ в брони» → «Выбрать места заново?»: «да» — снова к афише, «нет» — «Отказ в брони»;
- банк отклонил блокировку суммы → F3.2 отправляет «P12 Итог покупки (отказ: банк отклонил блокировку)» → покупатель «Причина отказа?» — «банк отклонил блокировку» → «Повторить оплату?»: «да» — снова к оплате (бронь действует), «нет» — «Оплата не прошла»;
- сервис не списал деньги → F3.3 записывает результат (заказ снова «бронь», платёж «отменён»), «Списано?» — «нет» → сервису «P27 Решение о списании (отменить)», покупателю «P12 Итог покупки (отказ: не списано)», билетов нет; у покупателя та же ветка «Повторить оплату?» (FR-27);
- 15 минут без оплаты → процесс **F3.4** сам, по времени, снимает бронь (Q07), отменяет у сервиса счёт и блокировку (P27) и сообщает покупателю «P12 Итог покупки (отказ: бронь истекла)» → «Причина отказа?» — «бронь истекла» → «Выбрать места заново?»;
- сумма заблокировалась, но бронь уже истекла → F3.2: «нет», «Сумма заблокирована?» — «да» → «Снятие блокировки» («P27 Решение о списании (отменить)») и покупателю «бронь истекла» — та же ветка «Выбрать места заново?». Деньги не списаны.

## Шаг 5. Архитектура (раздел 3)

### Зачем
DFD — логика (что делает система с данными), архитектура — устройство программы: из каких компонентов она состоит, как они связаны, где лежат данные, и **как каждая функция служит назначению** (ПФ).

### Что помнить
- 5 ЭСО (= E1–E5), 11 компонентов, 5 групп данных в одной БД PostgreSQL, 22 связи, 6 ПФ, 8 ПР.
- Компоненты — из листьев дерева функций, сгруппированных по данным и теме («за каждой группой операций стоит компонент»): 16 подфункций и листья F5, F6 → 8 модулей; плюс три по природе работы — K1 шлюз (вход и роли), K7 адаптер банка, K10 планировщик (запуск по времени).
- Назначение — четыре части по главным участникам: Н1 место продано один раз, Н2 билет или понятный отказ, Н3 проход только по действительному билету, Н4 организатор сам выставляет на продажу и видит итоги. Каждый ПФ начинается с «служит назначению … способом …».
- Рисунок ПФ — участок общей схемы, путь функции цветом; номер на стрелке = шаг в таблице шагов (электронное приложение).

### Что может спросить преподаватель
- *Почему не 16 компонентов по числу листьев?* — Листья с одними данными в разных программах — дублирование кода и автомата состояний (F4.1 и F4.2 считают возврат по одному правилу R16; F3.2–F3.4 меняют один заказ).
- *Почему K2 обслуживает F1 и F2?* — И публикация, и афиша работают с мероприятиями в БД1.
- *Почему БД нарисована у каждого компонента?* — Видно, кто к какой группе ходит; физически база одна (рамка внизу), решение A2 — ради одной транзакции бронь → оплата → билеты.
- *Чем ПФ отличается от BPMN?* — BPMN — порядок действий и развилки; ПФ — по каким компонентам и связям идут документы и где меняются состояния.

## Шаг 6. Solution (раздел 4)

### Зачем
Архитектура отвечает «что и как связано», Solution — «на чём и как именно»: стек, контейнеры, технология на каждой связи, запросы API с типами полей, физическая схема БД, развёртывание.

### Что помнить
- 3 контейнера: `app` (FastAPI; K1–K11), `db` (PostgreSQL 17), `payments-mock` (эмулятор банка, ESO5).
- 25 запросов API; у каждого — документ DFD, который он реализует (P08 → `POST /orders`, P11 → `POST /payments/callback`).
- Двойную продажу и повторный проход защищают уникальные индексы в БД; к банку — ключ идемпотентности.
- Платёж: принят (заблокировано) → списан / отменён; выручка — только по списанным.

### Что может спросить преподаватель
- *Почему нет nginx?* — Упрощение учебного стенда: один экземпляр приложения в локальной сети, TLS и балансировка не нужны, клиенты идут в `app:8000`. В эксплуатации перед `app` ставится nginx: HTTPS, балансировка нескольких экземпляров (ПР-2), ограничение частоты запросов. На схеме Solution он показан пунктиром.
- *Почему без ORM?* — Все запросы видны и объяснимы, правила-инварианты живут в функциях и триггерах PL/pgSQL (решение A5).
- *Что будет при «не списано»?* — Одной транзакцией заказ снова «бронь», платёж «отменён»; K7 отправляет отмену блокировки (P27), покупатель получает отказ и, пока бронь действует, может оплатить снова (FR-27, Ф-20).
