# 4 Методика испытаний и оценки качества

В разделе приведены программа и методика испытаний и методика оценки качества ПО. Испытания проводятся после завершения разработки приложения.

## 4.1 Программа и методика испытаний

Программа и методика испытаний разработаны по ГОСТ 19.301 \[20\] в следующем порядке:

1. по требованиям (подраздел 2.1) и критериям К1–К7 (подраздел 1.5) составлен перечень проверяемых свойств;
2. для каждого свойства определено испытание — сценарий, исходные данные и ожидаемый результат; некорректные операции подобраны так, чтобы каждое ограничение и код ошибки проверялись хотя бы раз;
3. определены состав обстоятельств, обусловливающих успешное проведение испытаний, и критерии приёмки;
4. требования, критерии, испытания и их связи занесены в базу данных качества (рисунок 5): до испытаний запрос выявляет непроверяемые требования, после прогона — выдаёт решение о приёмке.

Объект испытаний — база данных project_mgmt, версия схемы 013 (по таблице schema_migrations), со сценариями развёртывания, функциями, триггерами, представлениями, запросами и отчётами. Область применения — учёт проектов, команд, задач, трудозатрат и договоров организации (подраздел 1.1).

Предмет испытаний — свойства, которые проявляются при работе базы: правильность функций и отчётов, целостность данных при некорректных и одновременных операциях, атомарность составных операций, время выполнения модулей и воспроизводимость развёртывания.

Цель испытаний — установить, выполняет ли база данных требования к программе, и принять решение о приёмке.

Требования к программе — требования назначения ТН-1–ТН-3, функциональные ФТ-1–ФТ-21, функционально-технические ФТТ-1–ФТТ-4 и технические ТТ-1–ТТ-5 (подраздел 2.1) и критерии качества К1–К7 (подраздел 1.5).

Требования к программной документации — на испытания предъявляются пояснительная записка, файл README.md с порядком развёртывания и запуска сценариев, тексты миграций, сценариев проверок и наборов данных в репозитории; специальных требований к документации не задано.

Средства и условия испытаний (состав обстоятельств, обусловливающих успешное проведение испытаний):

- среда — PostgreSQL 16.15, Ubuntu 24.04 (WSL2), клиент psql; база разворачивается с нуля сценарием db/init.sh;
- данные — контрольный набор для проверок с заранее известным результатом, демонстрационный набор для отчётов и сценариев, нагрузочный набор 100 000 задач на отдельной базе для производительности;
- изменяющие проверки выполняются на копии базы (createdb -T), поэтому испытания не влияют друг на друга и повторяемы;
- дата расчёта показателей фиксирована — 14.11.2026, генератор данных детерминирован, поэтому результат воспроизводим;
- замеры времени выполняются после прогрева кэша, без посторонней нагрузки, берётся медиана нескольких прогонов.

Порядок проведения испытаний:

1. подготовка — база развёртывается с нуля, миграция 005 применяется к заполненной базе (И1, И8);
2. допуск — миграции применены без ошибок, контрольные данные загружены, а запрос к базе данных качества не находит требований без испытаний;
3. функциональные испытания, испытания целостности, транзакций и прав на копиях базы (И2–И7, И9–И12, И15);
4. нагрузочные испытания на отдельной базе со 100 000 задач (И13, И14);
5. регистрация фактических результатов и значений критериев в базе данных качества и решение о приёмке.

Испытания приостанавливаются, если схема базы изменена без новой миграции, повреждён исходный набор данных или замер искажён посторонней нагрузкой. После устранения причины база разворачивается заново и повторяются испытания, на которые повлияла причина. После исправления программы новой миграцией выполняется новый прогон: повторяются развёртывание И1 и испытания изменённых требований, найденные по связям в базе данных качества.

Виды испытаний: функциональные, целостности, транзакций и конкурентного доступа, нагрузочные, развёртывания и прав. Методы испытаний: каждое испытание выполняется сценарием из репозитория (db/init.sh, db/demo/\*.sql, db/demo/concurrency.sh, db/import/import_tasks.sql, db/perf/\*.py). Фактический результат сравнивается с ожидаемым. Для некорректной операции ожидается отказ СУБД с конкретным ограничением или кодом ошибки, для запросов — результат, заранее вычисленный по контрольным данным, для производительности — время не больше допустимого.

Критерии приёмки: испытания считаются успешными, если одновременно все 17 некорректных операций и 9 некорректных списаний часов отклонены, составные операции не оставляют частичных изменений, инвариант ёмкости соблюдён в обоих защищённых вариантах конкурентного доступа, результаты запросов совпадают с эталоном, а время каждого модуля при 100 000 задач не превышает 1 с. Качество ПО оценивается по критериям К1–К7 подраздела 1.5, построенным на модели качества ГОСТ Р ИСО/МЭК 25010 \[13\]. Для каждого критерия определены способ измерения, источник данных и требуемое значение (таблица 22).

| К1  | доля подфункций дерева функций, для которых есть таблицы, функции или SQL-операции                                           | дерево функций, технические компоненты (подраздел 3.1) | 100 %              |

Решение о приёмке выдаёт база данных качества: требование выполнено, если пройдены все его испытания и выполнены все его критерии. Связи требований с испытаниями приведены в таблицах 5 и 21, с критериями — в базе данных качества; уже сейчас она показывает, что все 33 требования покрыты.

Критерии К1–К7 относятся к модели качества продукта; качество при использовании (доля заданий, выполненных без помощи, время задания, удовлетворённость) оценивается на готовом приложении с пользователями.
