# 1 Анализ предметной области

В разделе дано вербальное описание предметной области: участники, объекты, правила и проблемы учёта. Построены функциональная и декларативная модели, определены показатели и критерии качества и формально поставлена задача.

## 1.1 Вербальное описание предметной области

Компания одновременно ведёт несколько проектов. Сотрудники зарегистрированы в системе как пользователи (ФИО, уникальный адрес почты, дата регистрации); новых сотрудников передаёт каталог сотрудников с единым входом (SSO) или вводит администратор. Посторонние лица и заказчики учётных записей не имеют.

Проект создаёт сотрудник, который становится его владельцем. У проекта есть уникальное название, короткий уникальный код (например, MOB, SHOP), описание, даты начала и окончания и статус. В команду проекта включают участников с одной из ролей, приведённых в таблице 1.

Таблица 1 — Роли участников проекта

| Роль (значение в БД)    | Обязанности                                                                                                                        |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Руководитель (manager)  | ведёт проект, планирует спринты, создаёт задачи, назначает исполнителей и сроки, закрывает спринты, принимает решения по эскалации |
| Разработчик (developer) | выполняет задачи и обсуждает их в комментариях                                                                                     |
| Тестировщик (tester)    | проверяет результаты задач, принимает их или возвращает на доработку                                                               |
| Аналитик (analyst)      | собирает и уточняет требования                                                                                                     |

Проекты выполняются для внутренних подразделений или для внешних заказчиков. О заказчике известны название (уникальное), контактное лицо и адрес почты. С заказчиком внешнего проекта заключается договор: номер (уникальный), дата подписания, сумма и бюджет часов. У проекта не более одного договора, у внутреннего проекта нет ни заказчика, ни договора. Заказчик с системой не работает: требования он передаёт руководителю проекта, а сведения о ходе проекта получает по почте.

Работа ведётся двухнедельными спринтами. У спринта есть номер в проекте, цель, даты начала и окончания, ёмкость в часах и состояние: запланирован, активный, закрыт. Руководитель планирует задачи в спринт так, чтобы сумма их оценок не превышала ёмкость. При закрытии спринта незавершённые задачи переходят в следующий спринт.

Задача имеет название (уникальное в проекте), описание, исполнителя из команды (может быть ещё не назначен), приоритет от 1 (наивысший) до 5, срок, оценку трудоёмкости в часах (может быть ещё не оценена) и ключ вида SHOP-42. Разработчик указывает ключ в описании коммита, и по нему система связывает изменения кода с задачей. Задачам назначают метки («bug», «frontend», «срочно»), у метки может быть цвет. Ход работы обсуждается в комментариях, которые нельзя терять. Состояния проекта: запланирован, выполняется, завершён, отменён (planned, active, completed, cancelled); спринта: запланирован, активный, закрыт; задачи: todo, in_progress, review, done.

Задача проходит жизненный цикл todo → in_progress → review → done; тестировщик может вернуть её на доработку, выполненную задачу можно переоткрыть, взять в работу можно только назначенную. Каждая смена статуса сохраняется в истории с моментом и автором, а изменения проектов, задач и договоров — в журнале аудита. Участники проекта ежедневно списывают на задачу фактически затраченные часы; по ним бюджет договора сравнивается с фактом. Бэклог заказчика загружают пакетом из файла CSV. Git-хостинг сообщает о коммитах веб-хуком, сервис уведомлений доставляет сообщения и отчёты по почте.

Система должна соблюдать следующие правила предметной области (далее — П1–П18):

- П1 — у каждого проекта есть владелец; пользователя нельзя удалить, пока он владеет проектом;
- П2 — название и код проекта уникальны, код состоит из 2–5 прописных символов, дата окончания проекта не раньше даты начала;
- П3 — пользователь входит в команду проекта не более одного раза и имеет в ней одну роль;
- П4 — у проекта не более одного заказчика, название заказчика уникально; заказчика нельзя удалить, пока у него есть проекты;
- П5 — договор есть только у проекта с заказчиком и заключён именно с ним; у проекта не более одного договора; проект с договором нельзя удалить или сделать внутренним; номер договора уникален, сумма неотрицательна, бюджет часов положителен;
- П6 — спринты проекта нумеруются уникально и не пересекаются по времени, активный спринт у проекта один, ёмкость спринта положительна, окончание спринта позже начала;
- П7 — задача входит в спринт только своего проекта и только оценённой; сумма оценок задач спринта не превышает его ёмкость; в закрытый спринт задачи не планируются; ёмкость нельзя уменьшить ниже запланированного объёма;
- П8 — исполнитель задачи — участник её проекта; при исключении участника из команды его задачи сохраняются, но становятся неназначенными;
- П9 — в пределах проекта названия задач не повторяются; приоритет — целое от 1 до 5; оценка неотрицательна, её отсутствие означает «не оценена»;
- П10 — статус задачи меняется только по жизненному циклу; взять в работу можно только назначенную задачу;
- П11 — момент завершения задачи известен тогда и только тогда, когда задача выполнена, и он не раньше момента её создания;
- П12 — каждая смена статуса задачи сохраняется в истории с моментом и автором;
- П13 — при удалении проекта удаляются его спринты, задачи, состав команды, обсуждения, история и трудозатраты задач;
- П14 — нельзя удалить автора комментариев и метку, назначенную задачам, — история сохраняется;
- П15 — комментарий не может быть пустым; адрес почты имеет корректный формат, цвет метки — формат #RRGGBB;
- П16 — изменения проектов, задач и договоров фиксируются в журнале аудита с типом операции, моментом, пользователем и изменёнными данными;
- П17 — сотрудник списывает не больше 24 ч в сутки по всем задачам; по задаче за день у сотрудника одна запись о часах, число часов положительно;
- П18 — часы списывает участник проекта на задачу в работе или на проверке за день от создания задачи до текущего; часы выполненной задачи не меняются; сотрудника со списанными часами нельзя удалить.

## 1.2 Проблемы учёта и способы их решения

Сложность предметной области определяют связи «многие ко многим» (участие сотрудников в проектах, метки задач), ограничения, зависящие от других строк (ёмкость спринта, суточный лимит часов, непересечение спринтов, исполнитель из команды), согласованность состояний (выполненная задача обязана иметь момент завершения), одновременная работа нескольких руководителей с одними и теми же спринтами, требование сохранять историю и взаимодействие с внешними сервисами. Основные проблемы учёта без единой системы и способы их решения приведены в таблице 2.

Таблица 2 — Проблемы предметной области и способы их решения

| Проблема                                                               | Последствие                                  | Способ решения в системе                                     |
| ---------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| Сведения о задачах распределены по переписке и таблицам                | данные дублируются и противоречат друг другу | единая БД, каждый факт хранится в одном месте (3НФ)          |
| Правила не проверяются при вводе                                       | недопустимые статусы, сроки, дубликаты       | ограничения PK, FK, UNIQUE, CHECK, EXCLUDE и триггеры        |
| Спринт перегружается задачами, особенно при одновременном планировании | срыв итерации, недостоверный план            | проверка ёмкости триггером с блокировкой строки спринта      |
| Незавершённые задачи «теряются» при смене итерации                     | работа не доводится до конца                 | закрытие спринта одной операцией с переносом задач           |
| Бюджет договора контролируется по оценкам, а не по факту               | перерасход часов обнаруживается поздно       | учёт трудозатрат, отчёт по договорам «план/факт» с прогнозом |
| Неизвестно, кто и когда менял задачу                                   | спорные ситуации не разрешить                | история статусов и журнал аудита триггерами                  |
| Бэклог заказчика вводится вручную                                      | ошибки ввода, потери времени                 | пакетная загрузка CSV с проверкой каждой строки              |
| Просрочки и перегрузка сотрудников видны поздно                        | срыв сроков, узкие места                     | запросы просрочек и нагрузки, отчёт о рисках                 |
| Удаление записей разрушает историю                                     | теряются обсуждения и ответственные          | правила удаления RESTRICT, CASCADE, SET NULL                 |

## 1.5 Показатели и критерии качества

Эффективность системы при эксплуатации характеризуют следующие показатели:

- время получения ответа на управленческий вопрос («какие задачи просрочены», «кто перегружен», «успеет ли проект к сроку», «уложится ли договор в бюджет»): вместо ручного сбора — однократное выполнение запроса;
- полнота выявления проблемных ситуаций: перегруженные спринты и сотрудники, просрочки, проекты без тестировщика, риски срыва сроков и перерасхода бюджета находятся запросами автоматически;
- достоверность данных: противоречивые записи не могут быть сохранены ни при каком способе изменения и ни при каком порядке одновременных действий пользователей, поскольку их отклоняет СУБД.

Качество ПО оценивается по характеристикам модели качества ГОСТ Р ИСО/МЭК 25010 \[13\]. Критерии, метрики и требуемые значения приведены в таблице 4. Расчётный объём — 100 000 задач: около 1000 проектов по 100 задач, что соответствует нескольким годам работы средней компании.

## 1.6 Постановка задачи

Дано: предметная область, описанная в подразделе 1.1, с правилами П1–П18; набор функций (рисунок 3) и элементов окружения (рисунок 1); СУБД PostgreSQL 16.

Требуется построить схему БД S в 3НФ, в которой правила П1–П18 выражены ограничениями и триггерами, и набор модулей M (SQL-сценариев и функций), реализующих функции системы, при трёх условиях. Первое — производительность:

$\max_{m\in M} t(m, N) \le T_{доп},$ (1)

где t(m, N) — время выполнения модуля m при объёме данных N = 100 000 задач, с;

T<sub>доп</sub> — допустимое время отклика, T<sub>доп</sub> = 1 с.

Второе — атомарность составных операций. Третье — корректность при конкурентном доступе: при любом порядке одновременного планирования задач в спринт s сохраняется инвариант ёмкости

$∑e_t \le C_s, t \in T(s),$ (2)

где e<sub>t</sub> — оценка задачи t, ч;

T(s) — множество задач спринта s;

C<sub>s</sub> — ёмкость спринта s, ч.

Входные данные — сведения о проектах, командах, спринтах, задачах и обсуждениях, файлы CSV; выходные — перечни, отчёты и история. Результат — база project_mgmt с модулями, программой и методикой испытаний и методикой оценки по К1–К7.
