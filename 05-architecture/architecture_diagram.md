# Пояснение к архитектурной диаграмме АС «Каршеринг»

## 1. Назначение

Файл `architecture.drawio.xml` показывает логическую архитектуру системы: границу системы, программные компоненты, информационные ресурсы, внешних участников и внешние системы, а также связи между ними. Диаграмма является логическим представлением; выбранные технологии описаны в техническом проекте.

## 2. Граница системы

Штриховая рамка `АС «Каршеринг»` включает:

- шлюз доступа к прикладным сервисам;
- модуль аутентификации и доступа;
- прикладные модули;
- подсистему интеграции с внешними системами;
- сервис уведомлений;
- базу данных и предметные информационные ресурсы.

Внешними являются арендатор, администратор, техническая служба, системы проверки паспорта и ВУ, телематический модуль, платёжный шлюз и SMTP-сервер.

## 3. Программные компоненты

| Обозначение | Компонент | Ответственность |
|---|---|---|
| `gateway` | Шлюз доступа | единая точка входа и маршрутизация |
| `auth` | Модуль аутентификации | JWT, роли, проверка прав |
| `registration` | Модуль регистрации | оферта, документы, пользователь |
| `rental` | Модуль аренды | поиск, начало, сведения, завершение |
| `state` | Модуль состояния | приём и хранение состояния |
| `finance` | Модуль финансовых обязательств | штрафы, задолженности, оплата |
| `maintenance` | Модуль обслуживания | перечень ТС на обслуживание |
| `admin` | Модуль администрирования | тарифы и парковки |
| `docs_adapter` | Адаптер проверки документов | паспорт и ВУ |
| `telemetry_adapter` | Адаптер телематики | команды и телеметрия |
| `payment_adapter` | Адаптер платежей | списание, ссылка, результат |
| `notifier` | Сервис уведомлений | формирование, отправка, повтор |

## 4. Информационные ресурсы

В составе базы данных перечислены предметные массивы: пользователи и документы, ТС, модели и паспорт ТС, состояние ТС, аренды, тарифы, парковки, штрафы, задолженности, история уведомлений. Логический массив может объединять несколько связанных сущностей; физическая структура таблиц раскрывается в техническом проекте.

## 5. Внешнее окружение

| Элемент | Назначение |
|---|---|
| Арендатор | регистрация, поиск, аренда, завершение, просмотр обязательств |
| Администратор | тарифы, парковки, штрафы, просмотр обязательств |
| Техническая служба | запрос перечня обслуживания |
| Система проверки паспорта | проверка паспортных данных |
| Система проверки ВУ | проверка водительского удостоверения |
| Телематический модуль ТС | открытие и закрытие, передача состояния |
| Платёжный шлюз | списание и результат оплаты |
| SMTP-сервер | доставка уведомлений |

## 6. Связи

- участники обращаются к системе через шлюз доступа;
- шлюз передаёт проверенный запрос прикладному компоненту;
- `registration` и `rental` вызывают адаптер проверки документов;
- адаптер обращается к системам проверки паспорта и ВУ;
- `rental` и `state` взаимодействуют с адаптером телематики;
- адаптер телематики передаёт команды и принимает телеметрию;
- `rental` и `finance` используют адаптер платежей;
- адаптер платежей отправляет запрос и принимает результат;
- прикладные компоненты читают и записывают базу данных;
- прикладные компоненты формируют события для сервиса уведомлений;
- сервис уведомлений отправляет письма через SMTP-сервер и участнику.

## 7. Типы связей

- сплошная линия — синхронный запрос и ответ;
- штриховая линия — асинхронное событие или сообщение;
- штриховая рамка — граница системы.

## 8. Правила согласованности

1. Обозначения компонентов совпадают с BPMN и техническим проектом.
2. Логические компоненты не превращаются в отдельные микросервисы без отдельного решения.
3. Внешние участники и системы не обращаются к базе данных напрямую.
4. Внешние системы подключаются через адаптеры.
5. База данных является общим источником состояния сущностей ER-модели.
6. Диаграмма является логическим представлением; стек описывается в техническом проекте.
