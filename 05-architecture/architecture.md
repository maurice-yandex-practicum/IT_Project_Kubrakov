# Архитектура программного обеспечения АС «Каршеринг»

## 1. Стороны и интересы

Арендатор заинтересован в подтверждённом начале, согласованном окончании, понятной стоимости и доступе к собственным обязательствам. Администратор представляет оператора и поддерживает справочники, начисление и достоверность расчётов. Техническая служба использует перечень ТО с основаниями. Архитектура связывает эти результаты с программными обязанностями и ресурсами.

## 2. Состав и граница

В границу серверного приложения входят следующие логические компоненты. Они работают в модульном монолите. Внешними являются три роли, имитаторы паспорта/ВУ/телематики, платёжный шлюз и SMTP-сервер. Для описания интересов, представлений, связей и решений используется ГОСТ Р 57100-2025; предметные принципы далее раскрываются через конкретные результаты.

|---|---|---|
| gateway | Приём, ответы и маршрутизация | RA3, RA8, RA9, RS4, RI4, ST4, ST5, MT4, MT5, FN4, FN5, FN7, RG1, RG8, RG9, AU3, AU4, FI3, OB4, CF4, PY11 |
| auth | JWT, роли, служебный доступ | RA1, RA13, RS1, RI1, ST1, MT1, FN1, CL5, RG6, AU1, AU2, FI1, OB1, CF1 |
| registration | Оферта, пользователь и документы | RG2, RG5, RG7 |

| state | F6: актуальное состояние и квитанции | RA6, RS2, ST2, ST3, FN2 |

## 3. Информационные ресурсы и доступ

PostgreSQL хранит D1–D9. Пользователи/документы, парк/ТО/состояние, аренды/снимки, справочники, обязательства и технические задания различаются по назначению. Ресурсы на схеме показывают это разделение.

- registration создаёт пользователя/документы D1; auth читает учётные данные.
- rental читает парк/состояние, справочники и задолженности; изменяет аренду D4, операционный статус D2 и записывает команды/задания D9.
- state читает карточку ТС, изменяет актуальную запись/квитанции D3. Обновления упорядочены временными отметками.
- finance ведёт D7/D8, финансовый результат D4 и историю операций/заданий D9.
- maintenance читает D2/D3, включая нормы модели и базу последнего ТО.
- admin изменяет D5/D6. Снимки стоимости D4 изменениями справочника не затрагиваются.
- адаптеры и notifier исполняют сохранённые задания своего типа и сохраняют результаты технического обмена.

## 4. Связи и содержание обменов

| Инициатор → адресат | Передаваемые сведения и результат |
|---|---|
| Участник → gateway → auth | запрос, JWT/роль либо сведения входа; результат доступа |
| gateway → прикладной компонент | проверенный запрос и контекст пользователя |
| registration/rental → docs_adapter → имитаторы | идентификатор проверки, серия/номер; valid/invalid/timeout |
| rental/maintenance → state | идентификатор ТС; телематические значения, отметка и возраст |
| rental → telemetry_adapter → имитатор | command_id, attempt_id, lease_version, command_seq; подтверждённый результат команды |
| Имитатор → telemetry_adapter → state | сообщение поддерживаемой схемы; квитанция после фиксации |
| rental/finance → payment_adapter → ЮKassa | сохранённая операция, сумма, RUB, ключ; внешний id, URL и проверенный статус |
| ЮKassa → payment_adapter → finance | сигнал и текущий объект; сверка metadata/магазина/суммы; однократное применение |
| rental/finance → notifier → SMTP | сохранённое уведомление, адресат и содержание; результат передачи серверу |

Прикладные компоненты обращаются к перечисленным ресурсам. Внешние вызовы выполняются вне транзакций; исходящее действие связано с предметной записью сохранённым заданием. Схема содержит повторную проверку документов из rental и перенос F11 в finance.

## 5. Принципы функционирования

### 5.1. Подтверждённый допуск к автомобилю

auth определяет пользователя; rental проверяет ТС и задолженность, docs_adapter повторно проверяет документы, state предоставляет свежие сведения. rental защищает создание starting блокировкой ТС и сохраняет условия/задание. telemetry_adapter исполняет команду, rental принимает только соответствующее попытке и сроку подтверждение. Результат — active с временем начала либо объяснимый отказ и blocked до согласования. Проверки: П-04–П-07; результат для участника — П-24.

### 5.2. Достоверное состояние и доступность

state сравнивает отметку и обновляет данные атомарно; telemetry_adapter не передаёт техническому признаку право менять операционный статус. rental/maintenance получают одно актуальное состояние по ТС с его возрастом. Согласование закрытия использует поколение команды. Результат — поиск и оформление используют допустимый автомобиль, устаревшее событие не освобождает занятый ТС. Проверки: П-03, П-07, П-17–П-21.

### 5.3. Воспроизводимая стоимость

rental сохраняет условия попытки, started_at задаётся подтверждением открытия, ended_at — успешной проверкой парковки в транзакции до внешних вызовов. F4 и F5 читают снимок, используют одну формулу округления минут; admin меняет только справочник. Результат — стоимость объясняется конкретной продолжительностью и условиями, ожидание открытия не оплачивается. Проверки: П-08, П-09, П-16, П-24.

### 5.4. Окончание и финансовый исход

rental фиксирует finished и задания; закрытие и оплата завершаются независимо от ответа на запрос окончания. finance обрабатывает только проверенный объект, историю попыток и допустимый переход. Отказ аренды создаёт долг один раз, неизвестный исход остаётся pending, несовместимый результат вызывает сверку. Результат участнику доступен в F4/F11 и уведомлении. Проверки: П-09–П-14, П-22, П-28.

### 5.5. Сохранность продолжения

Предметные изменения и исходящие задания фиксируются одной транзакцией PostgreSQL. Обработчик компонента арендует задание, выполняет вызов с тем же идентификатором и сохраняет результат. Перезапуск не создаёт новое списание; устаревшая команда не затрагивает следующую аренду. SMTP повторяется по сохранённому заданию, а сбой письма не отменяет предметный результат. Проверки: П-07, П-22, П-23.

### 5.6. Результат обслуживания и границы доступа

maintenance соединяет состояние, базу ТО и регламент модели, выдаёт каждую причину включения. auth и прикладные компоненты проверяют роль и владельца; gateway формирует различимые ответы. Результат — пригодный перечень технической службе и отсутствие чужих сведений у арендатора. Проверки: П-02, П-14–П-16, П-25–П-26.

## 6. Развитие

Изменение формата интеграции локализуется адаптером и проверяется совместимостью П-21/П-28. Новый тариф не меняет сохранённые условия аренды; проверка П-16 сохраняется при развитии справочников. Изменение данных выполняется миграцией с сохранением связей и истории попыток. Рост нагрузки требует повторного П-20 на заданном профиле; масштабируется серверное приложение. Новый канал уведомлений реализуется notifier при сохранении предметного события. Новая бизнес-функция требует изменения области и своей цепочки требований/проверок.

## 7. Обоснование решения

Модульный монолит позволяет согласовать предметные записи и задания транзакциями PostgreSQL при ограниченном учебном объёме. Разделение ответственности сохраняет происхождение компонентов из операций. Адаптеры отделяют форматы внешнего обмена от предметных переходов. Раздельные пулы и ограничение приёма отделяют телеметрию от пользовательского чтения в выбранном нагрузочном профиле. Надёжность и пригодность этих механизмов оцениваются испытаниями; их наличие в описании не является результатом выполненного программного прогона.
